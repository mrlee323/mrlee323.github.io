## 처음에 틀렸던 가정들

LLM을 처음 제품에 붙일 때 몇 가지를 당연하게 생각했다. 다 틀렸다.

**"응답이 빠를 것이다"** — GPT-4o-mini 기준으로도 응답이 3~8초 걸린다. 사용자는 3초 이상부터 이탈한다. Non-streaming이면 사용자는 빈 화면을 보다가 갑자기 결과를 받는다.

**"API가 안정적일 것이다"** — OpenAI 포함 모든 LLM API는 간헐적으로 느려지거나 타임아웃이 난다. rate limit도 예상보다 자주 맞는다. retry 로직 없이 배포하면 사용자 에러율이 갑자기 튄다.

**"비용이 관리될 것이다"** — 입력 토큰 수에 무관심하면 특정 요청 하나가 예상 비용의 10배가 된다. 긴 context를 그대로 넘기거나, 필요 없는 리뷰를 전부 포함하거나.

**"프롬프트는 나중에 정리해도 된다"** — 프롬프트가 소스코드에 하드코딩되면 A/B 테스트가 배포 없이 불가능하다. 프롬프트 수정 = 코드 배포가 되어버린다.

## 스트리밍: 넣어야 하는 이유와 넣는 방법

UX 관점에서 스트리밍은 옵션이 아니다. "AI가 생각하고 있다"는 시각적 피드백이 없으면 사용자는 앱이 멈췄다고 생각한다.

스트리밍은 크게 두 가지 방식이 있다.

**텍스트 스트리밍** — LLM이 토큰을 생성하는 대로 클라이언트로 흘려보낸다. `text/event-stream` 또는 Server-Sent Events. 채팅 UI나 긴 설명 텍스트에 적합하다.

**Partial JSON 스트리밍** — structured output과 스트리밍을 같이 써야 할 때. Vercel AI SDK의 `streamObject`가 이걸 처리해준다. 필드별로 채워지는 걸 실시간으로 렌더링할 수 있다.

```typescript
// Route Handler에서 Vercel AI SDK 스트리밍
import { streamText } from "ai";
import { openai } from "@ai-sdk/openai";

export async function POST(req: Request) {
  const { prompt } = await req.json();

  const result = streamText({
    model: openai("gpt-4o-mini"),
    prompt,
    maxTokens: 1024,
  });

  return result.toDataStreamResponse();
}
```

```typescript
// 클라이언트에서 useChat
import { useChat } from "@ai-sdk/react";

function SummaryComponent() {
  const { messages, isLoading } = useChat({ api: "/api/ai/summary" });

  return (
    <div>
      {isLoading && <StreamingIndicator />}
      {messages.map((m) => (
        <div key={m.id}>{m.content}</div>
      ))}
    </div>
  );
}
```

주의할 점은 스트리밍 중 에러 처리다. non-streaming이면 HTTP status code로 에러를 전달할 수 있지만, 스트리밍은 응답 헤더가 이미 200으로 나간 뒤에 에러가 발생할 수 있다. SSE 프로토콜에서는 `event: error` 타입으로 에러를 내려보내고 클라이언트가 처리해야 한다.

## 비용: 실제로 돈이 나가는 지점들

LLM 비용에서 가장 놀랐던 건 캐싱이다. 같은 입력을 반복해서 보내는 경우가 생각보다 많다. 숙소 상세 페이지에서 리뷰 요약을 요청할 때, 같은 숙소를 10명이 같은 날 보면 10번 API를 호출한다.

Redis에 `propertyId + reviewHash`를 키로 응답을 캐싱하면 실제 API 호출 횟수가 급감한다. 리뷰가 바뀌지 않는 한 같은 숙소의 요약은 재생성할 이유가 없다.

```typescript
async function getOrGenerateSummary(propertyId: string, reviews: Review[]) {
  const reviewHash = hashReviews(reviews);
  const cacheKey = `summary:${propertyId}:${reviewHash}`;

  const cached = await redis.get(cacheKey);
  if (cached) return JSON.parse(cached);

  const summary = await generateSummary(reviews);

  // TTL 24시간 — 리뷰가 업데이트되면 hash가 바뀌어서 자연스럽게 무효화
  await redis.set(cacheKey, JSON.stringify(summary), { ex: 86400 });

  return summary;
}
```

두 번째 비용 포인트는 context 크기다. 리뷰를 전부 넘기지 않고 최근 30개, 또는 평점별로 샘플링해서 넘기는 것만으로도 입력 토큰이 절반 이하가 된다. 품질 차이는 생각보다 작다.

세 번째는 모델 선택이다. GPT-4o가 필요한 태스크와 GPT-4o-mini로 충분한 태스크를 구분하면 비용이 10분의 1로 줄 수 있다. 요약, 분류, 단순 추출은 거의 항상 mini로 된다.

## 에러 처리: LLM은 일반 API와 다르다

일반 API 에러 처리와 LLM 에러 처리는 다르다. 일반 API는 대부분 즉각 응답하고 에러 코드가 명확하다. LLM은 타임아웃이 길고, 에러 종류가 많으며, 부분 실패 개념이 있다.

에러를 크게 세 가지로 나눠서 처리한다.

**Retriable 에러** — 429 (rate limit), 500/503 (일시적 서버 에러). 지수 백오프로 재시도한다.

**Non-retriable 에러** — 400 (잘못된 요청), 401 (인증 실패). 재시도해도 같은 에러가 난다.

**Timeout** — 응답이 오지 않는 상태. `AbortSignal.timeout(25_000)`으로 hard cut하고 사용자에게 명시적으로 알린다.

```typescript
async function callLLMWithRetry(
  request: LLMRequest,
  maxRetries = 2
): Promise<LLMResponse> {
  let lastError: Error;

  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    try {
      return await callLLM(request);
    } catch (error) {
      if (isNonRetriable(error)) throw error;

      lastError = error as Error;
      if (attempt < maxRetries) {
        await sleep(Math.pow(2, attempt) * 1000); // 1s, 2s
      }
    }
  }

  throw lastError!;
}
```

에러 UX도 중요하다. "AI 요약을 불러올 수 없습니다" 대신 "요약을 생성하는 데 시간이 걸리고 있습니다. 잠시 후 다시 시도해주세요."처럼 사용자가 다음 행동을 알 수 있게 한다.

## 프롬프트 관리: 소스코드에서 꺼내야 하는 이유

프롬프트가 소스코드에 있으면 몇 가지가 불가능해진다.

1. **배포 없는 프롬프트 수정** — 버그 수준의 프롬프트 문제가 생겨도 코드 배포 프로세스를 거쳐야 한다.
2. **A/B 테스트** — 어떤 프롬프트가 더 나은 결과를 내는지 실험하려면 배포 플래그나 별도 인프라가 필요하다.
3. **비개발자 협업** — PM이나 콘텐츠 담당자가 프롬프트를 개선하려면 개발자를 거쳐야 한다.

Langfuse, Helicone 같은 LLM observability 도구는 프롬프트 관리 기능도 제공한다. 버전 관리, A/B 실험, 성능 추적이 된다. 자체 DB에 프롬프트 테이블을 두는 것도 방법이다.

최소한 해야 하는 것은 프롬프트를 상수로 분리하는 것이다. 파일 하나에 몰아두면 수정 범위가 명확해진다.

## AI 기능을 안 쓰는 게 맞을 때

LLM이 모든 문제의 해결책은 아니다. 오히려 쓰면 안 되는 경우가 있다.

**결정론이 필요한 곳** — 가격 계산, 날짜 처리, 재고 확인. LLM은 확률적이다. "현재 객실 재고가 있나요?"에 LLM을 쓰면 틀릴 수 있다.

**빠른 응답이 핵심인 인터랙션** — 검색 자동완성, 버튼 클릭 피드백. 300ms 안에 응답해야 하는 UI에 LLM을 넣으면 UX가 망가진다.

**패턴이 명확한 분류** — 리뷰가 긍정인지 부정인지 분류하는 거라면 fine-tuned된 작은 모델이나 규칙 기반이 더 빠르고 싸다.

AI 기능을 붙이는 판단 기준은 "이게 LLM이 아니면 불가능한가"다. 가능하다면 LLM 없이 구현하는 게 대부분 더 낫다.

## 1년 운영 후 바뀐 것들

처음에 없었던 것들이 지금은 기본이 됐다.

- **LLM 응답 로깅** — 어떤 입력에 어떤 결과가 나왔는지 기록. 프롬프트 개선의 근거가 된다.
- **토큰 사용량 모니터링** — 이상 탐지. 평소보다 토큰이 10배 나가면 알림.
- **결과 캐싱** — 동일 입력 재요청 방지.
- **프롬프트 버전 관리** — 변경 이력과 성능 비교.
- **사용자 피드백 수집** — 엄지 위/아래. 어떤 요약이 좋은지 실제 데이터가 쌓인다.

처음부터 이걸 다 갖출 필요는 없다. 하지만 운영이 시작되면 이 중 하나씩 필요성을 느끼게 된다. 그때 급하게 만드는 것보다 설계 단계에서 자리를 비워두는 게 낫다.
