## TypedArray가 존재하는 이유

일반 `Array`는 사실 이름만 배열입니다. 엔진 입장에서는 어떤 타입이든 담을 수 있고, 길이도 바뀌고, 중간이 비어 있을 수도 있는 **객체**에 가깝습니다. V8이 최적화로 연속 메모리처럼 다루긴 하지만, 그건 어디까지나 엔진의 추측(elements kind)이고 언제든 깨질 수 있습니다.

문제는 바이너리 데이터를 다룰 때 터집니다.

- WebGL/WebGPU는 GPU로 **정확한 바이트 레이아웃**을 넘겨야 한다
- 파일, 네트워크 소켓, 오디오는 **바이트 스트림**이다
- WebAssembly의 선형 메모리는 **하나의 큰 바이트 배열**이다

`[0.1, 0.2, 0.3]`을 GPU에 넘기려면 각 숫자가 32비트 float로 연속 배치되어야 하는데, 일반 배열은 그걸 보장하지 못합니다. TypedArray는 이 요구에서 나왔습니다.

> "데이터의 메모리 레이아웃을 개발자가 직접 확정한다."

## 내부 동작 방식

### 버퍼와 뷰의 분리

핵심 설계는 **저장소와 해석을 분리**한 것입니다.

```
ArrayBuffer (고정 길이 raw 바이트)
┌────┬────┬────┬────┬────┬────┬────┬────┐
│ 00 │ 00 │ 80 │ 3F │ 00 │ 00 │ 00 │ 40 │   8 bytes
└────┴────┴────┴────┴────┴────┴────┴────┘
   ▲ Float32Array 뷰: [1, 2]       (4바이트씩)
   ▲ Uint8Array 뷰:   [0,0,128,63,0,0,0,64]
   ▲ Uint16Array 뷰:  [0, 16256, 0, 16384]
```

`ArrayBuffer`는 읽고 쓰는 방법이 **없습니다.** 길이만 있는 바이트 덩어리일 뿐입니다. 읽고 쓰려면 반드시 뷰가 필요합니다.

```javascript
const buf = new ArrayBuffer(8);
const f32 = new Float32Array(buf);
const u8 = new Uint8Array(buf);

f32[0] = 1;
console.log(u8); // Uint8Array [0, 0, 128, 63, 0, 0, 0, 0]
```

`f32[0] = 1`이 `u8`에 바로 반영된 이유는 둘이 **같은 메모리를 가리키기 때문**입니다. 복사가 일어나지 않습니다. 이게 TypedArray의 가장 큰 성능 이점이자 가장 큰 함정입니다.

### 뷰 생성자의 세 가지 얼굴

`new Float32Array(...)`는 인자에 따라 완전히 다르게 동작합니다.

| 인자 | 동작 | 메모리 |
|---|---|---|
| 숫자 `new Float32Array(4)` | 새 버퍼 할당 | 새로 생성 |
| 배열/이터러블 `new Float32Array([1,2])` | 값을 변환해 복사 | 새로 생성 |
| 버퍼 `new Float32Array(buf, offset, len)` | 기존 버퍼 위에 뷰 생성 | **공유** |

### 요소 접근은 어떻게 동작하나

`f32[i]`는 대략 `buffer.byteOffset + i * 4` 위치의 4바이트를 float32로 해석해 읽는 연산입니다. 그래서 모든 요소의 크기가 같아야 하고, 인덱스 계산이 단순한 곱셈이라 JIT이 매우 공격적으로 최적화할 수 있습니다.

쓸 때는 타입 변환이 **조용히** 일어납니다.

```javascript
const u8 = new Uint8Array(1);
u8[0] = 300;
console.log(u8[0]); // 44  (300 mod 256, 에러 없음)

const clamped = new Uint8ClampedArray(1);
clamped[0] = 300;
console.log(clamped[0]); // 255 (범위로 고정)
```

범위를 넘는 값은 에러가 아니라 **모듈러 연산으로 잘립니다.** `Uint8ClampedArray`는 캔버스 픽셀(0~255)처럼 포화 연산이 필요한 경우를 위한 별도 타입입니다.

### 엔디언과 DataView

TypedArray는 **실행 환경의 네이티브 엔디언**으로 읽습니다. 사실상 현재 대부분의 플랫폼이 리틀 엔디언이라 문제가 드러나지 않을 뿐입니다. 네트워크 프로토콜이나 파일 포맷처럼 엔디언이 명세에 고정된 데이터는 `DataView`를 씁니다.

```javascript
const view = new DataView(buf);
view.setUint32(0, 0x12345678, false); // false = 빅 엔디언
view.getUint32(0, true);              // 리틀 엔디언으로 읽으면 다른 값
```

`DataView`는 오프셋마다 타입과 엔디언을 지정하므로 **서로 다른 타입이 섞인 헤더 구조**를 파싱하는 데 적합하고, TypedArray는 **같은 타입이 연속된 대량 데이터**에 적합합니다.

## 실제로 언제 쓰는가

**적합한 경우:**
- WebGL/WebGPU 버텍스·유니폼 버퍼
- 파일 업로드 전 바이너리 파싱, 이미지/오디오 처리
- WebAssembly와의 메모리 공유
- Web Worker 간 대용량 데이터 전달 (`postMessage`의 transfer, `SharedArrayBuffer`)
- 대량 숫자 연산에서 메모리 사용량을 줄여야 할 때

**쓰지 않아도 되는 경우:**
- 데이터가 수백 개 수준이고 `map`/`filter` 체이닝이 주 용도일 때
- 길이가 동적으로 자주 변하는 컬렉션 (`push`가 없습니다)
- 숫자가 아닌 값이 섞이는 경우

OTA 서비스에서 이 개념을 마주치는 대표적인 순간은 **영수증/바우처 파일 처리**입니다. 서버에서 받은 PDF 응답을 `fetch`로 받아 `arrayBuffer()`로 읽고, 매직 넘버(`%PDF`)를 `Uint8Array`로 검사하거나 `Blob`으로 바꿔 다운로드시키는 식입니다. 이때 `arrayBuffer()`가 반환하는 건 배열이 아니라 **버퍼**이고, 읽으려면 뷰를 씌워야 한다는 구조가 그대로 드러납니다.

```javascript
const res = await fetch("/api/voucher/123.pdf");
const buf = await res.arrayBuffer();
const head = new Uint8Array(buf, 0, 4);
const isPdf = String.fromCharCode(...head) === "%PDF";
```

## 흔한 오해와 함정

### 1. TypedArray는 Array가 아니다

```javascript
const t = new Uint8Array([1, 2, 3]);
Array.isArray(t); // false
t.push(4);        // TypeError: t.push is not a function
```

길이가 고정이라 `push`, `pop`, `splice`가 없습니다. `map`, `filter`, `slice`는 있지만 **같은 타입의 TypedArray를 반환**합니다. 결과를 문자열로 바꾸는 `map`은 기대와 다르게 동작합니다.

```javascript
new Uint8Array([1, 2, 3]).map((x) => String(x)); // Uint8Array [1, 2, 3] (문자열이 숫자로 되돌아감)
```

### 2. slice는 복사, subarray는 공유

```javascript
const a = new Uint8Array([1, 2, 3, 4]);

const copied = a.slice(0, 2);     // 새 버퍼에 복사
const shared = a.subarray(0, 2);  // 같은 버퍼의 다른 구간을 보는 뷰

a[0] = 99;
console.log(copied[0]); // 1
console.log(shared[0]); // 99
```

이름이 비슷해서 헷갈리지만 의미는 정반대입니다. 큰 버퍼를 잘라 넘길 때 `subarray`는 비용이 거의 없지만, 원본이 바뀌면 같이 바뀌고 **원본 버퍼 전체가 GC되지 않고 유지**됩니다. 작은 조각만 오래 들고 있을 거라면 `slice`로 복사해 큰 버퍼를 놓아주는 편이 낫습니다.

### 3. 오프셋 정렬 규칙

```javascript
const buf = new ArrayBuffer(8);
new Float32Array(buf, 1, 1);
// RangeError: start offset of Float32Array should be a multiple of 4
```

뷰의 `byteOffset`은 요소 크기의 배수여야 합니다. 헤더가 홀수 바이트인 바이너리 포맷을 파싱할 때 이 에러를 만납니다. 이럴 때 `DataView`가 정렬 제약 없이 읽을 수 있어 대안이 됩니다.

### 4. 버퍼 크기는 바꿀 수 없다 (그리고 transfer하면 사라진다)

`ArrayBuffer`는 기본적으로 크기가 고정입니다. Worker로 보낼 때 `postMessage(buf, [buf])`로 **transfer**하면 복사 없이 소유권이 넘어가고, 보낸 쪽의 버퍼는 **detached** 상태가 되어 길이가 0이 됩니다.

```javascript
worker.postMessage(buf, [buf]);
console.log(buf.byteLength); // 0
console.log(f32.length);     // 0 (같은 버퍼를 본 뷰도 전부 무효화)
```

일반 `postMessage(buf)`는 structured clone으로 **복사**합니다. 수십 MB를 보낼 땐 transfer 여부가 성능을 가릅니다.

### 5. 정밀도는 타입이 정한다

```javascript
const f = new Float32Array(1);
f[0] = 0.1;
console.log(f[0]); // 0.10000000149011612
```

JS의 `number`는 float64인데 `Float32Array`에 저장하면 32비트로 잘립니다. 금액 계산에 쓰면 안 되고, 반대로 GPU 입력처럼 32비트가 필요한 경우엔 의도한 동작입니다.

## 정리

TypedArray의 핵심은 **"바이트는 ArrayBuffer가 갖고, 해석은 뷰가 한다"** 입니다.

바이너리를 다루거나 대량의 같은 타입 숫자를 연산해야 한다면 TypedArray를, 그렇지 않다면 일반 Array로 충분합니다. 쓰기 전에 지금 만드는 것이 **복사본인지 공유 뷰인지**만 먼저 확인하세요. 대부분의 버그는 거기서 나옵니다.
