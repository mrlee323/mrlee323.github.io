## Symbol이 존재하는 이유

ES5까지 객체의 프로퍼티 키는 사실상 문자열뿐이었습니다. 이건 두 가지 문제를 만들었습니다.

1. **키 충돌** — 라이브러리 A와 B가 같은 객체에 `id`, `_meta` 같은 키를 붙이면 서로 덮어씁니다. 여러 팀이 만지는 객체, 혹은 서드파티가 확장하는 객체에서 흔한 사고입니다.
2. **언어 확장의 벽** — 언어 명세가 `for...of`를 도입하려면 객체가 "순회 가능하다"는 표시가 필요합니다. 그런데 `iterate` 같은 문자열 키를 정하는 순간, 이미 그 이름을 쓰던 기존 코드가 깨집니다.

> "기존 코드와 절대 충돌하지 않는 키를 만들 수 없을까?"

Symbol은 이 질문의 답입니다. 같은 설명(description)으로 만들어도 매번 **고유한 값**이 나오는 원시 타입이고, 이게 있어야 `Symbol.iterator` 같은 언어 훅을 하위 호환을 지키면서 추가할 수 있었습니다.

```js
const a = Symbol("id");
const b = Symbol("id");
a === b; // false — description은 식별자가 아니라 디버깅용 라벨
```

## 내부 동작 방식

### 값 자체가 정체성이다

Symbol은 `new` 없이 호출하는 팩토리이고, 반환값은 객체가 아니라 **원시값**입니다. 문자열처럼 값으로 비교되지만, 그 "값"이 생성 시점에 엔진이 발급한 고유 토큰이라는 점이 다릅니다. description은 `toString()`이나 디버거에 보이는 라벨일 뿐 동일성 판단에 쓰이지 않습니다.

### 프로퍼티 키로서의 Symbol

객체의 프로퍼티 키는 `string | symbol` 두 종류입니다. 엔진은 내부적으로 두 키를 따로 관리합니다.

```js
const SECRET = Symbol("secret");
const user = { name: "mimi", [SECRET]: 42 };

Object.keys(user);                 // ["name"]
JSON.stringify(user);              // '{"name":"mimi"}'
for (const k in user) {}           // "name"만
Object.getOwnPropertySymbols(user) // [Symbol(secret)]
Reflect.ownKeys(user)              // ["name", Symbol(secret)]
```

`Object.keys`, `for...in`, `JSON.stringify`가 Symbol 키를 건너뛰는 건 의도된 설계입니다. 기존 코드가 순회하던 결과에 새 키가 섞여 들어가지 않아야 하위 호환이 지켜지기 때문입니다.

### Global Symbol Registry

`Symbol()`은 호출할 때마다 새 값을 만들지만, `Symbol.for(key)`는 **전역 레지스트리**에서 같은 key면 같은 Symbol을 돌려줍니다.

```js
Symbol.for("app.token") === Symbol.for("app.token"); // true
Symbol.keyFor(Symbol.for("app.token"));              // "app.token"
```

iframe, 다른 realm, 번들이 분리된 모듈 사이에서 "같은 Symbol"을 공유해야 할 때 쓰는 장치입니다. 반대로 말하면 `Symbol.for`는 전역 네임스페이스를 다시 여는 셈이라, 충돌 방지라는 원래 목적이 약해집니다. 그래서 `"app.token"`처럼 네임스페이스를 붙이는 관례가 생겼습니다.

### Well-known Symbol: 언어가 열어둔 훅

진짜 핵심은 이쪽입니다. 엔진은 특정 동작을 수행할 때 객체에서 well-known symbol 키를 찾아 호출합니다.

| Symbol | 엔진이 언제 보는가 |
|---|---|
| `Symbol.iterator` | `for...of`, 스프레드, 구조분해 |
| `Symbol.asyncIterator` | `for await...of` |
| `Symbol.toPrimitive` | 객체를 원시값으로 변환할 때 |
| `Symbol.hasInstance` | `instanceof` 평가 |
| `Symbol.toStringTag` | `Object.prototype.toString` 결과 |

```js
class Range {
  constructor(a, b) { this.a = a; this.b = b; }
  *[Symbol.iterator]() {
    for (let i = this.a; i <= this.b; i++) yield i;
  }
}
[...new Range(1, 3)]; // [1, 2, 3]
```

`[...range]`는 내부에서 `range[Symbol.iterator]()`를 호출해 iterator를 얻고 `next()`를 반복합니다. 문자열 키였다면 이런 프로토콜을 나중에 추가하는 건 불가능했을 겁니다.

## 실제로 언제 쓰는가

**적합한 경우:**
- 커스텀 이터러블, `toPrimitive` 등 언어 프로토콜을 구현할 때
- 라이브러리가 사용자 객체에 메타데이터를 붙이되 사용자 키와 충돌하면 안 될 때
- 외부에 노출하고 싶지 않은 "준-비공개" 키가 필요할 때 (열거 대상에서 제외)

**쓰지 않아도 되는 경우:**
- 진짜 비공개가 필요한 경우 — `#private` 필드가 맞습니다. Symbol 키는 `getOwnPropertySymbols`로 누구나 꺼낼 수 있습니다.
- 단순 상수 구분 — 직렬화·로깅에서 불편해지는 비용이 더 큽니다. TS의 `unique symbol` 타입이 필요한 경우가 아니라면 문자열 리터럴 유니온이 낫습니다.

```ts
// src/lib/store.ts
const STORE_META = Symbol("store.meta");

export function attachMeta<T extends object>(target: T, meta: Meta) {
  return Object.assign(target, { [STORE_META]: meta });
}
```

## 흔한 오해와 함정

### 1. "Symbol은 private이다"

```js
// 오해
const _pw = Symbol("pw");
const user = { [_pw]: "1234" };

// 현실
Object.getOwnPropertySymbols(user).map(s => user[s]); // ["1234"]
```

숨겨질 뿐 막히지는 않습니다. 접근 제어는 `#field`나 클로저가 담당합니다.

### 2. JSON과 구조화 복제에서 사라진다

`JSON.stringify`는 Symbol 키도, Symbol 값도 버립니다. `structuredClone`은 Symbol 값을 가진 프로퍼티에서 `DataCloneError`를 던지고, Symbol 키는 복제하지 않습니다. 직렬화가 필요한 데이터에 Symbol을 섞으면 조용히 유실됩니다.

### 3. 암시적 문자열 변환 불가

```js
const s = Symbol("x");
`${s}`;      // TypeError
s + "";      // TypeError
String(s);   // "Symbol(x)" — 명시적 변환은 허용
```

문자열로 실수로 새어 나가 키 충돌을 일으키는 걸 막기 위한 의도적 제약입니다.

### 4. `Symbol.for`와 `Symbol()` 혼용

모듈 두 곳에서 한쪽은 `Symbol("k")`, 다른 쪽은 `Symbol.for("k")`를 쓰면 서로 다른 값입니다. 공유가 목적이라면 한 가지로 통일하고, 모듈에서 export한 상수를 import해서 쓰는 쪽이 더 안전합니다.

## 정리

Symbol의 핵심은 **"문자열 네임스페이스에 의존하지 않는 고유 키"** 입니다. 사용자 코드와 충돌하지 않는 확장 지점을 만들어야 할 때, 혹은 이터레이터 같은 언어 프로토콜을 구현할 때 꺼내 쓰세요. 진짜 비공개나 단순 상수 구분이 목적이라면 `#private`이나 문자열 리터럴이 더 적절합니다.
