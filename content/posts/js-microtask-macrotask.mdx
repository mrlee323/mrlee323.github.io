## 큐가 두 개로 나뉜 이유

이벤트 루프를 설명할 때 "콜 스택이 비면 큐에서 하나 꺼낸다"까지는 다들 압니다. 그런데 왜 큐가 **두 종류**일까요?

Promise가 도입되기 전에는 비동기 후속 작업이 전부 `setTimeout`, I/O 콜백 같은 태스크였습니다. 문제는 "방금 끝난 작업의 직후에 반드시 실행돼야 하는 후속 처리"를 표현할 방법이 없었다는 점입니다. 태스크로 밀어 넣으면 그 사이에 렌더링이나 다른 이벤트 핸들러가 끼어들 수 있습니다.

Promise의 `.then`은 이 요구를 충족해야 했습니다.

- 같은 동기 코드 흐름의 **연장선**처럼 실행되어야 한다
- 그 사이에 다른 태스크나 렌더링이 끼어들면 안 된다 (상태가 중간에 노출되면 안 되기 때문)

그래서 HTML 명세는 **마이크로태스크 큐**를 따로 두었습니다.

> 매크로태스크는 "다음 턴에 할 일", 마이크로태스크는 "이번 턴이 끝나기 전에 마무리할 일"입니다.

## 내부 동작 방식

한 번의 루프 반복(tick)은 대략 이렇게 흘러갑니다.

```
[매크로태스크 1개 실행]
        ↓
[마이크로태스크 큐를 완전히 비움]  ← 실행 중 추가된 것도 포함
        ↓
[렌더링 기회: rAF → style → layout → paint]
        ↓
[다음 매크로태스크]
```

핵심은 **비우는 규칙의 차이**입니다.

| | 매크로태스크 | 마이크로태스크 |
|---|---|---|
| 대표 | setTimeout, setInterval, I/O, 이벤트 핸들러, MessageChannel | Promise.then/catch/finally, queueMicrotask, MutationObserver |
| 한 번에 처리 | **1개** | **큐가 빌 때까지 전부** |
| 렌더링과의 관계 | 사이사이 렌더링 가능 | 렌더링 전에 반드시 소진 |
| 실행 중 새 작업 추가 | 다음 턴으로 | **같은 턴 안에서 계속 실행** |

마지막 줄이 중요합니다. 마이크로태스크가 또 마이크로태스크를 등록하면, 엔진은 큐가 완전히 빌 때까지 렌더링도 다음 매크로태스크도 허용하지 않습니다.

```javascript
console.log("1 sync");
setTimeout(() => console.log("5 macro"), 0);
Promise.resolve().then(() => console.log("3 micro"));
queueMicrotask(() => console.log("4 micro"));
console.log("2 sync");
// 1 sync → 2 sync → 3 micro → 4 micro → 5 macro
```

스크립트 전체 실행 자체가 하나의 매크로태스크이므로, 그것이 끝난 직후 마이크로태스크가 먼저 비워지고, 그다음에야 `setTimeout` 콜백이 실행됩니다.

### 이벤트 핸들러 안에서의 마이크로태스크

사용자 클릭처럼 브라우저가 호출하는 핸들러에서는 콜백이 끝나 콜 스택이 비는 시점에 마이크로태스크 체크포인트가 실행됩니다. 그래서 **핸들러가 여러 개 등록되어 있어도 각 핸들러 사이마다 마이크로태스크가 비워집니다.** 반면 `element.click()`처럼 스크립트가 직접 디스패치하면 스택이 비어 있지 않아, 모든 핸들러가 끝난 뒤에야 마이크로태스크가 돕니다. 같은 코드인데 순서가 달라지는 대표적인 사례입니다.

## 실제로 언제 쓰는가

**마이크로태스크가 적합한 경우:**
- 동기 코드가 끝난 직후, 렌더링 전에 상태를 정리해야 할 때
- 여러 동기 호출을 모아 한 번만 처리하는 배칭 (`queueMicrotask`로 flush 예약)
- 라이브러리가 "항상 비동기"로 콜백을 호출하도록 보장할 때

```javascript
let scheduled = false;
const pending = new Set();

export function enqueue(item) {
  pending.add(item);
  if (scheduled) return;
  scheduled = true;
  queueMicrotask(() => {
    scheduled = false;
    flush([...pending]);
    pending.clear();
  });
}
```

**매크로태스크가 적합한 경우:**
- 브라우저가 렌더링하거나 입력을 처리할 틈을 줘야 할 때
- 무거운 작업을 쪼개서 UI 응답성을 유지해야 할 때
- 타이머 기반 지연 실행

여행 서비스의 검색 결과 리스트처럼 수천 건을 가공해야 하는 화면이라면, 한 번에 `Promise.all`로 처리하는 것보다 청크 단위로 매크로태스크 경계를 두는 편이 체감 성능이 좋습니다.

## 흔한 오해와 함정

### 1. "async 함수니까 UI가 안 멈추겠지"

`await`는 마이크로태스크 경계일 뿐, 렌더링 경계가 아닙니다.

```javascript
// 수정 전: 렌더링 기회가 한 번도 없다
async function processAll(items) {
  for (const item of items) {
    await heavy(item); // 이미 resolve된 Promise면 마이크로태스크만 계속 돈다
  }
}

// 수정 후: 일정 간격으로 매크로태스크에 양보
async function processAll(items) {
  for (let i = 0; i < items.length; i++) {
    await heavy(items[i]);
    if (i % 50 === 0) await new Promise((r) => setTimeout(r, 0));
  }
}
```

### 2. 마이크로태스크 무한 루프는 setTimeout 무한 루프와 다르다

```javascript
// 탭이 완전히 멈춘다 (렌더링 불가)
function loop() { Promise.resolve().then(loop); }

// 느리지만 UI는 살아 있다
function loop() { setTimeout(loop, 0); }
```

### 3. setTimeout(fn, 0)은 0ms가 아니다

중첩 5단계 이상이면 브라우저가 최소 4ms로 클램핑합니다. "즉시 다음 턴"을 원하면 `MessageChannel`이나 `scheduler.postTask`를 고려해야 합니다.

### 4. 마이크로태스크 안의 에러

`.then` 체인 밖에서 던져진 에러는 `unhandledrejection`으로 올라오고, `queueMicrotask` 안의 예외는 일반 uncaught error로 보고됩니다. 둘의 처리 경로가 다르다는 것을 기억해야 합니다.

### 5. Node.js는 한 단계가 더 있다

Node에서는 `process.nextTick` 큐가 Promise 마이크로태스크보다 **먼저** 비워집니다. 또한 Node 11 이후 타이머/immediate 콜백 사이사이에도 마이크로태스크가 비워지도록 브라우저와 동작이 맞춰졌습니다.

## 정리

마이크로태스크와 매크로태스크의 차이는 **"큐를 얼마나 비우느냐"** 입니다. 매크로태스크는 한 번에 하나, 마이크로태스크는 빌 때까지 전부.

상태 일관성이 중요한 후속 처리는 마이크로태스크로, UI에 숨 쉴 틈을 줘야 하는 작업은 매크로태스크로 나누세요. `await`가 곧 양보는 아니라는 점만 기억해도 UI 멈춤 버그의 상당수를 예방할 수 있습니다.
