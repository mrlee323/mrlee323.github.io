## 버튼 하나에 상태가 다섯 개였다

"알림 받기" 버튼입니다. 눌리면 신청되고 다시 누르면 취소됩니다. 여기까지가 기획이었습니다.

실제로 구현하려니 화면이 구분해서 보여줘야 하는 경우가 이만큼 나왔습니다.

- 신청할 수 있는 상태
- 이미 신청한 상태
- 신청 기간이 **마감된** 상태
- **로그인이 안 된** 상태
- 앱 **푸시 수신 동의가 꺼진** 상태
- 기획전이 이미 **오픈된**(발송이 끝난) 상태

여섯 가지고, 각각 문구와 동작이 다릅니다. 마감이면 눌러도 소용없다고 알려야 하고, 수신 동의가 꺼져 있으면 설정으로 보내야 하고, 비로그인이면 로그인 후 **돌아와서 신청까지 이어져야** 합니다.

## 처음엔 프론트에서 판단하게 만들었다

익숙한 방식으로 시작했습니다. 서버는 사실만 주고 프론트가 조합해서 판단하는 구조입니다.

```ts
// 처음 구조 — 서버가 준 값들로 프론트가 판단
const state = (() => {
  if (!isLoggedIn) return 'NEED_LOGIN'
  if (now > applyEndAt) return 'CLOSED'
  if (!pushAgreed) return 'NEED_AGREE'
  if (alreadyApplied) return 'APPLIED'
  return 'AVAILABLE'
})()
```

깔끔해 보였고 실제로 동작했습니다. 문제는 곧 나왔습니다.

**첫째, 같은 판단을 하는 곳이 늘어났습니다.** 웹에서 한 번, 앱 웹뷰에서 한 번, 그리고 어드민의 미리보기에서 또 한 번. 조건이 다섯 개면 다섯 개를 세 곳에서 똑같이 유지해야 합니다. 하나가 빠지면 **플랫폼마다 다른 문구가 뜹니다.**

**둘째, 시간 판단이 클라이언트에 있었습니다.** `now > applyEndAt` 의 `now` 는 사용자 기기 시각입니다. 기기 시간이 틀어진 사용자에게는 마감이 아닌데 마감으로 보이거나 그 반대가 됩니다. 신청 마감처럼 **돈이나 약속이 걸린 판단을 클라이언트 시계로 하면 안 됩니다.**

**셋째, 진짜 판정은 어차피 서버에서 또 합니다.** 프론트가 "신청 가능"이라고 판단해서 요청을 보내도, 서버는 그 요청을 다시 검증해야 합니다. 안 그러면 API를 직접 호출해서 마감된 건에 신청할 수 있으니까요. **결국 같은 규칙이 두 곳에 존재**했습니다.

세 번째가 결정적이었습니다. 어차피 서버가 판단해야 한다면, 프론트가 미리 흉내 내는 판단은 **중복이자 불일치의 원천**일 뿐입니다.

## 서버가 상태를 하나로 내려주게 바꿨다

구조를 뒤집었습니다. 서버가 상태 코드 하나를 내려주고, 프론트는 **코드를 화면에 매핑하기만** 합니다.

```ts
// 바꾼 구조 — 서버가 판정, 프론트는 매핑만
const VIEW = {
  AVAILABLE:   { label: '오픈 알림 받기', action: 'apply' },
  APPLIED:     { label: '알림 신청 완료', action: 'cancel' },
  CLOSED:      { label: '신청이 마감되었습니다', action: null },
  NEED_LOGIN:  { label: '로그인하고 알림 받기', action: 'login' },
  NEED_AGREE:  { label: '알림 설정하기', action: 'openSettings' },
  DONE:        { label: '오픈되었습니다', action: 'goDetail' },
} as const

const view = VIEW[res.code]
```

프론트에 조건문이 사라졌습니다. 새 상태가 생기면 서버가 코드를 추가하고 프론트는 매핑에 한 줄을 더합니다. **웹·앱·미리보기가 자동으로 같은 판단을 공유**합니다.

여기서 프론트를 해온 게 도움이 됐습니다. **상태 코드의 개수를 "화면이 구분해서 보여줘야 하는 문구의 개수"로 정했습니다.** 서버 입장에서만 설계하면 성공/실패 둘이거나, 반대로 내부 사정을 반영해 지나치게 잘게 쪼갭니다. 둘 다 프론트에서 다시 뭉치거나 나눠야 해서 조건문이 되돌아옵니다.

> API 응답의 분기 개수는 **화면의 분기 개수와 같아야** 합니다.

## 진짜 어려웠던 건 우선순위였다

상태를 서버로 옮기고 나니 새 문제가 생겼습니다. **여러 조건에 동시에 걸리면 무엇을 보여줄 것인가.**

마감됐고, 이미 신청했고, 수신 동의도 꺼져 있는 사용자가 있습니다. 셋 다 사실입니다. 하나만 골라야 합니다.

처음엔 코드 순서대로, 즉 검사하기 편한 순서로 두었습니다. 로그인 → 동의 → 중복 → 마감 순이었습니다. 그랬더니 이런 화면이 나왔습니다.

> 마감된 기획전인데 **"이미 신청하셨습니다"** 라고 뜬다

틀린 말은 아닙니다. 그런데 사용자가 이 화면에서 알고 싶은 건 **"그래서 나한테 알림이 오나?"** 입니다. "이미 신청됨"은 온다는 뜻으로 읽힙니다. 실제로는 마감돼서 안 옵니다.

그래서 우선순위를 다시 정했습니다.

| 순위 | 조건 | 왜 이 순서인가 |
|---|---|---|
| 1 | **마감** | 이 뒤의 어떤 상태든 결과가 안 바뀐다. 가장 먼저 알려야 할 사실 |
| 2 | 로그인 필요 | 로그인 없이는 아래 조건 자체를 판단할 수 없다 |
| 3 | 수신 동의 필요 | 신청해도 실제로 못 받는 상태. 신청 전에 해결해야 함 |
| 4 | 이미 신청 | 여기까지 왔으면 정상 경로 |
| 5 | 발송 완료 | 이미 끝난 건 |

기준을 한 문장으로 정리하면 이렇습니다.

> **뒤의 조건을 해결해도 결과가 안 바뀌는 것부터 알려준다.**

마감된 건에서는 로그인을 하든 동의를 켜든 알림이 오지 않습니다. 그러면 마감을 먼저 알려야 합니다. 반대로 수신 동의는 켜면 해결되는 문제라 나중입니다. **사용자가 행동해서 바꿀 수 있는 것일수록 뒤로** 갑니다.

이건 서버 로직처럼 보이지만 사실 UX 판단입니다. 프론트를 안 해봤으면 "검사 비용이 싼 순서"로 짰을 것 같습니다.

## 무엇을 포기했나

이 구조에도 대가가 있습니다.

**낙관적 UI를 포기했습니다.** 버튼을 누르면 즉시 "신청 완료"로 바꾸고 뒤에서 요청을 보내는 방식이 반응은 빠릅니다. 하지만 판정이 서버에 있으니 응답을 받아야 다음 상태를 압니다. 대신 **화면과 실제가 어긋나는 일이 없습니다.**

알림 신청은 초 단위 반응성보다 **정확성이 중요한 기능**이라고 봤습니다. "신청됐다고 떴는데 알림이 안 왔다"는 신뢰를 깎지만, 버튼이 0.2초 늦게 바뀌는 건 아무도 항의하지 않습니다.

**서버 왕복이 늘었습니다.** 상태 조회가 필요한 지점마다 요청이 갑니다. 이건 캐시 정책으로 다뤘고, 마감 시각이 지나면 무효화되도록 했습니다.

## 정리

- **판정이 두 곳에 있으면 반드시 어긋납니다.** 서버가 어차피 검증해야 한다면 판정은 서버 하나입니다
- **시간 판단을 클라이언트에 두지 않습니다.** 기기 시계는 믿을 수 없습니다
- **응답 코드 개수 = 화면 분기 개수.** 이걸 맞추면 프론트에서 조건문이 사라집니다
- **우선순위 기준: 해결해도 결과가 안 바뀌는 것부터.** 사용자가 행동으로 바꿀 수 있는 조건일수록 뒤로
- **반응성보다 정확성이 중요한 기능이 있습니다.** 무엇을 포기할지 정하는 것도 설계입니다

[다음 글](/posts/frontend-to-fullstack-notification-3)에서는 이 기능의 가장 어려웠던 부분을 다룹니다. **신청하는 시점과 실제로 보내는 시점 사이에 며칠이 있다**는 것, 그 사이에 세상이 바뀐다는 문제입니다.
