## 분명히 켜뒀는데 꺼져 있다

기능을 내보내고 한참 뒤였습니다. 운영자가 알림 설정을 켜뒀는데 나중에 보면 꺼져 있다는 이야기가 나왔습니다.

재현이 안 됐습니다. 설정하고 저장하면 잘 남아 있습니다. 로그를 봐도 누가 끈 기록이 없습니다. **끈 사람이 없는데 꺼져 있는 상태**였습니다.

원인은 이거였습니다.

> 같은 페이지 데이터를 편집하는 **다른 기능**이 저장할 때, 자기가 모르는 필드를 빼고 저장하고 있었다.

알림 설정은 기획전 페이지 데이터 안에 필드로 들어갑니다. 그런데 그 페이지를 편집하는 도구가 하나가 아니었습니다. 페이지 구성을 편집하는 기능이 따로 있었고, 그 편집기는 **자기가 아는 필드만으로 데이터를 다시 조립해서 저장**했습니다.

알림 설정 필드는 그 편집기가 만들어진 뒤에 추가된 것이라 목록에 없었습니다. 그래서 페이지 구성을 한 번 손대면 그 필드가 조용히 사라졌습니다.

## 왜 못 잡았나

이건 각 기능만 보면 버그가 아닙니다.

- 알림 기능은 **자기 필드를 잘 저장**합니다
- 편집 기능은 **자기 필드를 잘 저장**합니다
- 둘 다 테스트를 통과합니다

문제는 **"저장한다"의 의미가 서로 달랐다**는 데 있습니다. 한쪽은 "내 필드를 갱신한다"였고 다른 쪽은 "이 문서를 내가 아는 모양으로 다시 쓴다"였습니다. 후자는 모르는 것을 지웁니다.

그리고 이 조합은 **두 기능을 번갈아 써야만** 드러납니다. 각 기능 담당자는 자기 기능만 테스트하니까 안 걸립니다. 실제로 운영에서 며칠 지나 나왔습니다.

## 고친 방식: 모르는 것을 지우지 않는다

수정 자체는 크지 않았습니다. 편집기가 저장할 때 **자기가 모르는 필드를 그대로 통과시키도록** 바꿨습니다.

```ts
// 문제 — 아는 필드로만 다시 조립한다
const next = {
  layout: editor.layout,
  blocks: editor.blocks,
}

// 수정 — 원본을 보존하고 아는 부분만 덮는다
const next = {
  ...original,        // 모르는 필드도 그대로 살아남는다
  layout: editor.layout,
  blocks: editor.blocks,
}
```

코드는 한 줄이지만 **원칙이 하나 생겼습니다.**

> 하나의 문서를 여러 편집기가 다룬다면, 각 편집기는 **자기가 모르는 것을 지우지 않아야** 한다.

이게 왜 중요하냐면, 앞으로 필드가 또 늘어나기 때문입니다. 이번에 알림 설정이 사라졌으니 그 필드만 목록에 추가하는 식으로 고쳤다면, 다음에 추가되는 필드에서 **같은 사고가 다시 납니다.** 목록에 하나 넣는 수정은 증상을 고치는 것이고, 통과시키는 수정은 구조를 고치는 것입니다.

## 배운 것: 얹기 전에 누가 또 건드리는지 본다

1편에서 "기존 시스템에 얹는다"를 골랐고, 그건 지금도 옳은 판단이었다고 생각합니다. 그런데 얹을 때 확인했어야 하는 걸 하나 빠뜨렸습니다.

**내가 넣는 데이터를 누가 또 건드리는가.**

기존 시스템에 얹을 때는 보통 "내가 이걸 건드려도 되나"를 확인합니다. 반대 방향은 잘 안 봅니다. 하지만 공유되는 데이터에 필드를 추가하는 건, **그 데이터를 다루는 모든 코드에 영향을 주는 변경**입니다.

지금은 공유 데이터에 필드를 추가할 때 이걸 먼저 확인합니다.

- 이 데이터를 **쓰는(write)** 코드가 몇 개인가
- 그중 **전체를 다시 조립해서 저장**하는 곳이 있는가
- 있다면 그 코드가 모르는 필드를 어떻게 다루는가

읽는 곳은 문제가 안 됩니다. 모르는 필드를 무시하면 그만입니다. **쓰는 곳이 위험**합니다.

## 되돌릴 수 없는 동작 앞에는 잠금을 둔다

같은 기능에서 어드민 쪽에 넣은 설계도 적어둡니다. 결이 같은 이야기입니다.

운영자가 알림 설정을 하고 **테스트 발송**을 해볼 수 있게 했습니다. 그런데 테스트 발송 이후에 설정을 자유롭게 고칠 수 있으면 문제가 생깁니다. 테스트로 확인한 내용과 실제로 나갈 내용이 달라집니다. "테스트했는데 왜 다르게 갔죠?"가 나옵니다.

그래서 **테스트 발송을 하면 설정이 잠기게** 했습니다. 고치려면 명시적으로 [다시 수정]을 눌러야 하고, 그러면 테스트를 다시 해야 합니다.

처음엔 과하다고 생각했는데, 3편에서 적은 것과 같은 이유였습니다. **푸시는 되돌릴 수 없습니다.** 되돌릴 수 없는 동작 앞에는 한 단계 마찰을 두는 게 맞습니다. 마찰이 없으면 실수가 그대로 사용자에게 갑니다.

다만 이미 예약이 잡힌 건은 **수정을 허용**했습니다. 여기서 완전히 막으면 오타 하나를 고치려고 예약을 지우고 처음부터 다시 만들어야 합니다. 안전을 이유로 운영을 불가능하게 만들면, 운영자는 결국 시스템 밖에서 우회합니다.

> 잠금은 **실수를 막을 만큼만** 걸고, 그 이상은 걸지 않습니다.

## 연재를 마치며

프론트엔드 개발자로 일하다가 기능 하나를 여섯 구간에 걸쳐 만들었습니다. 끝나고 남은 건 새로 배운 스택보다 **판단 기준**이었습니다.

- **익숙하지 않은 영역일수록 기존 구조를 따른다** — 자유도는 틀릴 자유도이기도 하다 (1편)
- **판정이 두 곳에 있으면 어긋난다** — 어차피 서버가 검증한다면 판정은 하나다 (2편)
- **시점이 다른 검증을 합치지 않는다** — "자격이 있는가"와 "지금 보내도 되는가"는 다르다 (3편)
- **모르는 것을 지우지 않는다** — 공유 데이터는 쓰는 쪽이 위험하다 (4편)
- **되돌릴 수 없는 동작 앞에는 마찰을 둔다** — 단, 운영이 가능한 선까지만 (4편)

그리고 가장 크게 바뀐 건 **범위 감각**이었습니다. 프론트만 할 때는 화면까지가 내 일이었는데, 이제는 **기능이 실제로 완결되는 지점까지**가 범위가 됐습니다. 중간의 어느 구간이 남의 일이라고 생각하는 순간, 그 경계에서 문제가 납니다. 그리고 사용자에게는 그냥 "안 되는 기능"입니다.

서버를 잘하게 됐다고는 못 하겠습니다. 규모나 성능 판단은 여전히 검토를 받아야 하는 영역입니다. 다만 **모르는 걸 아는 척하지 않으면 관통할 수 있다**는 건 확인했습니다.
