## 왜 지금 하네스인가?

3년 넘게 운영 중인 서비스는 코드보다 관성이 더 강합니다. 사람이 바뀌고, 기능이 쌓이고, "일단 돌아가면 된다"는 판단이 반복되면서 조용히 기술 부채가 누적됩니다.

새 기능을 추가하기 전에, 잘못된 코드가 들어오지 못하도록 막는 **정적 분석 하네스**와 팀이 같은 방향으로 움직이게 하는 **컨벤션 하네스**를 먼저 갖추기로 했습니다.

목표는 간단합니다.

> **"나쁜 코드가 리뷰를 통과하기 전에, 도구가 먼저 잡아낼 것"**

---

## 1단계: TypeScript ESLint 하네스

기존 ESLint 설정은 Next.js 기본 룰 + 몇 가지 커스텀 규칙만 있었습니다. `.ts` / `.tsx` 파일에 TypeScript 전용 분석이 전혀 없었던 셈입니다.

### 기존 설정의 문제

```js
// 기존 .eslintrc.js — TypeScript 코드를 JS처럼 분석하고 있었음
module.exports = {
  rules: {
    "@next/next/no-img-element": "off",
    "import/no-unresolved": "error",
    "no-undef": "error",          // TypeScript에선 tsc가 처리해야 할 룰
  },
};
```

`no-undef`를 ESLint에서 잡고 있었는데, TypeScript 환경에서는 `tsc`가 이미 타입 체크를 담당합니다. ESLint에서 중복 처리하면 오탐(false positive)이 발생하고, 정작 TypeScript 전용 룰은 하나도 없는 상태였습니다.

### 개선: TypeScript ESLint 오버라이드 추가

```js
module.exports = {
  settings: {
    "import/resolver": {
      typescript: {
        alwaysTryTypes: true,
        project: "./tsconfig.json",
      },
    },
  },
  rules: {
    "@next/next/no-img-element": "off",
    "import/no-unresolved": "error",
    "no-undef": "error",
  },
  overrides: [
    {
      files: ["**/*.ts", "**/*.tsx"],
      parser: "@typescript-eslint/parser",
      parserOptions: {
        project: "./tsconfig.json",
      },
      plugins: ["@typescript-eslint"],
      extends: ["plugin:@typescript-eslint/recommended"],
      rules: {
        "@typescript-eslint/no-explicit-any": "warn",
        "@typescript-eslint/no-unused-vars": "warn",
        "no-undef": "off",       // TypeScript 파일에선 tsc에 위임
      },
    },
  ],
};
```

핵심은 `overrides`로 `.ts` / `.tsx` 파일에만 TypeScript 파서와 룰을 적용한 것입니다. 기존 JS 파일에 영향을 주지 않으면서 TypeScript 코드의 품질 기준을 올릴 수 있습니다.

`import/resolver`에 typescript 설정을 추가해 path alias(`@modules/`, `@components/` 등)를 ESLint가 올바르게 해석하도록 했습니다.

## 2단계: 정적 분석이 잡아낸 것들

설정을 추가하자마자 기존 코드에서 경고가 나왔습니다. 가장 대표적인 패턴이 `let` 오용입니다.

```tsx
// 수정 전 — 재할당이 없는데 let 사용
let timeout = status === "preDelaying" && setTimeout(() => setStatus("doing"), preDelay);
let interval = setInterval(() => { ... });
```

```tsx
// 수정 후 — const로 의도 명확화
const timeout = status === "preDelaying" && setTimeout(() => setStatus("doing"), preDelay);
const interval = setInterval(() => { ... });
```

`let`과 `const`의 차이는 단순한 스타일 문제가 아닙니다. `const`는 "이 값은 재할당하지 않는다"는 의도를 코드에 새기는 것입니다. 정적 분석이 이런 작은 신호들을 잡아주면, 코드 리뷰에서 더 중요한 로직 검토에 집중할 수 있습니다.

## 3단계: 도구 체인 정비

### check 스크립트 추가

```json
{
  "scripts": {
    "check": "tsc --noEmit && npm run lint",
    "format": "prettier --write ."
  }
}
```

`tsc --noEmit`은 JS 출력 없이 타입 체크만 실행합니다. `check` 한 번으로 타입 오류와 lint 오류를 모두 확인할 수 있게 됐습니다. CI 파이프라인에 붙이거나, PR 전 로컬에서 빠르게 검증하는 용도로 씁니다.

### Prettier 업그레이드

```json
// 기존
"prettier": "^2.8.8",
"prettier-plugin-tailwindcss": "^0.2.7"

// 업그레이드
"prettier": "^3.8.3",
"prettier-plugin-tailwindcss": "^0.6.14"
```

Prettier 3.x는 기본 파서가 변경되어 일부 포맷팅 결과가 달라집니다. 팀 전체가 동일한 버전을 쓰지 않으면 불필요한 diff가 계속 발생합니다. 버전을 고정해 두는 것 자체가 하네스입니다.

## 4단계: 지식 하네스 — 문서 3종

정적 분석은 나쁜 코드를 막지만, **왜 그렇게 써야 하는지**를 알려주지는 않습니다. 신규 팀원이 합류하거나 반복적인 리뷰 코멘트가 쌓일 때 문서 하네스가 그 역할을 합니다.

### CONVENTIONS.md — 금지 패턴 명시

가장 중요한 부분은 "하지 말아야 할 것"을 명확히 적는 것입니다.

```
❌  fetch() 직접 사용
❌  axios를 컴포넌트에서 직접 호출
❌  store/ 바깥에서 Jotai atom 선언
❌  .tsx 파일에 any 타입 사용
❌  인라인 style 속성 사용
❌  색상값 하드코딩
❌  console.log 커밋에 포함
```

"컴포넌트에서 API를 직접 호출하지 말라"는 말은 온보딩 때 한 번 듣고 잊혀집니다. 문서에 남겨두면 리뷰어가 매번 같은 설명을 반복할 필요가 없습니다.

### COMPONENT_GUIDE.md — 중복 구현 방지

Alert, Confirm, Toast, Popup이 이미 있는데 신규 개발자가 또 비슷한 모달을 만드는 일이 반복됩니다. 공통 컴포넌트 목록과 선택 기준을 문서화했습니다.

```
간단한 1버튼 알림              →  Alert
확인/취소 2버튼                →  Confirm
버튼 색상 커스터마이징 필요     →  Prompt
3초 후 사라지는 알림           →  Toast
위 케이스에 맞지 않는 모달     →  Popup
```

### DESIGN-SYSTEM.md — 디자인 토큰 기준

피그마에서 `Primary500`, `H4_24_145_Bold` 같은 토큰으로 넘어오는데, 이걸 어디서 찾아야 하는지 몰라서 색상값을 하드코딩하는 경우가 있었습니다. 토큰 표와 사용 예시를 함께 정리했습니다.

```jsx
// 하드코딩 — 디자인 시스템과 즉시 단절됨
<button style={{ color: '#7B3CFF' }}>

// 토큰 사용 — 디자인 변경 시 한 곳에서 제어 가능
<button className="text-Primary500">
```

## 하네스 구축 순서 정리

레거시 프로젝트에 하네스를 도입할 때 순서가 중요합니다. 한 번에 너무 많이 바꾸면 팀의 저항이 생깁니다.

```
1. 도구 하네스 먼저    — ESLint, Prettier (자동으로 잡아주는 것)
2. 문서 하네스 다음    — 컨벤션, 컴포넌트 가이드 (왜를 설명하는 것)
3. 점진적 적용         — warn으로 시작해 error로 단계적 상향
4. CI 연결             — check 스크립트를 PR 게이트에 추가
```

`warn`으로 시작하는 것이 핵심입니다. 기존 코드를 전부 수정하기 전에 `error`로 설정하면 빌드가 깨지고 팀 전체가 멈춥니다. 새 코드에는 엄격하게, 기존 코드는 점진적으로 개선하는 것이 현실적입니다.

---

## 정리

하네스 엔지니어링은 거창한 인프라 작업이 아닙니다. ESLint 규칙 하나, 문서 파일 하나가 쌓여서 **"이 프로젝트에는 기준이 있다"**는 신호를 만듭니다.

코드는 혼자 쓰는 것이 아닙니다. 팀이 같은 방향을 바라보게 만드는 도구와 문서가 곧 하네스입니다.
