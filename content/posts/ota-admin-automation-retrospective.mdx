## 무엇을 만들었나

OTA(온라인 여행사) 사이드 프로젝트에서 어드민 쇼케이스 콘텐츠 자동화 시스템을 구현했습니다.

서비스 메인 페이지에 노출되는 "도시별 추천 호텔" 쇼케이스 콘텐츠는 기존에 수동으로 관리했습니다. 운영자가 직접 타이틀을 쓰고, 이미지를 업로드하고, 호텔을 선택하는 작업이 주기적으로 반복됐습니다.

이 흐름을 자동화하면서 두 가지를 동시에 해결하고 싶었습니다.

- **Cron 자동화** — 매주 AI가 콘텐츠를 생성해 DB에 저장, 배포 없이 메인에 반영
- **어드민 위저드** — 운영자가 원할 때 도시·기간·프롬프트를 입력하고, AI 생성 결과를 검수·수정·저장하는 UI

---

## 기술 결정의 흐름

### n8n으로 시작했다가 Inngest로 전환

자동화 도구를 처음 선택할 때 n8n을 먼저 검토했습니다. GUI로 워크플로우를 빠르게 설계할 수 있고, Cron + API 연결도 간단합니다. [n8n 포스팅](/posts/n8n-frontend-automation/)에서 개념을 정리하면서 실제로 워크플로우 흐름을 먼저 그려봤습니다.

그런데 실제 구현 단계에서 세 가지 문제가 생겼습니다.

**첫째, 별도 서버 운영.** 프로젝트는 Vercel에 배포 중이었는데, n8n만을 위해 별도 서버를 띄우는 건 오버헤드였습니다.

**둘째, 타입 공유 불가.** 프로젝트 내부에 이미 `showcaseAiService.ts`, `autoConfigApi.ts` 같은 서비스 코드가 잘 정리되어 있었습니다. n8n은 이 코드를 직접 쓸 수 없어서 HTTP 엔드포인트로 다시 감싸야 했습니다. 같은 로직을 두 곳에서 관리하게 되는 구조였습니다.

**셋째, 동적 병렬 처리.** 생성할 도시 목록은 어드민이 런타임에 설정합니다. 도시 수가 고정되지 않은 동적 fan-out을 n8n GUI로 표현하기 어려웠습니다.

[Inngest로 전환](/posts/inngest-admin-automation/)하면서 세 문제가 모두 해결됐습니다. `src/app/api/inngest/route.ts` 하나로 Vercel 안에서 실행되고, 기존 서비스 코드를 그대로 import하고, `cities.map((city) => step.run(...))` 으로 동적 병렬 처리를 자연스럽게 표현할 수 있었습니다.

### 위저드 UI에 XState를 선택한 이유

어드민 생성 위저드는 7단계 플로우입니다. 도시 입력 → 기간 설정 → 프롬프트 → AI 타이틀 생성 → AI 이미지 생성 → 호텔 선택 → 저장.

각 단계에서 이전으로 돌아갈 수 있고, AI 생성 단계는 비동기이며, 실패 시 해당 단계만 재시도해야 합니다. 이미지는 재생성 또는 직접 업로드 중 선택 가능합니다.

`useState` 여러 개로 시작했을 때 문제가 금방 드러났습니다. `step`, `isLoading`, `error`를 따로 관리하면 "로딩 중인데 step이 4인 상태"처럼 불가능해야 할 조합이 코드상으로는 가능해집니다.

[XState v5](/posts/xstate-v5-wizard-ui/)는 이걸 근본적으로 해결했습니다. `generatingTitle`이라는 상태 하나가 "타이틀 생성 중"을 완전히 표현합니다. 그 상태에서는 CONFIRM 버튼이 눌릴 수 없고, 에러가 나면 `error` 상태로 전이하며 `failedState`에 어느 단계에서 실패했는지를 기록합니다. RETRY 이벤트가 오면 실패한 단계로 정확히 돌아갑니다.

### AI 파이프라인: Gemini + FLUX

AI 생성 파이프라인은 역할을 분리했습니다.

- **Gemini 2.5 Flash** — 쇼케이스 타이틀 생성 (20자 이내, 감성적 명사형), FLUX용 영문 프롬프트 변환, 호텔 목록 JSON 생성
- **HuggingFace FLUX 모델** — 도시 이미지 생성
- **Supabase Storage** — 생성된 이미지 업로드 및 URL 반환

이미지 생성에서 한 가지 개선이 있었습니다. 처음엔 도시명을 그대로 FLUX에 넘겼는데, 결과 품질이 일정하지 않았습니다. Gemini가 먼저 도시의 실제 랜드마크 정보를 담아 FLUX에 최적화된 영문 프롬프트를 만들어주는 단계를 추가했습니다.

```ts
// 개선 전
const blob = await generateImageWithFlux(`${cityName} hotel scenery`);

// 개선 후: Gemini가 FLUX 프롬프트를 먼저 생성
const fluxPrompt = await buildFluxPromptWithGemini(cityName, userPrompt);
const blob = await generateImageWithFlux(fluxPrompt);
```

"교토의 유명 랜드마크, 풍경 위주, 사람 없음, cinematic lighting, 8k"처럼 구체적인 프롬프트가 만들어지면서 이미지 품질이 안정됐습니다.

## 전체 구조 한눈에 보기

```
Cron (매주) 또는 어드민 수동 트리거
          ↓
  Inngest autoCheckShowcase
          ↓ (조건 충족 시 이벤트 발송)
  Inngest autoGenerateShowcase
          ↓
  도시별 병렬 step.run()
  ┌────────────────────────────────┐
  │ Gemini → 타이틀                │
  │ Gemini → FLUX 프롬프트 변환    │
  │ FLUX → 이미지 생성             │
  │ Supabase Storage → 이미지 저장 │
  │ DB → showcase_content 저장    │
  └────────────────────────────────┘

어드민 위저드 (XState v5)
  도시 입력 → 기간 설정 → 프롬프트 →
  AI 타이틀 생성/편집 →
  AI 이미지 생성/재생성/직접업로드 →
  호텔 선택 → 저장
```

Cron 자동화와 어드민 수동 생성이 **같은 Inngest 이벤트로 합류**합니다. 수동 테스트와 자동화 결과가 동일한 파이프라인을 통과한다는 보장이 됩니다.

## 돌아보며 아쉬운 점

**서비스 주입 패턴을 처음부터 했더라면.** XState 상태 머신에 `showcaseService`를 컨텍스트로 주입받는 구조는 좋았는데, 처음엔 서비스를 직접 import했습니다. 테스트를 작성하면서 뒤늦게 리팩토링했습니다. 처음 설계할 때부터 의존성 주입을 염두에 뒀으면 더 자연스러웠을 것 같습니다.

**Gemini 응답 파싱 방어 코드.** 호텔 목록을 JSON으로 받는 부분에서 Gemini가 마크다운 코드블록으로 감싸서 반환하는 경우가 있었습니다. ` ```json ` 을 제거하는 파싱 처리를 추가했는데, 프롬프트에서 "JSON만 출력하라"고 명시했음에도 불안정한 경우가 있었습니다. Zod로 파싱 결과를 검증하는 레이어를 추가하는 게 더 견고했을 것 같습니다.

**이미지 생성 시간.** FLUX 모델 이미지 생성이 도시당 10~20초 정도 걸립니다. Inngest `step.run()` 덕분에 타임아웃 문제는 없었지만, 어드민 위저드에서 기다리는 시간이 길게 느껴집니다. 이미지를 백그라운드에서 먼저 생성해두거나, 생성 완료 후 알림을 주는 방식도 고려해볼 만합니다.

## 이 작업에서 얻은 것

기술적인 결과물보다 더 기억에 남는 건 **"도구를 고를 때 현재 인프라와의 통합 비용"을 먼저 따지게 됐다**는 점입니다.

n8n은 좋은 도구입니다. 하지만 이 프로젝트에서는 기존 코드베이스와 분리된다는 점이 결정적인 단점이었습니다. 반대로 Inngest는 기능이 많아서가 아니라 "지금 있는 것들과 자연스럽게 붙는다"는 이유로 선택했습니다.

XState도 마찬가지입니다. 처음엔 배움 곡선이 있었지만, 7단계 비동기 위저드를 `useState`로 관리하는 것보다 상태 머신으로 모델링하는 쪽이 결과적으로 더 빠르고 버그도 적었습니다.
