## 약한 참조가 존재하는 이유

DOM 노드마다 메타데이터를 붙이고 싶다고 해봅시다. 가장 먼저 떠오르는 건 `Map`입니다.

```javascript
const meta = new Map();

function track(el) {
  meta.set(el, { clickedAt: Date.now() });
}
```

노드가 DOM에서 제거되어도 `meta`가 키로 노드를 붙잡고 있습니다. **Map은 키와 값을 강한 참조(strong reference)로 들고 있기 때문**입니다. 가비지 컬렉터는 "어디서도 닿을 수 없는 객체"만 수거하는데, 이 경우 `meta`를 통해 여전히 닿을 수 있습니다. 코드에는 버그가 없는데 메모리는 계속 늘어납니다.

> "내가 이 객체의 수명을 결정하지 않는다. 다른 누군가가 쓰는 동안만 붙어 있으면 된다."

이 의도를 표현하려고 만든 것이 약한 참조입니다. 객체의 생존 여부를 **결정하지 않는** 참조입니다.

## 내부 동작 방식

### 도달 가능성(reachability)

GC는 루트(전역, 실행 중인 스택, 클로저)에서 출발해 참조를 따라가며 표시(mark)합니다. 표시되지 않은 객체가 수거 대상입니다. 약한 참조는 이 탐색에서 **간선으로 취급되지 않습니다.**

```
[root] ──강한──▶ [el] ◀──약한── [WeakMap entry]
                  │
        root가 el을 놓으면 el은 미도달 → 수거
        entry도 함께 사라짐
```

### WeakMap은 키만 약하다

WeakMap의 키는 약하게, 값은 **키가 살아있는 동안 강하게** 유지됩니다. 엔진 구현은 보통 에페머론(ephemeron) 테이블입니다. "키가 도달 가능할 때에만 값을 도달 가능으로 본다"는 규칙입니다. 그래서 값이 키를 다시 참조하는 순환 구조여도 누수가 생기지 않습니다. 단순히 "값을 약하게 잡는 맵"이 아닙니다.

### 왜 순회가 안 되는가

`WeakMap`에는 `size`, `keys()`, `forEach`가 없습니다. 이건 편의 부족이 아니라 **설계상 불가능하게 만든 것**입니다. 순회가 가능하면 GC 시점에 따라 결과가 달라지고, 프로그램 동작이 엔진의 GC 타이밍에 의존하게 됩니다. 비결정성을 언어 표면에 드러내지 않기 위한 선택입니다.

### WeakRef와 FinalizationRegistry

`WeakRef`는 객체 하나에 대한 약한 참조를 직접 만듭니다.

```javascript
let target = { big: new Array(1e6) };
const ref = new WeakRef(target);

target = null;
// 이후 어느 시점에 GC가 돌면
ref.deref(); // 객체 또는 undefined
```

`deref()`가 객체를 돌려주면 그 시점부터 현재 이벤트 루프 턴이 끝날 때까지는 객체가 살아있음이 보장됩니다. 턴을 넘기면 보장이 사라집니다. `FinalizationRegistry`는 객체가 수거된 뒤 콜백을 받지만, 호출 시점도 **호출 여부 자체도 보장되지 않습니다.**

## 실제로 언제 쓰는가

**WeakMap / WeakSet이 적합한 경우:**
- 외부 객체(DOM 노드, 라이브러리 인스턴스)에 부가 데이터 붙이기
- 객체 단위 캐시. 객체가 사라지면 캐시도 사라져야 할 때
- 방문 표시. 그래프 순회에서 "이미 본 객체" 집합

```typescript
// src/shared/memo.ts
const cache = new WeakMap<object, number>();

export function heavy(obj: object): number {
  if (cache.has(obj)) return cache.get(obj)!;
  const result = compute(obj);
  cache.set(obj, result);
  return result;
}
```

**WeakRef가 적합한 경우:**
- 다시 만들 수 있는 큰 객체의 선택적 캐시
- 옵저버/리스너 레지스트리에서 구독자의 수명을 구독 대상이 좌우하지 않게 할 때

**쓰지 않아도 되는 경우:**
- 키가 문자열, 숫자 같은 원시값. WeakMap 키는 객체(최근에는 등록되지 않은 심볼 포함)만 가능
- 캐시 크기를 직접 제어할 수 있을 때. LRU가 더 예측 가능합니다
- 프로그램 정합성이 수거 여부에 달려 있을 때

## 흔한 오해와 함정

### 1. WeakRef를 일반 캐시처럼 쓰기

```javascript
// 수정 전: GC 타이밍에 따라 캐시가 마음대로 비워짐
function get(key) {
  return refs.get(key)?.deref() ?? load(key);
}
```

히트율이 엔진과 메모리 상황에 따라 달라집니다. 테스트에서는 항상 살아있고 운영에서만 사라지는 식의 재현 어려운 문제가 됩니다. 필요하면 일반 캐시 + 명시적 만료 정책을 쓰는 편이 낫습니다.

### 2. 값이 키를 강하게 잡는다고 착각

`WeakMap<K, V>`의 **V에 대한 참조가 K 쪽으로 이어지지 않는 한** 문제없습니다. 하지만 V가 WeakMap 밖의 전역에서도 참조되고 있다면 그건 V의 수명이지 WeakMap의 효과가 아닙니다.

### 3. 클로저가 키를 붙잡고 있는 경우

```javascript
// 수정 전
cache.set(el, () => console.log(el.id)); // 값(클로저)이 el을 캡처
```

에페머론 덕분에 이 경우도 수거되지만, 같은 클로저를 **다른 강한 경로**(이벤트 리스너 등)에 등록하면 `el`은 계속 살아있습니다. 누수 원인은 WeakMap이 아니라 그 다른 경로입니다.

### 4. FinalizationRegistry로 리소스 정리하기

정리 로직을 여기에 의존하면 콜백이 영영 안 불릴 수 있습니다. 파일 핸들, 소켓 같은 리소스는 명시적 `close()`가 기본이고, 레지스트리는 안전망일 뿐입니다.

## 정리

약한 참조의 핵심은 **"수명은 내가 정하지 않는다"** 입니다. 그래서 순회가 막혀 있고, 수거 시점을 알 수 없는 것도 의도된 제약입니다.

외부 객체에 데이터를 붙이거나 객체 단위 캐시가 필요하면 먼저 `WeakMap`을 고려하고, `WeakRef`와 `FinalizationRegistry`는 정합성에 영향이 없는 최적화에만 쓰세요.
