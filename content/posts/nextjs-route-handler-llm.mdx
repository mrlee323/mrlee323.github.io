## 선택지가 세 개 있었다

숙소 리뷰 AI 요약 기능을 붙이면서 어디에 LLM 호출 로직을 두느냐를 결정해야 했다. App Router 기준으로 선택지는 셋이다.

- **Route Handler** (`app/api/*/route.ts`) — HTTP 엔드포인트. 기존 REST API와 동일한 방식.
- **Server Action** — 폼 액션 또는 `"use server"` 함수 직접 호출.
- **Edge Runtime** — Vercel Edge Network에서 실행. 더 짧은 cold start, 더 강한 제약.

처음엔 Server Action이 더 자연스러워 보였다. 별도 API 파일 없이 컴포넌트와 서버 로직을 같은 컨텍스트에서 다룰 수 있고, `fetch`를 직접 쓸 필요도 없다. 그런데 LLM 호출을 Server Action에 맡기면 몇 가지 문제가 생긴다.

Server Action은 Next.js 내부 RPC로 동작한다. 클라이언트에서 호출할 때 별도의 HTTP 요청 설정 없이 쓸 수 있는 건 편하지만, **timeout 핸들링과 스트리밍이 까다롭다**. LLM 응답은 빠르면 3초, 느리면 15-20초도 걸린다. 그 사이에 Vercel serverless function의 기본 timeout(10초, Pro 플랜 300초)에 걸릴 수 있고, Server Action에서 스트리밍 응답을 구현하려면 `experimental_useFormState`나 별도 인프라가 필요해진다.

Route Handler는 그냥 HTTP다. 스트리밍이 필요해지면 `ReadableStream`을 그대로 반환하면 된다. 인터페이스가 명확하다.

## Edge Runtime을 안 쓴 이유

Edge Runtime이 매력적인 이유는 cold start다. Vercel 기준 serverless function의 cold start는 수백 ms 수준인데, Edge는 수십 ms 수준이다. LLM 호출 전에 발생하는 지연을 줄일 수 있다.

문제는 Edge Runtime의 제약이 LLM 호출과 충돌한다.

Edge Runtime은 Node.js API를 전부 지원하지 않는다. `fs`, `crypto` 일부, `node-fetch` 대신 Web Fetch API를 써야 한다. OpenAI SDK가 Edge에서 동작하긴 하지만, 의존성이 Edge-compatible인지 확인하는 비용이 있다. 더 큰 문제는 **실행 시간 제한**이다. Vercel Edge Function은 최대 30초다. OpenAI API가 느릴 때, 특히 gpt-4o 계열에서 긴 응답을 받으면 이 제한에 걸린다.

cold start 몇백 ms를 아끼려다가 LLM 응답 자체가 timeout에 걸리는 상황을 만드는 건 trade-off가 맞지 않는다. Node.js runtime Route Handler를 쓰는 게 맞다.

## 실제 구현에서 설계 결정들

```ts
// app/api/ai/review-summary/route.ts
export async function POST(req: NextRequest) {
  const body: ReviewSummaryRequest = await req.json();

  // 입력 제한 — 토큰 비용의 직접적인 제어
  if (body.reviews.length > 50) {
    return NextResponse.json({ error: "최대 50개" }, { status: 422 });
  }

  const summary = await generateReviewSummary(body);
  return NextResponse.json(summary);
}
```

여기서 `reviews.length > 50` 제한이 단순해 보이지만, 이게 실질적인 비용 방어선이다. 리뷰 50개를 평균 200자로 잡으면 약 5,000자, 토큰으로 2,500 정도다. 제한이 없으면 하나의 요청이 예상의 10배가 될 수 있다.

```ts
async function generateReviewSummary(data: ReviewSummaryRequest) {
  const response = await fetch("https://api.openai.com/v1/chat/completions", {
    method: "POST",
    headers: { Authorization: `Bearer ${process.env.OPENAI_API_KEY}` },
    body: JSON.stringify({
      model: "gpt-4o-mini",
      messages: buildMessages(data.reviews),
      response_format: { type: "json_object" },
    }),
    // signal: AbortSignal.timeout(25_000) — 나중에 추가한 부분
  });

  if (!response.ok) {
    // 에러 본문을 서버 로그에만 남기고 클라이언트엔 최소한만
    const detail = await response.text();
    console.error("[review-summary] OpenAI error", response.status, detail);
    throw new Error(`upstream_error:${response.status}`);
  }

  const data = await response.json();
  return parseResponse(data.choices[0].message.content);
}
```

`AbortSignal.timeout(25_000)` 줄이 처음엔 없었다. Vercel Pro 기준 serverless function timeout은 300초인데, LLM API 쪽에서 hang이 걸리면 그 300초를 전부 소모한다. 동시에 여러 요청이 이 상태가 되면 function instance가 모자라게 된다. 25초로 hard cut하고 클라이언트에 명시적인 timeout 에러를 내려주는 게 낫다는 걸 운영에서 배웠다.

## streaming을 나중에 붙이려고 미리 결정한 것들

지금 구현은 non-streaming이다. LLM이 전체 응답을 완성하면 JSON으로 파싱해서 한 번에 반환한다. 리뷰 요약처럼 구조화된 JSON을 반환해야 할 때는 이게 더 단순하다.

그런데 streaming을 나중에 붙여야 할 상황이 명확히 예상됐다. 요약 텍스트가 길어질수록 사용자가 빈 화면을 보는 시간이 늘어나고, UX 팀에서 "로딩 중 텍스트가 타이핑되는 것처럼 보이면 어때요"가 나오는 건 시간 문제다.

그래서 처음부터 Route Handler의 반환 형태를 바꾸기 쉽게 격리해뒀다. 컴포넌트는 `/api/ai/review-summary`를 `fetch`로 호출하고 응답을 파싱할 뿐이다. 나중에 서버 쪽에서 `ReadableStream`으로 바꾸고 클라이언트에서 `response.body`를 읽도록 수정하면 된다. 이 분리가 Server Action을 선택하지 않은 결정적인 이유 중 하나다.

streaming 전환 시 Route Handler 쪽 변경점만 보면:

```ts
// streaming 버전으로 전환할 때의 골격
export async function POST(req: NextRequest) {
  const encoder = new TextEncoder();
  const stream = new ReadableStream({
    async start(controller) {
      const openaiStream = await fetchOpenAIStream(body);
      for await (const chunk of openaiStream) {
        controller.enqueue(encoder.encode(chunk));
      }
      controller.close();
    },
  });
  return new Response(stream, {
    headers: { "Content-Type": "text/event-stream" },
  });
}
```

컴포넌트 쪽이 `fetch` + `response.json()`에서 `response.body` reader로 바뀌는 것 외에 구조 변경은 없다.

## 지금 돌아보면 바꾸고 싶은 것들

**캐싱을 Route Handler 안에 뒀다.** 같은 `propertyId`에 대한 요청이 들어오면 Redis에서 캐시 히트를 확인하는 로직이 Route Handler 안에 있다. 이게 단기적으로 빠른 방법이었는데, 지금은 LLM 호출 로직과 캐싱 로직이 한 파일에 섞여 있다. 캐싱 레이어를 미들웨어로 빼거나 별도 service 계층으로 분리했으면 테스트가 훨씬 쉬웠을 것이다.

**에러 타입이 문자열이다.** `throw new Error("upstream_error:429")`처럼 에러 코드를 문자열로 인코딩해서 catch 쪽에서 파싱한다. 이 패턴을 다른 AI 엔드포인트에도 복붙하다 보니 에러 처리 방식이 일관되지 않게 됐다. 처음부터 typed error class를 쓰거나, Result 타입을 쓰거나 했어야 했다.

**`response_format: json_object`에 과도하게 의존했다.** GPT-4o-mini는 이 옵션을 쓰면 유효한 JSON을 반환한다. 그런데 JSON 스키마 자체의 정합성까지 보장해주진 않는다. `highlights`가 배열이 아닌 문자열로 오거나, 필드가 빠지거나 하는 경우가 드물게 있었다. zod로 파싱하고 실패 시 재시도나 폴백을 두는 게 맞다.

## 결론보다 기준

Route Handler를 선택한 핵심 이유는 세 가지다. 스트리밍 전환이 가능한 구조, timeout 제어의 명확함, Edge Runtime의 실행시간 제약 회피. 보안은 이미 전제이기 때문에 선택 기준에 들어가지 않는다.

LLM 호출은 일반 API 호출과 다르다. 응답 시간 분포가 넓고, timeout이 UX와 직결되고, 비용이 입력에 비례한다. 이 특수성을 기준으로 서버 계층을 설계하면 나머지는 자연스럽게 따라온다.
