## 처음엔 그냥 클라이언트에서 호출했다

AI 리뷰 요약 기능을 처음 붙였을 때, 가장 빠른 방법을 선택했습니다. 컴포넌트 안에서 직접 OpenAI API를 호출하는 것이었습니다.

```ts
// 이렇게 하면 안 됩니다
const response = await fetch("https://api.openai.com/v1/chat/completions", {
  method: "POST",
  headers: {
    Authorization: `Bearer ${process.env.NEXT_PUBLIC_OPENAI_API_KEY}`,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({ model: "gpt-4o-mini", messages }),
});
```

코드 자체는 동작했습니다. 문제는 그 다음에 나왔습니다.

첫 번째로, `NEXT_PUBLIC_` 접두사를 붙인 순간 API 키가 번들에 포함됩니다. 브라우저 DevTools → Network 탭을 열면 Authorization 헤더에 키가 그대로 보입니다. 누구든 키를 가져가 자기 목적으로 사용할 수 있습니다.

두 번째로, 비용 제어가 불가능해집니다. 요청이 클라이언트에서 직접 나가기 때문에 서버에서 중간에 끊을 방법이 없습니다. 유저가 버튼을 연속으로 누르거나, 악의적인 스크립트가 루프를 돌면 청구서가 기하급수적으로 불어납니다.

세 번째는 rate limit입니다. OpenAI는 분당 요청 수(RPM)와 토큰 수(TPM)를 제한합니다. 클라이언트에서 직접 호출하면 여러 유저가 동시에 요청을 보낼 때 제어할 수단이 없습니다. 429 에러가 사용자에게 그대로 노출됩니다.

---

## 왜 서버 계층이 필요한가

클라이언트와 LLM API 사이에 서버를 끼워 넣으면 문제가 세 가지 방향에서 해결됩니다.

**보안**: API 키는 서버 환경 변수(`process.env.OPENAI_API_KEY`)에만 존재합니다. 클라이언트는 내부 엔드포인트(`/api/ai/review-summary`)만 알고 있습니다. 브라우저에서 번들을 아무리 뜯어봐도 키가 없습니다.

**비용 제어**: 서버에서 요청을 받는 시점에 인증 확인, 요청 빈도 제한, 입력 길이 제한을 적용할 수 있습니다. 같은 숙소 리뷰 요약을 1분 안에 두 번 요청하면 첫 번째 결과를 캐시에서 돌려줄 수도 있습니다. LLM 호출 횟수가 직접적으로 비용이기 때문에 이 부분이 중요합니다.

**로깅과 관찰 가능성**: 어떤 유저가 어떤 숙소의 리뷰 요약을 요청했는지, 응답 시간은 얼마였는지, 어떤 에러가 났는지를 서버 로그로 남길 수 있습니다. 클라이언트에서 직접 호출하면 이런 정보를 모을 방법이 없습니다.

## Route Handler 구현

Next.js App Router의 Route Handler는 서버에서 실행되는 API 엔드포인트입니다. `app/api` 아래에 `route.ts` 파일을 만들면 됩니다.

```ts
// app/api/ai/review-summary/route.ts
import { NextRequest, NextResponse } from "next/server";

interface ReviewSummaryRequest {
  propertyId: string;
  reviews: string[];
}

interface ReviewSummaryResponse {
  summary: string;
  highlights: string[];
}

export async function POST(req: NextRequest) {
  try {
    const body: ReviewSummaryRequest = await req.json();
    const { propertyId, reviews } = body;

    if (!propertyId || !reviews?.length) {
      return NextResponse.json(
        { error: "propertyId와 reviews는 필수입니다." },
        { status: 400 }
      );
    }

    // 요청당 리뷰 수 제한 — 비용 제어
    if (reviews.length > 50) {
      return NextResponse.json(
        { error: "한 번에 최대 50개의 리뷰만 처리할 수 있습니다." },
        { status: 422 }
      );
    }

    const summary = await generateReviewSummary(propertyId, reviews);

    return NextResponse.json(summary);
  } catch (error) {
    console.error("[review-summary] 오류:", error);
    return NextResponse.json(
      { error: "리뷰 요약 생성에 실패했습니다." },
      { status: 500 }
    );
  }
}

async function generateReviewSummary(
  propertyId: string,
  reviews: string[]
): Promise<ReviewSummaryResponse> {
  // API 키는 서버 환경 변수에서만 읽습니다
  const apiKey = process.env.OPENAI_API_KEY;
  if (!apiKey) throw new Error("OPENAI_API_KEY가 설정되지 않았습니다.");

  const prompt = buildPrompt(reviews);

  const response = await fetch("https://api.openai.com/v1/chat/completions", {
    method: "POST",
    headers: {
      Authorization: `Bearer ${apiKey}`,
      "Content-Type": "application/json",
    },
    body: JSON.stringify({
      model: "gpt-4o-mini",
      messages: [
        {
          role: "system",
          content:
            "당신은 숙소 리뷰를 분석해 간결한 요약과 핵심 장점을 추출하는 전문가입니다.",
        },
        { role: "user", content: prompt },
      ],
      response_format: { type: "json_object" },
    }),
  });

  if (!response.ok) {
    const errorBody = await response.text();
    throw new Error(`OpenAI API 오류 (${response.status}): ${errorBody}`);
  }

  const data = await response.json();
  const parsed = JSON.parse(data.choices[0].message.content);

  return {
    summary: parsed.summary,
    highlights: parsed.highlights ?? [],
  };
}

function buildPrompt(reviews: string[]): string {
  const reviewText = reviews
    .slice(0, 50)
    .map((r, i) => `${i + 1}. ${r}`)
    .join("\n");

  return `다음 숙소 리뷰들을 분석해 JSON 형식으로 응답해주세요.

리뷰:
${reviewText}

응답 형식:
{
  "summary": "전체 리뷰를 2-3문장으로 요약",
  "highlights": ["핵심 장점 1", "핵심 장점 2", "핵심 장점 3"]
}`;
}
```

몇 가지 설계 결정을 짚어두겠습니다.

`reviews.length > 50` 제한은 단순해 보이지만 중요합니다. LLM 비용은 토큰 수에 비례하는데, 입력이 무제한이면 하나의 요청이 예상보다 수십 배 비쌀 수 있습니다. 서버에서 입력을 제한하는 것이 가장 확실한 방어선입니다.

`response_format: { type: "json_object" }`는 GPT-4o 계열에서 JSON만 반환하도록 강제합니다. 파싱 실패 가능성을 줄입니다.

에러 로그는 서버에서만 남깁니다(`console.error`). 클라이언트에는 최소한의 메시지만 내려보냅니다. 내부 에러 메시지가 클라이언트에 그대로 노출되면 API 구조나 의존성 정보가 유출될 수 있습니다.

## 프론트에서 호출하는 패턴

클라이언트는 외부 LLM API가 아니라 내부 Route Handler만 알고 있습니다.

```ts
// hooks/useReviewSummary.ts
import { useState } from "react";

interface ReviewSummaryResult {
  summary: string;
  highlights: string[];
}

export function useReviewSummary() {
  const [data, setData] = useState<ReviewSummaryResult | null>(null);
  const [isLoading, setIsLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);

  const summarize = async (propertyId: string, reviews: string[]) => {
    setIsLoading(true);
    setError(null);

    try {
      const response = await fetch("/api/ai/review-summary", {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({ propertyId, reviews }),
      });

      if (!response.ok) {
        const errorData = await response.json();
        throw new Error(errorData.error ?? "요청에 실패했습니다.");
      }

      const result: ReviewSummaryResult = await response.json();
      setData(result);
    } catch (err) {
      setError(err instanceof Error ? err.message : "알 수 없는 오류");
    } finally {
      setIsLoading(false);
    }
  };

  return { data, isLoading, error, summarize };
}
```

```tsx
// components/PropertyReviewSummary.tsx
import { useReviewSummary } from "@/hooks/useReviewSummary";

interface Props {
  propertyId: string;
  reviews: string[];
}

export function PropertyReviewSummary({ propertyId, reviews }: Props) {
  const { data, isLoading, error, summarize } = useReviewSummary();

  return (
    <div>
      <button
        onClick={() => summarize(propertyId, reviews)}
        disabled={isLoading}
      >
        {isLoading ? "요약 중..." : "AI 리뷰 요약 보기"}
      </button>

      {error && <p className="text-red-500">{error}</p>}

      {data && (
        <div>
          <p>{data.summary}</p>
          <ul>
            {data.highlights.map((h, i) => (
              <li key={i}>{h}</li>
            ))}
          </ul>
        </div>
      )}
    </div>
  );
}
```

컴포넌트는 `/api/ai/review-summary`에 POST 요청을 보낼 뿐입니다. 어떤 LLM을 쓰는지, API 키가 무엇인지, 모델이 바뀌었는지를 알 필요가 없습니다. 서버 계층에서 LLM 제공자를 OpenAI에서 다른 것으로 바꿔도 클라이언트 코드는 그대로입니다.

## trade-off: 이 구조가 항상 옳은가

서버 계층을 추가하면 latency가 늘어납니다. 클라이언트 → Route Handler → LLM API → Route Handler → 클라이언트로 한 홉이 추가됩니다. Vercel 같은 엣지 환경에서는 큰 차이가 없지만, 서버와 LLM API가 다른 리전에 있으면 수십 ms가 추가될 수 있습니다.

또한 서버리스 환경에서는 Route Handler도 콜드 스타트 비용이 있습니다. 자주 호출되지 않는 엔드포인트라면 첫 요청이 느릴 수 있습니다.

그럼에도 불구하고, **API 키를 클라이언트에 노출하는 비용**은 이 latency보다 훨씬 큽니다. 키가 유출되면 비용 청구가 즉시 발생하고 회수가 어렵습니다.

공개 API처럼 인증 없이 누구나 쓰는 서비스라면, 서버 계층에서 IP별 rate limit이나 요청 대기열을 관리하는 것이 더욱 중요해집니다.

---

## 정리

**LLM API 키를 `NEXT_PUBLIC_`으로 시작하는 환경 변수에 넣는 순간, 그 키는 공개된 것과 같습니다.**

Next.js Route Handler는 이 문제를 해결하는 가장 간단한 방법입니다. 서버에서만 API 키를 읽고, 클라이언트는 내부 엔드포인트만 호출합니다. 구조가 한 겹 늘어나지만, 그 한 겹이 보안·비용·관찰 가능성을 동시에 챙겨줍니다.

이 구조가 필요한 순간은 명확합니다. LLM, 결제, 외부 서드파티처럼 **키가 유출되면 즉시 피해가 발생하는 API를 프론트에서 쓰고 싶을 때**입니다. 그 순간이 Route Handler를 만들어야 할 타이밍입니다.
