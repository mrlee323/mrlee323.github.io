## useContext가 존재하는 이유

props drilling은 단순하지만 비용이 큽니다. 테마, 로그인 유저, 로케일처럼 앱 전반에서 쓰는 값을 10단계 아래 컴포넌트까지 내리려면 중간 컴포넌트 전부가 쓰지도 않는 props를 받아 넘겨야 합니다.

Context는 이 문제를 **"중간 컴포넌트를 건너뛰고 값을 주입한다"** 는 방식으로 풉니다. 여기서 중요한 점이 하나 있습니다.

> Context는 상태 관리 도구가 아니라 **의존성 주입 도구**다.

값이 어떻게 만들어지고 바뀌는지는 Context의 관심사가 아닙니다. `useState`나 `useReducer`가 만든 값을 아래로 전달할 뿐입니다. 이 구분을 놓치면 성능 함정에 거의 반드시 빠집니다.

## 내부 동작 방식

### 구독 단위는 "값 전체"다

`useContext(Ctx)`를 호출하면 React는 현재 렌더 중인 Fiber를 해당 Context의 소비자로 기록합니다. Provider의 `value`가 바뀌면, React는 `Object.is`로 이전 값과 비교하고 다르면 **그 Context를 구독한 모든 Fiber에 업데이트를 예약**합니다.

핵심은 비교 대상이 value 전체라는 겁니다. 객체 안의 어떤 필드를 읽는지는 추적하지 않습니다.

```tsx
const AppContext = createContext(null);

function Provider({ children }) {
  const [user, setUser] = useState(null);
  const [theme, setTheme] = useState("light");

  // 렌더마다 새 객체 → 항상 참조가 다름
  return (
    <AppContext.Provider value={{ user, theme, setUser, setTheme }}>
      {children}
    </AppContext.Provider>
  );
}
```

`theme`만 읽는 컴포넌트도 `user`가 바뀌면 리렌더링됩니다. 심지어 아무것도 안 바뀌어도 Provider의 부모가 리렌더링되면 value 객체가 새로 만들어져서 전부 리렌더링됩니다.

### memo로도 막을 수 없다

일반적인 리렌더링은 부모 → 자식으로 전파되므로 `React.memo`로 끊을 수 있습니다. 하지만 Context 변경은 **부모를 거치지 않고 소비자 Fiber에 직접 업데이트를 건다**는 점이 다릅니다. 중간에 `memo`가 있어도 소비자는 리렌더링됩니다.

```
Provider (value 변경)
   ↓ memo(Middle)  ← props 같음, 렌더 스킵
      ↓ Consumer   ← Context 구독 중이라 그래도 리렌더링
```

React는 `Middle`을 건너뛰면서도 하위에 context 변경 표시(lanes)를 전파해 소비자까지 도달하게 합니다. 이 동작은 정확성을 위한 설계이고, 소비자 단위 선택 구독은 지원하지 않습니다.

## 실제로 언제 쓰는가

Context가 잘 맞는 조건은 두 가지입니다.

**적합한 경우:**
- 값이 거의 안 바뀐다 (테마, 로케일, 인증 유저, 설정)
- 소비자가 적거나, 값이 바뀔 때 어차피 다 같이 바뀌어야 한다

**쓰지 않아도 되는 경우:**
- 입력값, 필터, 장바구니처럼 자주 바뀌는 상태를 넓은 트리에 공유할 때
- 소비자마다 전체 값 중 일부만 필요할 때

OTA 서비스에서 검색 조건(날짜, 인원, 목적지)을 Context 하나에 몰아넣었다가, 인원 스테퍼를 누를 때마다 결과 리스트 전체가 리렌더링되는 문제를 겪은 적이 있습니다. 값은 한 덩어리인데 소비자는 필드별로 다르게 쓰고 있었던 것이 원인이었습니다.

대응 방법은 다음과 같이 비용 순으로 고려합니다.

| 방법 | 효과 | 비용 |
|------|------|------|
| value 참조 안정화 (`useMemo`) | 불필요한 리렌더링 제거 | 낮음 |
| Context 분리 (state / dispatch, 도메인별) | 구독 범위 축소 | 중간 |
| children 패턴으로 Provider 위치 조정 | 리렌더링 전파 차단 | 낮음 |
| 외부 스토어 (Zustand, `useSyncExternalStore`) | selector 단위 구독 | 의존성 추가 |

## 흔한 오해와 함정

### 1. "Context 값이 안 바뀌면 리렌더링도 없다"

값의 의미가 같아도 **참조**가 다르면 변경으로 취급합니다.

```tsx
// 수정 전: 렌더마다 새 객체
<Ctx.Provider value={{ user, logout }}>

// 수정 후: 의존성이 바뀔 때만 새 객체
const value = useMemo(() => ({ user, logout }), [user, logout]);
<Ctx.Provider value={value}>
```

단, `logout` 같은 함수도 `useCallback`으로 안정화해야 `useMemo`가 의미를 가집니다.

### 2. "selector처럼 일부만 구독할 수 있다"

`const { theme } = useContext(AppContext)`는 destructuring일 뿐, 구독은 여전히 전체입니다. 일부만 구독하고 싶다면 Context를 쪼개거나 외부 스토어가 필요합니다.

```tsx
// 읽기와 쓰기를 분리: dispatch는 거의 안 바뀌므로 쓰기 전용 소비자는 리렌더링되지 않음
const StateContext = createContext(null);
const DispatchContext = createContext(null);
```

### 3. Provider를 앱 최상단에서 상태까지 들고 있게 하기

상태를 가진 Provider가 리렌더링되면 `children`은 같은 참조이므로 다시 렌더링되지 않습니다. 이 특성을 활용해 상태 보유 컴포넌트를 분리하면 전파를 막을 수 있습니다.

```tsx
// children 요소는 부모가 만든 참조라서, 이 컴포넌트의 state 변경에 리렌더링되지 않는다
function SearchProvider({ children }) {
  const [filter, setFilter] = useState(initial);
  const value = useMemo(() => ({ filter, setFilter }), [filter]);
  return <SearchCtx.Provider value={value}>{children}</SearchCtx.Provider>;
}
```

다만 이것은 Provider 자신의 리렌더링이 자식으로 퍼지는 것만 막을 뿐, value 변경으로 인한 소비자 리렌더링은 막지 못합니다. 두 가지 경로를 구분해서 봐야 합니다.

### 4. 기본값만 믿고 Provider를 빼먹기

`createContext(null)`로 만들고 Provider 밖에서 쓰면 조용히 `null`을 받습니다. 커스텀 훅에서 null을 검사해 명시적으로 에러를 던지는 편이 디버깅 비용이 훨씬 낮습니다.

```tsx
function useApp() {
  const ctx = useContext(AppContext);
  if (!ctx) throw new Error("AppProvider 안에서 사용해야 합니다");
  return ctx;
}
```

## 정리

Context의 핵심은 **"구독 단위가 Provider의 value 전체"** 라는 점입니다.

값이 드물게 바뀌는 전역 설정에는 Context가 가장 단순한 선택이고, 자주 바뀌거나 소비자가 필드를 나눠 쓰는 상태라면 Context 분리나 selector 구독이 되는 외부 스토어를 고려하세요. 리렌더링이 의심될 때는 먼저 Profiler로 "누가 왜 렌더링됐는지"를 확인하고, value 참조가 매번 새로 만들어지고 있지는 않은지부터 점검해 보시길 권합니다.
