## 개인 도구가 팀 도구가 되는 순간

Cursor를 처음 쓴 건 혼자였다. 빠르게 보일러플레이트를 생성하고, 모르는 API를 물어보고, 리팩토링 방향을 제안받는 용도. 확실히 빨라졌다.

팀이 다 같이 쓰기 시작하면서 달라졌다. 각자 다른 방식으로 쓰고, AI가 생성한 코드의 품질이 사람마다 달랐고, 리뷰에서 "이 코드 왜 이렇게 됐어요?"라는 질문이 늘었다. 도구가 팀으로 번지면 개인 효율이 팀 품질 문제로 전환된다.

---

## .cursorrules: 컨벤션을 AI에게 가르치는 방법

팀이 쓰는 AI 어시스턴트가 팀의 코드 스타일을 모르면 생성 코드가 제각각이 된다. Cursor는 프로젝트 루트의 `.cursorrules` 파일을 컨텍스트로 읽는다. 여기에 우리 팀 컨벤션을 써두면 AI 제안이 그 기준에 맞게 나온다.

```
# .cursorrules

## 기술 스택
- Next.js 15 App Router
- TypeScript strict mode
- Tailwind CSS (inline 스타일 금지)
- React Query v5 for server state
- Zustand for client state

## 컴포넌트 규칙
- 컴포넌트 파일: PascalCase (PropertyCard.tsx)
- 훅 파일: camelCase, use 접두사 (usePropertyData.ts)
- Server Component 기본, 클라이언트 필요 시만 'use client'

## 타입 규칙
- interface > type (확장 가능성)
- any 금지, unknown 허용
- API 응답 타입은 types/api/ 디렉토리에 분리

## 패턴
- 데이터 페칭은 Server Component 또는 React Query
- useEffect로 데이터 페칭 금지
- 에러 처리는 Error Boundary + React Query onError
```

`.cursorrules`를 git에 커밋한다. 팀원이 repo를 클론하면 동일한 AI 컨텍스트를 가진다. 컨벤션 문서가 살아있는 이유가 생긴다 — AI가 그걸 실제로 쓰기 때문에.

---

## AI가 짠 코드를 리뷰할 때

AI 생성 코드를 리뷰하는 게 사람이 짠 코드를 리뷰하는 것과 다른 점이 하나 있다. **작성자가 이 코드를 완전히 이해하지 못한 채로 PR을 올리는 경우**가 있다.

이건 의도적인 게 아니다. AI가 제안하고 테스트 통과시키고 올리는 흐름에서 "왜 이렇게 됐는지"를 건너뛰게 된다. 코드가 동작하는 것과 작성자가 그 코드를 이해하는 건 다르다.

리뷰에서 이걸 감지하는 신호들이 있다.

- 스타일이 PR 전체에서 일관되지 않다 (AI가 컨텍스트마다 다른 패턴을 제안했다)
- 같은 로직이 다른 방식으로 두 번 구현됐다
- 에러 처리가 패턴 없이 여기저기 다르게 되어 있다
- 질문하면 "AI가 이렇게 하길래요"라는 답이 나온다

이런 PR은 코드 수정 요청 전에 "이 부분 어떻게 동작하는지 설명해줄 수 있어요?"를 먼저 한다. 설명을 못하면 코드를 바꾸기 전에 이해부터 해야 한다는 피드백을 준다. AI 코드를 그대로 올리는 게 문제가 아니라, 이해 없이 올리는 게 문제다.

---

## 주니어가 AI에 과의존할 때

올해 팀에 합류한 2년차 개발자가 있다. Cursor를 처음부터 쓰면서 입사했는데, 3개월 지나서 문제가 보였다.

에러 메시지를 보면 바로 AI한테 물어본다. 스택 트레이스를 읽지 않는다. "AI가 이렇게 하라고 했는데 안 되는데요"가 자주 나온다.

문제는 AI 어시스턴트가 틀릴 때 본인이 검증을 못 한다는 것이다. 정답이 뭔지 모르면 AI 답이 틀렸는지도 모른다.

조치는 두 가지였다.

**첫째**, 에러 디버깅은 AI 없이 먼저 시도하는 것을 팀 컨벤션으로 만들었다. 스택 트레이스 읽기 → 재현 조건 파악 → 원인 가설 → 그 다음에 AI 참고. 순서가 중요하다.

**둘째**, AI가 제안한 코드를 쓰기 전에 "이게 왜 이런 방식인지" 설명하는 걸 요구한다. 설명 못하면 쓰지 않는다. 귀찮아 보이지만 이 과정이 실제로 이해를 만든다.

AI 어시스턴트가 주니어를 더 빠르게 성장시킬 수도 있고, 성장을 막을 수도 있다. 차이는 AI를 쓰는 순서와 방식에 있다.

---

## 보안: AI에 넘기면 안 되는 것들

Cursor를 포함한 대부분의 AI 어시스턴트는 컨텍스트로 넘긴 코드를 서버로 전송한다. 어떤 데이터가 컨텍스트에 있는지 팀원들이 의식해야 한다.

실제로 있었던 상황: `.env.local`이 열려있는 상태에서 Cursor에게 API 연동 코드를 물어봤고, AI가 실제 API 키 값을 응답에 포함시켰다.

팀 차원에서 설정한 것들:

- `.cursorrules`에 "환경변수 파일을 컨텍스트에 포함시키지 않는다" 명시
- Cursor의 Privacy Mode 활성화 여부 팀 전체 통일 (우리는 켰다)
- 내부 비즈니스 로직이 담긴 파일은 AI 컨텍스트에서 의식적으로 제외

Cursor Privacy Mode를 켜면 코드가 학습 데이터로 쓰이지 않는다. 대신 일부 기능이 제한된다. 이 trade-off를 팀 레벨에서 결정하는 것이지, 개인 설정으로 두면 안 된다.

## AI 어시스턴트가 못하는 것

AI 코딩 어시스턴트를 쓰면서 명확해진 것이 있다. 잘하는 영역과 못하는 영역이 다르다.

**잘하는 것:**
- 반복적인 boilerplate 생성
- 타입 정의 작성
- 알고 있는 패턴의 변형
- 특정 라이브러리 API 사용법
- 테스트 케이스 초안

**못하는 것:**
- 우리 서비스의 도메인 맥락을 아는 것 (숙소 예약 플로우가 왜 이렇게 됐는지)
- 기술 선택의 이유를 아는 것 (왜 A 대신 B를 썼는지)
- 레거시 코드를 건드릴 때 사이드 이펙트 예측
- 팀 내 미완성 작업이나 known issue를 아는 것

두 번째 항목들이 사실 시니어가 판단하는 영역이다. AI가 잘 못하는 것이 시니어가 해야 하는 것이다. 이게 "AI가 시니어를 대체한다"는 주장이 틀린 이유다. AI가 반복을 줄여주면 판단에 쓸 시간이 늘어난다.

## 지금 팀이 쓰는 방식 요약

- **`.cursorrules`** — 팀 컨벤션 공유, git 관리
- **Privacy Mode** — 전원 활성화
- **AI 코드 리뷰 기준** — 이해 여부 확인을 리뷰에 포함
- **주니어 가이드** — 에러 디버깅 순서 정의
- **AI 없이 먼저** — 설계 결정과 레거시 수정은 AI보다 먼저 직접 생각

AI 어시스턴트 도입은 도구의 문제가 아니라 팀의 작업 방식 문제다. 도구가 바뀌면 그에 맞는 관행도 같이 바뀌어야 한다.
