## 클로저가 존재하는 이유

"클로저는 함수가 선언될 때의 스코프를 기억하는 것"이라는 설명은 맞지만, **왜 기억해야 하는지**는 잘 말해주지 않습니다.

JavaScript는 함수를 값으로 다룹니다. 함수를 변수에 담고, 인자로 넘기고, 다른 함수에서 반환합니다. 이 순간 문제가 생깁니다.

```javascript
function makeCounter() {
  let count = 0;
  return () => ++count;
}

const counter = makeCounter();
counter(); // 1
```

`makeCounter`의 실행은 이미 끝났습니다. 스택 프레임이 사라졌다면 `count`도 사라져야 합니다. 그런데 `counter()`는 `count`를 계속 읽고 씁니다.

만약 변수가 호출 스택에만 존재한다면 콜백, 이벤트 핸들러, `setTimeout`처럼 **나중에 실행되는 함수**는 아무것도 참조할 수 없습니다. 비동기가 기본인 언어에서 이건 치명적입니다. 그래서 JS는 스코프를 스택이 아니라 **함수가 만들어진 위치(렉시컬)** 기준으로 결정하고, 그 환경을 함수와 함께 살려 둡니다.

> 클로저는 "기능"이 아니라 렉시컬 스코프를 선택한 언어에서 함수가 일급 값일 때 따라오는 필연입니다.

## 내부 동작 방식

### 렉시컬 환경과 [[Environment]]

엔진은 코드 블록·함수 호출마다 **렉시컬 환경(Lexical Environment)** 을 만듭니다. 구조는 단순합니다.

```
LexicalEnvironment
├─ Environment Record   // 이 스코프의 변수 → 값 매핑
└─ outer                // 바깥 렉시컬 환경에 대한 참조
```

함수 객체가 **생성되는 시점**에 스펙은 내부 슬롯 `[[Environment]]`에 그때의 렉시컬 환경을 저장합니다. 함수가 호출되면 새 환경을 만들고, 그 `outer`를 `[[Environment]]`로 연결합니다.

```
counter (함수 객체)
  [[Environment]] ──▶ makeCounter 호출 시 만들어진 환경 { count: 0 }
                                   outer ──▶ 글로벌 환경
```

변수 조회는 현재 환경 → `outer` → `outer` … 체인을 타고 올라가는 탐색입니다. `makeCounter`의 스택 프레임은 사라져도, 환경 레코드는 `counter`가 `[[Environment]]`로 참조하고 있으므로 **GC 대상이 되지 않습니다.** 이게 클로저의 전부입니다.

### 호출 시점이 아니라 선언 시점

스코프가 호출 위치가 아니라 선언 위치로 결정된다는 점이 동적 스코프와의 차이입니다.

```javascript
const x = "global";

function show() {
  console.log(x);
}

function run() {
  const x = "local";
  show(); // "global"
}
```

`show`의 `[[Environment]]`는 글로벌이므로, `run` 안에서 호출해도 `local`은 보이지 않습니다.

### 엔진은 모든 변수를 살려 두지 않는다

실제 엔진(V8)은 최적화를 합니다. 클로저가 **참조하는 변수만** 힙의 컨텍스트 객체로 옮기고, 나머지는 스택/레지스터에 둡니다. 정적 분석으로 "이 변수는 내부 함수에서 쓰인다"를 판단합니다.

다만 이 최적화에는 함정이 있습니다. 같은 스코프의 여러 클로저는 **컨텍스트를 공유**하므로, 하나라도 변수를 참조하면 그 컨텍스트에 올라간 변수는 다른 클로저가 안 써도 함께 살아 있습니다. `eval`이나 `with`가 있으면 정적 분석이 불가능해 전부 보존됩니다.

## 실제로 언제 쓰는가

### 상태 은닉

외부에서 접근할 수 없는 상태를 만들 때 가장 직접적입니다. `class`의 `#private` 이전부터 쓰던 패턴이고, 지금도 모듈 스코프 변수가 사실상 같은 역할을 합니다.

```javascript
// src/utils/createRateLimiter.js
export function createRateLimiter(limit, windowMs) {
  const calls = [];
  return function allow() {
    const now = Date.now();
    while (calls.length && now - calls[0] > windowMs) calls.shift();
    if (calls.length >= limit) return false;
    calls.push(now);
    return true;
  };
}
```

`calls` 배열은 외부에서 건드릴 방법이 없습니다.

### 설정을 미리 바인딩하는 팩토리

OTA 서비스에서 API 클라이언트를 만들 때 지역별 baseURL·헤더를 한 번 묶어 두는 식입니다.

```javascript
// src/infrastructure/http/createClient.ts
const createClient = (baseURL, headers) => (path, init) =>
  fetch(baseURL + path, { ...init, headers: { ...headers, ...init?.headers } });

const kr = createClient("https://api.example.kr", { "x-region": "KR" });
```

### React 훅

`useState`, `useEffect` 콜백, 이벤트 핸들러는 모두 **렌더링마다 새로 만들어지는 클로저**입니다. 이 사실이 다음 섹션의 가장 흔한 버그로 이어집니다.

## 흔한 오해와 함정

### 1. "클로저는 값을 복사한다"

클로저는 값이 아니라 **변수 바인딩(환경 레코드) 자체**를 참조합니다.

```javascript
let n = 1;
const read = () => n;
n = 2;
read(); // 2, 선언 시점의 1이 아님
```

### 2. 루프의 var

```javascript
// 수정 전
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// 3, 3, 3

// 수정 후
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// 0, 1, 2
```

`var`는 함수 스코프라 환경이 하나뿐이고, 세 콜백이 같은 `i`를 봅니다. `let`은 스펙상 **매 반복마다 새 환경을 만들고 값을 복사**해 넘깁니다. 클로저가 매 반복의 환경을 각각 붙잡는 겁니다.

### 3. React의 stale closure

```javascript
function Timer() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      console.log(count); // 항상 0
      setCount(count + 1); // 항상 0 + 1
    }, 1000);
    return () => clearInterval(id);
  }, []);
}
```

의존성 배열이 `[]`라 effect는 첫 렌더에서 한 번만 실행됩니다. 이 콜백의 `[[Environment]]`는 **첫 렌더의 환경**이고, 그 안의 `count`는 영원히 `0`입니다. 렌더마다 새 `count` 바인딩이 생기지만 낡은 클로저는 그걸 볼 수 없습니다.

해결은 클로저가 낡은 값을 보지 않게 만드는 것입니다.

```javascript
setCount((c) => c + 1); // 함수형 업데이트: 최신 값은 React가 넘겨줌
```

또는 의존성에 `count`를 넣어 effect를 재생성하거나, 최신 값을 `ref`에 담아 읽습니다. 핵심은 "버그가 아니라 클로저의 정상 동작"이라는 인식입니다.

### 4. 의도치 않은 메모리 보존

```javascript
function attach(el) {
  const hugeData = loadBigPayload();
  const summary = hugeData.length;

  el.addEventListener("click", () => {
    console.log(summary);
  });
}
```

핸들러는 `summary`만 쓰지만, 같은 스코프에 `eval` 같은 동적 요소가 있거나 다른 클로저가 `hugeData`를 참조하고 있으면 컨텍스트가 공유되어 `hugeData`가 핸들러 수명만큼 살아남을 수 있습니다. 장수 객체(이벤트 리스너, 타이머, 모듈 캐시)에 붙은 클로저가 큰 객체를 잡고 있는지는 힙 스냅샷에서 `(closure)` / `Context`를 보면 확인됩니다.

습관으로 삼을 것은 하나입니다. **필요한 값만 꺼내고, 큰 참조는 스코프 밖으로 풀어 주기**, 그리고 리스너·타이머의 **해제**.

## 정리

클로저의 핵심은 **"함수는 만들어진 환경을 `[[Environment]]`로 붙잡고, 그 환경은 함수가 살아 있는 한 GC되지 않는다"** 입니다.

상태를 숨기거나 설정을 미리 묶을 때는 적극 활용하고, 비동기 콜백·React 훅처럼 "언제의 환경을 보고 있는가"가 중요한 곳에서는 선언 시점의 값을 보고 있다는 전제로 코드를 읽으세요. 다음에 stale 값을 만나면 먼저 "이 함수는 어느 렌더에서 만들어졌지?"를 물어보면 됩니다.
