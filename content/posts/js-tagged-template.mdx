## Tagged template이 존재하는 이유

일반 템플릿 리터럴은 편합니다. 하지만 편한 만큼 **정보를 버립니다.**

```javascript
const name = userInput;
const q = `SELECT * FROM users WHERE name = '${name}'`;
```

결과는 그냥 하나의 문자열입니다. 어디까지가 개발자가 쓴 고정 문자열이고 어디부터가 외부에서 들어온 값인지, 이 시점에는 구분할 방법이 없습니다. SQL 인젝션, XSS, 로케일별 포맷팅 같은 문제가 전부 이 지점에서 생깁니다.

Tagged template은 이렇게 답합니다.

> "문자열을 합치기 전에, 조각과 값을 따로 받아서 네가 직접 합쳐라."

```javascript
const q = sql`SELECT * FROM users WHERE name = ${name}`;
```

`sql`은 문자열 메서드가 아니라 **그냥 함수**입니다. 문법만 다를 뿐, 이 구문은 함수 호출로 변환됩니다.

## 내부 동작 방식

### 호출 형태로의 변환

```javascript
tag`Hello ${a} and ${b}!`
// 대략 이렇게 평가된다
tag(["Hello ", " and ", "!"], a, b)
```

첫 번째 인자는 **리터럴 조각 배열**, 나머지는 보간된 값입니다. 규칙은 하나입니다.

> strings.length === values.length + 1

보간이 맨 앞이나 맨 뒤에 있어도 빈 문자열 조각이 들어가 이 관계는 항상 유지됩니다. 그래서 합치는 코드는 항상 이 형태가 됩니다.

```javascript
// utils/html.js
function html(strings, ...values) {
  return strings.reduce(
    (acc, str, i) => acc + str + (i < values.length ? escape(values[i]) : ""),
    ""
  );
}
```

### strings 배열은 매번 새로 만들어지지 않는다

여기가 잘 알려지지 않은 부분입니다. 스펙상 **같은 소스 위치의 템플릿은 호출될 때마다 같은 strings 배열 객체**를 받습니다. 엔진이 템플릿 객체(Template Object)를 사이트별로 한 번 만들어 캐싱하고, 이 배열은 `Object.freeze`되어 있습니다.

```javascript
const seen = new Set();
function tag(strings) { seen.add(strings); }

for (let i = 0; i < 3; i++) tag`a${i}b`;
console.log(seen.size); // 1 — 루프를 3번 돌아도 같은 객체

tag`a${0}b`; // 다른 소스 위치
console.log(seen.size); // 2
```

이 성질 덕분에 `strings`를 `WeakMap`의 키로 쓸 수 있습니다. lit-html이 템플릿 파싱 결과를 캐싱하는 방식이 정확히 이것입니다. "이 템플릿은 이미 파싱했다"를 문자열 비교 없이 **참조 동일성**으로 판단합니다. 값이 바뀌어도 strings는 그대로이므로, 정적 부분은 한 번만 처리하고 동적 부분만 갱신할 수 있습니다.

### raw 프로퍼티

strings 배열에는 `raw`라는 프로퍼티가 달려 있습니다. 이스케이프 시퀀스를 **해석하기 전** 원본 텍스트입니다.

```javascript
function show(strings) {
  console.log(strings[0]);     // 줄바꿈 문자 (해석됨)
  console.log(strings.raw[0]); // \n 두 글자 그대로
}
show`line1\nline2`;
```

`String.raw`가 바로 이 `raw`를 합쳐 주는 태그 함수입니다. 정규식 문자열이나 Windows 경로처럼 백슬래시가 많은 문자열에 쓰입니다.

### 반환값은 문자열일 필요가 없다

태그 함수는 무엇이든 반환할 수 있습니다. styled-components는 React 컴포넌트를, GraphQL의 `gql`은 AST를, lit의 `html`은 템플릿 결과 객체를 반환합니다. **문자열 보간 문법을 빌려 쓴 DSL**이라고 보는 편이 정확합니다.

## 실제로 언제 쓰는가

**적합한 경우:**
- 외부 값이 섞이는 문자열을 안전하게 처리해야 할 때 (SQL, HTML, 셸 명령)
- 내장 DSL이 필요할 때 (스타일, 쿼리, 템플릿)
- 정적 조각과 동적 값을 분리해 캐싱·최적화하고 싶을 때

**쓰지 않아도 되는 경우:**
- 단순 문자열 조립 — 일반 템플릿 리터럴로 충분합니다
- 팀원이 태그 동작을 모르는 코드 — 마법처럼 보이는 비용이 이득보다 큽니다

여행 서비스에서 흔한 예로, 다국어 가격 표기를 태그로 묶을 수 있습니다.

```javascript
// utils/format.js
const krw = new Intl.NumberFormat("ko-KR");

function price(strings, ...values) {
  return strings.reduce((acc, s, i) => {
    const v = values[i];
    return acc + s + (typeof v === "number" ? `${krw.format(v)}원` : v ?? "");
  }, "");
}

price`객실 ${"디럭스"} 1박 ${189000}`; // "객실 디럭스 1박 189,000원"
```

## 흔한 오해와 함정

### 1. sql 태그가 있어도 안전한 건 아니다

태그 함수가 값을 **파라미터로 분리**해서 DB 드라이버에 넘길 때만 안전합니다. 태그 안에서 그냥 합쳐 버리면 일반 템플릿 리터럴과 다를 게 없습니다.

```javascript
// 위험: 이름만 태그지 그냥 문자열 결합
const sql = (s, ...v) => String.raw({ raw: s }, ...v);

// 안전: 값은 placeholder로, 값 배열은 따로
const sql = (s, ...v) => ({
  text: s.reduce((acc, str, i) => acc + "$" + i + str),
  values: v,
});
```

### 2. 태그 뒤에 괄호를 붙인 것과는 다르다

```javascript
tag`a${1}`   // tag(strings, 1)
tag(`a${1}`) // tag("a1") — 이미 합쳐진 문자열 하나
```

후자는 조각 분리 정보가 이미 사라진 뒤입니다.

### 3. strings를 수정하려 하지 말 것

배열이 freeze되어 있고 캐싱되므로, 수정하려 하면 strict mode에서 TypeError가 납니다. 변형이 필요하면 복사본을 만드세요.

### 4. 잘못된 이스케이프는 태그에서만 허용된다

일반 템플릿에서 `\u` 뒤에 잘못된 값이 오면 SyntaxError지만, 태그드 템플릿에서는 해당 조각이 `undefined`가 되고 `raw`에만 남습니다. 태그 함수가 이스케이프를 직접 해석하는 DSL을 만들 수 있게 하려는 설계입니다. 그래서 `strings[i]`는 `undefined`일 수 있다는 점을 방어해야 합니다.

## 정리

Tagged template의 핵심은 **"문자열이 합쳐지기 전에 조각과 값을 분리해서 가로채는 함수 호출"** 입니다.

외부 입력을 안전하게 다뤄야 하거나, 문자열 문법을 빌린 DSL이 필요할 때 쓰면 좋습니다. 단순 조립이라면 일반 템플릿 리터럴이면 충분합니다. 다음에 styled-components나 `gql`을 쓸 때, 그 백틱이 사실 함수 호출이라는 점을 떠올려 보세요.
