## useState가 존재하는 이유

함수 컴포넌트는 그냥 함수입니다. 렌더링할 때마다 처음부터 끝까지 다시 실행되고, 지역 변수는 실행이 끝나면 사라집니다.

```tsx
function Counter() {
  let count = 0; // 렌더마다 0으로 초기화
  return <button onClick={() => count++}>{count}</button>;
}
```

클래스 컴포넌트는 `this`라는 인스턴스가 있어서 상태를 붙일 곳이 있었습니다. 함수에는 그게 없습니다. 그래서 React는 **함수 바깥, 즉 React가 관리하는 저장소에 상태를 두고 렌더링 때마다 꺼내 주는 방식**을 택했습니다. `useState`는 그 저장소에 접근하는 창구입니다.

> 상태는 컴포넌트 함수 안에 있지 않습니다. 해당 컴포넌트의 Fiber 노드에 있습니다.

## 내부 동작 방식

### 훅은 Fiber의 연결 리스트다

컴포넌트 하나는 Fiber 노드 하나에 대응합니다. 이 Fiber의 `memoizedState` 필드에 **훅 객체들의 연결 리스트**가 매달립니다.

```
Fiber(Counter)
  memoizedState ─▶ [hook1: useState] ─▶ [hook2: useEffect] ─▶ [hook3: useState] ─▶ null
```

`useState`가 호출될 때 React는 "지금 렌더 중인 Fiber의 몇 번째 훅인가"를 포인터로 추적하며 리스트를 순서대로 따라갑니다. **훅에 이름이나 키가 없는데도 값을 찾을 수 있는 이유는 오직 호출 순서 때문입니다.**

여기서 훅 규칙이 나옵니다. 조건문 안에서 훅을 호출하면 렌더마다 순서가 달라지고, 리스트의 2번 자리에 있던 값을 엉뚱한 훅이 읽게 됩니다. 린트 규칙이 아니라 자료구조의 제약입니다.

### mount와 update는 다른 함수다

React는 렌더 단계마다 훅 구현체(dispatcher)를 갈아 끼웁니다.

- **mount**: 훅 객체를 새로 만들어 리스트 끝에 붙이고, 초기값을 저장
- **update**: 기존 훅 객체를 리스트에서 꺼내 대기 중인 업데이트를 반영

그래서 `useState(expensive())`의 초기값 계산은 매 렌더 실행됩니다. 인자를 평가하는 것은 JS이고, React는 update 때 그 값을 버릴 뿐입니다. 비싼 계산이라면 `useState(() => expensive())`처럼 초기화 함수를 넘겨야 mount에서만 실행됩니다.

### setState는 값을 바꾸지 않고 큐에 넣는다

`setCount(1)`은 `count`를 바꾸지 않습니다. 훅 객체의 **업데이트 큐(순환 연결 리스트)** 에 업데이트를 추가하고, Fiber에 "다시 렌더 필요" 표시를 한 뒤 스케줄링합니다.

```
setCount(c => c + 1)
setCount(c => c + 1)
  → queue: [update1, update2]
  → 다음 렌더에서 초기 상태에 순서대로 적용 → 2
```

다음 렌더에서 React는 큐를 처음부터 끝까지 돌려 최종 상태를 계산합니다. 값을 넘기면 "이 값으로 교체", 함수를 넘기면 "이전 상태를 받아 계산"입니다.

## 실제로 언제 쓰는가

- 렌더링 결과에 영향을 주고, 바뀌면 화면이 다시 그려져야 하는 값 → `useState`
- 바뀌어도 화면과 무관한 값(타이머 ID, 이전 값 추적) → `useRef`
- 다른 상태에서 계산 가능한 값 → 상태로 두지 말고 렌더 중에 계산

세 번째가 특히 중요합니다. `items`와 `filteredItems`를 둘 다 상태로 두면 동기화 버그의 원인이 됩니다. 원본만 상태로 두고 파생값은 계산하세요.

## 흔한 오해와 함정

### 1. setState 직후에 값이 안 바뀐다

```tsx
// 수정 전
const handleClick = () => {
  setCount(count + 1);
  setCount(count + 1);
  console.log(count); // 여전히 이전 값
};
// 결과: +1
```

`count`는 **이번 렌더의 스냅샷**입니다. 상수나 마찬가지입니다. 두 호출 모두 `0 + 1`을 큐에 넣습니다.

```tsx
// 수정 후
const handleClick = () => {
  setCount(c => c + 1);
  setCount(c => c + 1);
};
// 결과: +2
```

### 2. 객체를 직접 변경하면 렌더가 안 된다

setState는 `Object.is`로 이전 값과 비교하고, 같으면 리렌더를 건너뜁니다(bail out). `state.list.push(x)` 후 `setState(state)`를 하면 참조가 같아서 아무 일도 일어나지 않습니다. 새 참조를 만들어야 합니다.

### 3. bail out은 완전한 무시가 아니다

같은 값으로 setState해도 React가 해당 컴포넌트 함수를 한 번 더 호출해 본 뒤 버리는 경우가 있습니다. 렌더 함수가 순수해야 하는 이유이고, StrictMode가 두 번 실행하는 것과도 같은 맥락입니다.

### 4. 배칭 덕분에 렌더는 한 번

이벤트 핸들러 안의 여러 setState는 큐에 쌓였다가 한 번의 렌더로 처리됩니다. React 18부터는 `setTimeout`, Promise 안에서도 동일합니다.

## 정리

`useState`의 핵심은 **"상태는 Fiber의 훅 리스트에 저장되고, 호출 순서로 찾으며, setState는 값 변경이 아니라 큐 적재"** 라는 것입니다.

이전 상태에 의존하는 갱신이면 함수형 업데이트를 쓰고, 파생 가능한 값은 상태로 만들지 마세요. 렌더 도중 "왜 값이 안 바뀌지?" 싶을 때는 스냅샷 개념부터 의심해 보면 대부분 풀립니다.
