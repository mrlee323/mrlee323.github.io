## 규칙을 적는 건 쉽다

AI에게 프로젝트 컨벤션을 가르치는 이야기는 [예전에](/posts/ai-coding-assistant-team) 한 번 썼고, 여러 저장소를 지도로 묶은 이야기도 [따로](/posts/multi-repo-ai-workflow) 정리했습니다. 규칙 파일을 만들고 컨벤션을 적어 넣으면 결과물이 눈에 띄게 안정됩니다. 여기까지는 어렵지 않습니다.

문제는 그다음입니다. **시간이 지나면 그 문서를 아무도 안 믿게 됩니다.**

규칙이 쌓이면서 지금은 맞지 않는 문장이 섞이고, 한번 틀린 문장이 발견되면 나머지도 의심받습니다. 그러면 사람은 문서를 안 읽고 AI만 읽는 상태가 되는데, 이게 최악입니다. **틀린 규칙을 AI만 성실히 지킵니다.**

그래서 운영하면서 실제로 중요했던 건 무엇을 넣을지가 아니라 **무엇을 넣지 않을지**였습니다.

## 1. 영속적인 규칙만 넣는다

가장 큰 기준입니다.

> **하네스에는 영속적인 규칙만. 티켓으로 추적되는 일시적 결함은 넣지 않는다.**

실제로 이런 문장을 넣고 싶은 유혹이 자주 옵니다.

```markdown
❌ 현재 A 화면의 목록 정렬이 깨져 있으니 이 컴포넌트는 수정하지 말 것
❌ B API는 임시로 응답이 느리니 타임아웃을 늘려서 호출할 것
```

당장은 유용합니다. 그런데 저 버그가 고쳐지면 문장은 남습니다. 반년 뒤에 새로 온 사람이나 AI가 저걸 읽고 **멀쩡한 컴포넌트를 피해 다닙니다.**

일시적인 것은 이슈 트래커가 담당합니다. 규칙 문서의 수명은 **프로젝트의 수명과 같아야** 합니다.

반대로 이런 건 넣습니다. 전부 "몰라서 사고 났던 것"이고, 앞으로도 계속 참인 것들입니다.

```markdown
✅ 이 폴더는 백엔드가 아니라 프록시 계층이다. 비즈니스 로직을 두지 않는다
✅ 금액은 클라이언트 계산값이 아니라 서버 값을 기준으로 한다
✅ 겉보기에 비슷한 두 추적 시스템은 별개다. 한쪽 값을 다른 쪽에 쓰지 않는다
```

판단 기준은 하나입니다. **"이 문장이 티켓으로 닫힐 수 있는가?"** 닫힐 수 있으면 티켓으로 보냅니다.

## 2. 한 파일에 다 넣지 않는다 — 토큰 문제

규칙이 늘면 파일이 길어지고, 세션마다 그게 통째로 읽힙니다. 컨텍스트를 규칙이 차지하면 **정작 코드를 읽을 여유가 줄어듭니다.** 규칙을 잘 지키면서 엉뚱한 코드를 고치는 일이 생깁니다.

그래서 세 갈래로 나눴습니다.

| 무엇 | 언제 읽히나 |
|---|---|
| 규칙 문서 | 항상 |
| 도메인별 규칙 (인증·결제·다국어처럼 함정이 많은 영역) | 그 영역을 건드릴 때만 |
| 온보딩 문서 (폴더 구조, 요청 흐름 지도) | 처음 한 번 |

특히 **온보딩을 분리한 게 컸습니다.** 구조 지도는 길지만 매번 필요하지 않습니다. 이걸 상시 문서에 두면 매 세션 비용을 내면서 거의 안 씁니다.

## 3. 같은 사실을 두 곳에 적지 않는다

여러 저장소를 다루면 "어느 저장소가 무엇을 담당하는가"를 적은 상위 지도가 필요합니다. 그런데 여기에 상세를 적기 시작하면 곧 각 저장소의 규칙 문서와 어긋납니다.

그래서 상위 지도에는 **판별에 필요한 최소 정보만** 둡니다.

```markdown
### 서비스 프론트엔드
| 레이어 | 서비스 FE |
| 스택 | Next.js · React · TypeScript |
| 도메인 | 검색, 상세, 결제, 마이페이지 |
| 키워드 | 서비스, 프론트, 웹, 결제, 예약, 마이페이지 |
```

`키워드` 줄이 실질적인 역할을 합니다. 티켓 제목에 "결제"가 있으면 후보 저장소가 바로 나옵니다. 그 이상의 상세는 각 저장소 문서가 담당합니다.

> 같은 사실이 두 곳에 있으면 언젠가 어긋나고, 어긋나는 순간 **둘 다 못 믿게 됩니다.**

## 도구는 마지막

이 정도 정리되면 도구는 거들 뿐입니다. 그래도 실제로 도움이 된 둘은 적어둡니다.

**워크스페이스 도구** — worktree를 왜 쓰는지는 [앞 글](/posts/multi-repo-ai-workflow)에서 다뤘고, 지금도 [Orca](https://www.onorca.dev/)로 관리합니다. 여기서 하나만 덧붙이면, **막혔을 때 이유를 알려주는 게** 생각보다 중요했습니다. 기준 브랜치에서 워크스페이스를 만들 때 fast-forward가 안 되면 "어느 worktree에 커밋 안 된 변경이 있어서"까지 알려줍니다. worktree가 늘어날수록 사람이 원인을 못 찾는 상황이 생기는데, 그 지점을 도구가 메워줍니다.

**MCP 연동** — 이슈 트래커와 메신저를 [MCP](https://modelcontextprotocol.io/)로 붙여 세션 안에서 조회합니다. 편해서가 아니라, **AI가 티켓 본문과 논의 경위를 직접 읽고 판단에 쓸 수 있다**는 게 큽니다. 티켓 요약만 보면 왜 하는지가 안 나오는데, 댓글까지 읽으면 배경이 나옵니다. 사람이 매번 요약해서 전달하지 않아도 됩니다.

## 정리

규칙 문서를 오래 굴리려면 넣는 기준보다 **빼는 기준**이 필요합니다.

- **티켓으로 닫힐 수 있는 문장은 넣지 않는다** — 문서가 썩는 가장 흔한 경로
- **한 파일에 다 넣지 않는다** — 규칙이 컨텍스트를 다 먹으면 코드를 못 읽는다
- **같은 사실을 두 곳에 적지 않는다** — 어긋나면 둘 다 신뢰를 잃는다

문서는 쓰는 것보다 **안 썩게 유지하는 게** 어렵습니다. 그리고 이건 AI 때문에 생긴 문제가 아니라, 원래 있던 문제가 AI 덕분에 드러난 쪽에 가깝습니다.
