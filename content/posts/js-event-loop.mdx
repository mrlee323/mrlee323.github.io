## 이벤트 루프가 존재하는 이유

자바스크립트는 처음부터 브라우저 안에서 DOM을 만지기 위해 만들어진 언어입니다. 스레드가 둘이면 한쪽이 노드를 지우는 동안 다른 쪽이 그 노드를 수정하는 일이 생깁니다. 락과 동기화를 언어 차원에서 노출하는 대신, **실행 스레드를 하나로 고정**하는 선택을 했습니다.

문제는 네트워크 요청, 타이머, 사용자 입력처럼 "기다려야 하는 일"입니다. 싱글 스레드가 이걸 동기적으로 기다리면 화면 전체가 멈춥니다.

> "기다리는 일은 엔진 밖에 맡기고, 끝나면 결과만 돌려받자."

이 구조를 구현한 것이 이벤트 루프입니다. 중요한 점은 **이벤트 루프는 자바스크립트 엔진(V8)의 기능이 아니라 호스트 환경(브라우저, Node.js)의 기능**이라는 겁니다. V8은 호출 스택과 힙만 갖고 있고, 타이머나 fetch는 호스트가 제공합니다.

## 내부 동작 방식

### 구성 요소

```
        ┌─────────────── 호스트 환경 ───────────────┐
        │  Web APIs (timer, fetch, DOM events ...)  │
        └──────┬─────────────────────────▲──────────┘
               │ 완료 시 콜백 등록          │ 위임
               ▼                          │
        [Task Queue]  [Microtask Queue]   │
               │            │             │
               └─────┬──────┘             │
                     ▼                    │
              ┌─ Event Loop ─┐            │
              │ 스택이 비었나? │            │
              └──────┬───────┘            │
                     ▼                    │
              [Call Stack] ───────────────┘
              (JS 엔진, 한 번에 하나만 실행)
```

- **호출 스택**: 지금 실행 중인 함수들. 한 번에 하나의 작업만 처리합니다.
- **태스크 큐(매크로태스크)**: `setTimeout`, 사용자 이벤트, `MessageChannel` 등의 콜백이 대기하는 곳.
- **마이크로태스크 큐**: `Promise.then`, `queueMicrotask`, `MutationObserver` 콜백이 대기하는 곳.

### 한 바퀴의 순서

이벤트 루프 한 번(tick)은 대략 이렇게 돕니다.

1. 태스크 큐에서 **태스크 하나**를 꺼내 실행한다.
2. 호출 스택이 비면 **마이크로태스크 큐를 완전히 비울 때까지** 전부 실행한다. (실행 중 새로 추가된 마이크로태스크도 포함)
3. 브라우저라면 렌더링 기회가 있는지 확인하고, 있으면 스타일 계산 → 레이아웃 → 페인트를 수행한다. (`requestAnimationFrame` 콜백은 이 직전에 실행)
4. 다시 1번으로.

핵심은 2번입니다. 태스크는 한 바퀴에 하나지만, 마이크로태스크는 **큐가 빌 때까지 다 처리**합니다.

```javascript
console.log("1");
setTimeout(() => console.log("2"), 0);
Promise.resolve().then(() => console.log("3"));
console.log("4");
// 출력: 1 → 4 → 3 → 2
```

동기 코드(1, 4)가 끝나고, 마이크로태스크(3)가 돌고, 그 다음 태스크(2)가 돕니다. `setTimeout(fn, 0)`이 "즉시 실행"이 아닌 이유입니다. 0ms는 "최소 대기 시간"이 아니라 "다음 태스크 큐 차례"를 뜻합니다.

### 렌더링은 태스크 사이에 끼어든다

렌더링은 호출 스택이 비어 있을 때만 일어날 수 있습니다. 즉 **JS가 오래 실행되면 그동안 페인트도, 클릭 반응도 없습니다.** 60fps 기준으로 한 프레임은 약 16ms이고, 그 안에 스크립트 실행과 렌더링이 모두 들어가야 합니다.

## 실제로 언제 쓰는가

이벤트 루프를 "쓴다"기보다, 이 구조를 알고 **어느 큐에 일을 넣을지 선택**하는 상황이 있습니다.

| 하고 싶은 일 | 선택 | 이유 |
|---|---|---|
| 현재 동기 코드 직후, 렌더링 전에 처리 | `queueMicrotask` / `Promise.then` | 다음 페인트 전에 반드시 실행됨 |
| 렌더링 후로 미루고 싶음 | `setTimeout` / `MessageChannel` | 태스크로 넘어가 렌더링 기회를 줌 |
| 애니메이션/레이아웃 읽기 | `requestAnimationFrame` | 페인트 직전에 실행됨 |
| 긴 계산을 쪼개 UI 응답성 유지 | 청크 단위 + 태스크 양보 | 청크 사이에 입력/렌더링이 끼어들 수 있음 |

긴 작업을 쪼개는 패턴은 이런 모양입니다.

```javascript
async function processInChunks(items, handle) {
  for (let i = 0; i < items.length; i += 100) {
    items.slice(i, i + 100).forEach(handle);
    // 태스크 경계를 만들어 렌더링/입력이 끼어들 틈을 준다
    await new Promise((resolve) => setTimeout(resolve, 0));
  }
}
```

OTA 서비스에서 수천 건의 객실/요금 데이터를 클라이언트에서 정렬·필터링할 때, 한 번에 돌리면 검색창 입력이 얼어붙는 경험을 하게 됩니다. 원인은 데이터 양 자체보다 **한 태스크가 렌더링을 점유한 시간**입니다.

## 흔한 오해와 함정

### 1. "async/await이면 비동기니까 안 막힌다"

`async` 함수도 `await`를 만나기 전까지는 동기로 실행됩니다. 그리고 `await` 이후는 마이크로태스크입니다.

```javascript
// 수정 전: 마이크로태스크만 계속 이어져 렌더링이 영영 오지 않음
async function loop() {
  while (true) {
    await Promise.resolve();
  }
}

// 수정 후: 태스크 경계를 만들어 렌더링 기회를 줌
async function loop() {
  while (true) {
    await new Promise((resolve) => setTimeout(resolve, 0));
  }
}
```

마이크로태스크는 큐가 빌 때까지 실행되므로, 스스로를 계속 추가하면 **태스크 큐도 렌더링도 굶습니다.**

### 2. "setTimeout(fn, 100)은 100ms 뒤에 실행된다"

100ms 뒤에 태스크 큐에 **들어갈** 뿐입니다. 그 시점에 호출 스택이 바쁘면 실행은 더 늦어집니다. 브라우저는 중첩된 타이머를 4ms 이상으로 클램핑하고, 백그라운드 탭에서는 1초 이상으로 늦추기도 합니다. 타이머를 정밀한 시계로 쓰면 안 됩니다.

### 3. "Promise 안의 코드는 비동기로 실행된다"

`new Promise(executor)`의 executor는 **즉시 동기 실행**됩니다. 비동기인 것은 `.then` 콜백뿐입니다.

```javascript
new Promise((resolve) => {
  console.log("A"); // 동기
  resolve();
}).then(() => console.log("B")); // 마이크로태스크
console.log("C");
// A → C → B
```

### 4. Node.js도 똑같다고 생각하기

Node는 libuv 기반이라 timers → poll → check(`setImmediate`) 같은 **단계(phase)** 구조를 가집니다. 브라우저의 단일 태스크 큐 모델과 다르고, `process.nextTick`은 마이크로태스크보다 먼저 처리되는 별도 큐입니다. 브라우저에서 외운 출력 순서가 Node에서는 어긋날 수 있습니다.

## 정리

이벤트 루프의 핵심은 **"스택이 비어야만 다음 일이 시작된다"** 입니다. 비동기는 일을 병렬로 실행하는 것이 아니라, 기다림을 엔진 밖으로 보내고 결과 처리만 순서대로 끼워 넣는 방식입니다.

UI가 버벅일 때는 API 응답 속도보다 먼저 **한 태스크가 얼마나 오래 스택을 점유하는지** 보세요. 50ms를 넘는 긴 태스크가 보이면 쪼개거나, 렌더링 전/후 중 어느 큐에 넣을지 의도적으로 선택하는 것이 첫 번째 해법입니다.
