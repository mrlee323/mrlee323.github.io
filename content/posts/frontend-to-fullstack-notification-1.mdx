## 요청은 한 줄이었다

> "기획전 오픈 전에 알림 신청을 받고 싶다."

프로모션 페이지가 열리기 전에 사용자가 "열리면 알려줘"를 눌러두면, 오픈 시점에 신청한 사람에게만 푸시가 가는 기능입니다. 흔한 기능이고, 화면만 보면 버튼 하나입니다.

기존에 푸시 시스템이 이미 있었으니 붙이기만 하면 될 것 같았습니다. 그런데 열어보니 구조가 이랬습니다.

- 관리자가 **발송 대상을 직접 지정**해서 보내는 구조
- 신청자를 **모으는 경로가 없음**
- 특정 시점에 **자동으로 나가는 경로도 없음**

즉 "누가 신청했는지 쌓고, 마감하고, 때가 되면 그 사람들한테만 보낸다"는 흐름이 통째로 없었습니다. 버튼 하나가 아니라 **경로 하나를 새로 뚫는 일**이었습니다.

그리고 이 프로젝트에는 서버 담당자가 없었습니다. 프론트엔드를 맡고 있었지만, 이 기능은 프론트만으로는 성립하지 않았습니다.

## 첫 결정: 새로 만들 것인가, 얹을 것인가

가장 먼저 갈린 지점입니다. 선택지는 둘이었습니다.

**A. 알림 신청 전용 시스템을 새로 만든다**
신청 수집부터 발송까지 독립적으로. 기존 푸시를 안 건드리니 사고 위험이 낮습니다.

**B. 기존 푸시에 "알림 신청형"이라는 발송 타입을 하나 추가한다**
기존 코드를 건드려야 합니다. 대신 발송·로깅·재시도 같은 걸 다시 만들지 않습니다.

**B를 골랐습니다.** 이유는 셋이었습니다.

첫째, **발송은 이미 검증된 코드**였습니다. 푸시 발송에는 토큰 관리, 실패 재시도, 플랫폼별 페이로드 차이, 발송 결과 로깅 같은 게 붙어 있습니다. 이건 만드는 것보다 **운영하면서 다듬어진 게 훨씬 중요한** 종류의 코드입니다. 새로 만들면 겉보기엔 되는데 엣지 케이스에서 6개월 동안 조금씩 터집니다.

둘째, **운영자가 두 화면을 오가게 만들고 싶지 않았습니다.** 푸시는 저기서 보내고 알림 신청 푸시는 여기서 보내는 구조가 되면, 나중에 "왜 이건 저기 없어요?"라는 질문이 계속 나옵니다.

셋째, 솔직히 **제가 서버를 처음 만지는 상황**이었습니다. 익숙하지 않은 사람이 새 시스템을 설계하면 기존 시스템이 왜 그렇게 생겼는지 모르는 채로 같은 함정을 다시 밟습니다. 기존 구조에 맞춰 넣으면, 그 구조 자체가 **이미 검증된 설계 판단의 집합**이라 따라가는 것만으로 안전합니다.

> 익숙하지 않은 영역에서는 **새로 만드는 게 더 어려운 선택**입니다. 자유도가 높다는 건 틀릴 자유도 높다는 뜻입니다.

## 그 결정이 나머지를 정했다

"기존 것에 얹는다"를 정하니 작업 범위가 자동으로 나왔습니다. 기존 푸시 흐름이 지나가는 모든 구간이 대상이 됩니다.

| 구간 | 무엇을 해야 하나 |
|---|---|
| 서비스 프론트 | 신청·취소 UI, 상태 표시 |
| 서비스 서버 API | 신청 접수, 검증, 신청 상태 조회 |
| 어드민 프론트 | 대상 페이지와 발송 시점 설정, 신청 현황 |
| 어드민 서버 API | 알림 설정 저장, 푸시 자동 생성 |
| 스케줄러 | 마감 시점에 발송 대상 확정 |
| 배치 | 실제 발송 |

여섯 개입니다. 그리고 전부 별도 저장소였습니다.

미리 밝혀두면, 여섯 구간의 무게는 같지 않았습니다.

| 구간 | 성격 |
|---|---|
| 서비스 프론트 · 어드민 프론트 | 신규 개발 |
| 서비스 서버 API | 신규 개발 (신청 접수·검증) |
| 어드민 서버 API | 기존 푸시 생성 로직에 타입 추가 |
| 스케줄러 | 기존 스케줄러에 마감 스냅샷 로직 추가 |
| 배치 | 기존 발송 배치에 **타입 매핑만 추가** |

배치는 사실상 한 줄짜리 작업이었습니다. "배치 시스템을 만들었다"가 아니라 **"기존 배치가 새 타입을 알아듣게 했다"** 가 정확한 표현입니다. 이 연재에서 다룰 내용도 대부분 앞의 네 구간에 있습니다.

그래도 이 여섯 개를 다 봐야 했던 이유는, 한 곳이라도 규격이 어긋나면 기능이 성립하지 않기 때문입니다.

프론트만 하던 때와 가장 달랐던 게 여기였습니다. **프론트는 화면이 곧 경계**라서 "이 화면까지가 내 일"이 명확합니다. 그런데 이 기능은 경계가 없고, **중간 어느 한 구간만 어긋나도 사용자에겐 "안 되는 기능"**입니다.

## 코드보다 먼저 규격을 정했다

그래서 구현 순서를 이렇게 잡았습니다.

1. 여섯 구간이 **주고받는 데이터 규격**을 먼저 확정
2. 그다음 각 구간 구현
3. 마지막에 연결·검증

역순으로 갔다면, 즉 프론트부터 만들고 서버를 맞췄다면 어떻게 됐을까요. 프론트에서 편한 모양으로 규격이 정해지고, 스케줄러 단계에 가서 "이 정보로는 대상을 못 뽑는데요"가 나옵니다. 그때 되돌리면 앞의 세 구간을 다 고쳐야 합니다.

규격을 먼저 정하면서 실제로 잡힌 것들입니다.

- 신청 데이터는 **어디에 쌓이고 누가 소유하는가** — 신청자 정보는 서비스 쪽에 쌓지만, 발송 대상은 푸시 쪽 테이블로 옮겨져야 합니다. 옮기는 시점이 언제인가가 3편의 주제입니다
- 어드민이 설정한 "발송 시점"은 **누구의 시간인가** — 관리자 입력 시간, 저장 시간, 스케줄러 판단 시간이 다 다를 수 있습니다
- 신청 버튼의 **상태는 누가 판단하는가** — 이게 2편의 주제입니다

이 셋 중 하나라도 나중에 정했으면 여러 구간을 다시 손봐야 했습니다.

## 프론트 경험이 실제로 도움이 된 지점

서버를 처음 만지면서 의외로 프론트 경험이 유리했던 부분이 있었습니다.

**실패했을 때 화면이 어떻게 되는지를 안다는 것**입니다.

서버 API를 설계할 때 자연스럽게 이런 질문이 먼저 나왔습니다.

- 이미 신청한 사람이 또 누르면 화면에 뭐라고 떠야 하나
- 마감된 뒤에 들어온 요청은 실패인가, 아니면 "마감됨"이라는 정상 응답인가
- 비로그인 상태로 누르면 로그인 후 **돌아와서 신청까지 이어져야 하나**

이건 API 스펙 문서에 잘 안 적히는 것들인데, **프론트를 짜본 사람은 이게 없으면 화면을 못 만든다**는 걸 압니다. 그래서 응답 설계를 할 때 "성공/실패" 이분법이 아니라 **화면이 구분해서 보여줘야 하는 상태만큼** 응답을 나눴습니다.

반대로 부족했던 건 **규모 감각**이었습니다. 신청자가 10만 명이면 어떤 쿼리가 문제가 되는지, 인덱스를 어떻게 잡아야 하는지는 경험이 없었습니다. 이건 검토를 받으면서 배웠습니다. 모르는 걸 아는 척하지 않고 물어본 게 이 프로젝트에서 제일 잘한 일이었습니다.

## AI를 어떻게 썼나

솔직하게 적자면, 익숙하지 않은 영역을 혼자 관통할 수 있었던 데는 AI 활용이 있었습니다. 다만 역할이 명확히 갈렸습니다.

**제가 판단한 것**

- 새로 만들지 않고 기존 푸시를 확장한다는 방향
- 여섯 구간이 주고받는 데이터 규격
- 어떤 예외를 막아야 하는가
- 각 구간의 책임 경계

**AI가 한 것**

- 정해진 규격에 맞춘 구현
- 익숙하지 않은 스택의 관례 확인
- 반복적인 연결 코드

판단을 넘기면 안 된다는 게 핵심이었습니다. **"어떻게 만들지"는 물어봐도 되지만 "무엇을 만들지"는 물어보면 안 됩니다.** 후자를 넘기는 순간 왜 그렇게 만들었는지 설명할 수 없는 코드가 생기고, 그건 나중에 못 고칩니다.

## 정리

1편에서 한 일은 코드가 아니라 결정 하나였습니다.

- **기존 시스템을 존중한다** — 검증된 코드를 다시 만들지 않는다. 익숙하지 않은 영역일수록 더 그렇다
- **결정이 범위를 정한다** — "얹는다"를 고르니 여섯 구간이 자동으로 나왔다
- **규격을 코드보다 먼저** — 순서를 뒤집으면 되돌릴 때 앞 구간이 전부 딸려온다
- **모르는 건 물어본다** — 규모 감각은 경험의 영역이라 추측으로 메울 수 없다

프론트엔드 개발자가 서버를 하게 됐을 때 가장 크게 바뀐 건 기술 스택이 아니라 **경계 감각**이었습니다. 화면까지가 아니라 기능이 완결되는 지점까지가 범위가 됩니다.
