## Inngest란?

**Inngest**는 코드 기반의 백그라운드 작업 인프라입니다. 이전 글에서 다룬 n8n이 GUI로 워크플로우를 조립하는 방식이라면, Inngest는 **TypeScript 코드로 워크플로우를 작성하고 Vercel·AWS Lambda 같은 서버리스 환경에서 실행**합니다.

핵심 차이는 이겁니다.

| | n8n | Inngest |
|---|---|---|
| 방식 | GUI 노드 연결 | TypeScript 코드 |
| 실행 환경 | 별도 서버 필요 | 서버리스 (Next.js 안에서) |
| 타입 안전성 | 없음 | 완전한 TypeScript 지원 |
| 적합한 케이스 | 팀 자동화, 빠른 프로토타입 | 프로덕션 백그라운드 작업 |

Next.js 프로젝트에 이미 배포 인프라가 있다면 **Inngest가 훨씬 자연스럽습니다.** 별도 서버 없이 기존 API Route 하나를 서빙 엔드포인트로 쓰면 됩니다.

## 구현 배경

OTA(온라인 여행사) 서비스의 메인 페이지에는 도시별 쇼케이스 콘텐츠가 노출됩니다. 기존에는 운영팀이 직접 콘텐츠를 만들어 업로드했습니다.

문제는 두 가지였습니다.

1. **주기적인 수동 작업** — 콘텐츠 업데이트마다 배포 없이 데이터만 바꾸고 싶지만, 그 흐름 자체가 반복 업무
2. **AI 활용 기회** — 타이틀 카피, 이미지, 호텔 목록 모두 AI로 생성할 수 있는데 이를 자동화하고 싶음

목표는 이렇습니다.

```
매주 월요일 → AI가 도시별 콘텐츠 자동 생성 → DB 저장 → 메인에 자동 반영
어드민이 원할 때 → "지금 생성" 버튼 한 번 → 동일한 파이프라인 실행
```

## n8n에서 Inngest로 전환한 이유

처음엔 n8n으로 어드민 자동화를 설계했습니다. [이전 글](/posts/n8n-frontend-automation/)에서 다룬 것처럼 n8n은 GUI로 빠르게 워크플로우를 만들 수 있고, Cron + AI API 연결도 간단합니다. 프로토타입 단계에서는 충분했습니다.

그런데 실제 구현으로 넘어오면서 세 가지 문제가 구체적으로 드러났습니다.

### 문제 1: 별도 서버 운영 비용

n8n은 항상 떠 있는 서버가 필요합니다. Railway나 Render 무료 티어를 쓰더라도 **프로젝트 인프라가 Next.js(Vercel) + n8n 서버로 분리**됩니다. 배포 파이프라인, 환경변수, 장애 대응을 두 곳에서 관리해야 합니다.

이 프로젝트는 이미 Vercel로 배포 중이었고, 자동화만을 위해 별도 서버를 운영하는 건 오버헤드였습니다.

### 문제 2: 타입 공유 불가

가장 결정적인 문제였습니다. n8n 워크플로우는 TypeScript 프로젝트 외부에서 동작합니다. 즉 **프로젝트에서 쓰는 타입, 도메인 로직, 유틸리티 함수를 그대로 가져다 쓸 수 없습니다.**

도시별 병렬 생성 로직, Supabase 클라이언트, AI 서비스 함수들이 이미 `src/` 안에 잘 작성되어 있었는데, n8n에서 쓰려면 HTTP 엔드포인트로 다시 감싸야 했습니다. 결국 같은 로직을 두 곳에서 관리하게 되는 구조였습니다.

### 문제 3: 동적 fan-out 패턴의 한계

도시 목록은 어드민이 AutoConfig에서 설정합니다. 교토·제주·도쿄 3개일 수도 있고, 5개일 수도 있습니다. **도시 수가 런타임에 결정되는 동적 병렬 실행**은 n8n GUI로 표현하기 어렵습니다.

n8n의 Split in Batches 노드로 흉내 낼 수 있지만, 특정 도시 실패 시 다른 도시는 계속 진행하는 오류 격리까지 구현하면 워크플로우가 복잡해졌습니다.

### Inngest로 전환

세 문제가 모두 "코드 기반 자동화"로 해결됐습니다.

- **별도 서버 없음** — `src/app/api/inngest/route.ts` 하나로 Vercel에서 실행
- **타입 완전 공유** — 기존 `showcaseAiService.ts`, `autoConfigApi.ts` 그대로 import
- **동적 fan-out** — `cities.map((city) => step.run(...))` 으로 자연스럽게 표현

n8n 설계 단계가 낭비는 아니었습니다. 워크플로우 흐름 자체(Cron 확인 → 배치 이벤트 → 도시별 생성 → 완료 이벤트)는 그대로 Inngest 코드로 옮겼습니다. GUI로 설계하고 코드로 구현한 셈입니다.

## 전체 아키텍처

```
[Cron: 매일 00:00 KST]     [어드민 "지금 생성" 버튼]
          ↓                           ↓
  autoCheckShowcase      POST /api/admin/showcase/generate
          ↓                           ↓
          └──── admin/showcase.generate-batch 이벤트 ────┘
                                      ↓
                           autoGenerateShowcase
                                      ↓
                        도시별 병렬 step.run() 실행
                        ┌─────────────────────────┐
                        │  Gemini API → 타이틀     │
                        │  FLUX → 이미지 생성      │
                        │  Supabase → 호텔 조회    │
                        │  DB → 콘텐츠 저장        │
                        └─────────────────────────┘
```

Cron과 수동 실행이 **같은 이벤트로 합류**하는 구조가 핵심입니다. 실행 경로를 하나로 유지하면 수동 테스트한 결과가 실제 자동화와 동일하게 동작한다는 보장이 됩니다.

### 이벤트 타입 정의

Inngest는 이벤트 이름과 데이터 구조를 타입으로 연결할 수 있습니다. 이벤트를 발송하거나 수신할 때 타입이 자동으로 추론됩니다.

```ts
// src/infrastructure/inngest/events.ts
export type Events = {
  "admin/showcase.generate-batch": {
    data: {
      cities: string[];
      startDate: string;
      endDate: string;
      prompt?: string;
      triggeredBy: "cron" | "manual";
    };
  };

  "admin/showcase.batch-completed": {
    data: {
      generatedCount: number;
      failedCities: string[];
      nextGenerationDate: string;
    };
  };
};
```

### 서빙 엔드포인트

Next.js App Router에 API Route 하나만 추가하면 Inngest가 이 URL로 함수를 등록하고 실행 결과를 주고받습니다.

```ts
// src/app/api/inngest/route.ts
import { serve } from "inngest/next";
import { inngest } from "@/infrastructure/inngest/client";
import { showcaseFunctions } from "@/infrastructure/inngest/functions/showcase";

export const { GET, POST, PUT } = serve({
  client: inngest,
  functions: showcaseFunctions,
});
```

## Step 1: Cron 확인 함수

매일 자정에 실행되어 AutoConfig 테이블을 읽고, 자동 생성 조건이 맞으면 배치 이벤트를 발송합니다.

```ts
// src/infrastructure/inngest/functions/showcase/autoCheckShowcase.ts
export const autoCheckShowcase = inngest.createFunction(
  {
    id: "auto-check-showcase",
    triggers: [{ cron: "0 15 * * *" }], // 15:00 UTC = 00:00 KST
  },
  async ({ step }) => {
    // step.run()으로 감싸면 실패 시 이 단계만 재시도
    const config = await step.run("fetch-auto-config", () => getAutoConfig());

    if (!config.enabled) {
      return { skipped: true, reason: "auto generation disabled" };
    }

    const now = new Date();
    if (new Date(config.nextGenerationDate) > now) {
      return { skipped: true, reason: "not yet scheduled" };
    }

    if (config.suggestedCities.length === 0) {
      return { skipped: true, reason: "no suggested cities configured" };
    }

    // 조건 충족 → 배치 이벤트 발송
    await step.sendEvent("trigger-batch", {
      name: "admin/showcase.generate-batch",
      data: {
        cities: config.suggestedCities,
        startDate: config.contentStartDate,
        endDate: config.contentEndDate,
        triggeredBy: "cron",
      },
    });

    return { triggered: true, cities: config.suggestedCities };
  },
);
```

`step.run()`이 중요한 역할을 합니다. Inngest의 `step`은 **체크포인트**입니다. 각 step이 완료되면 그 결과를 저장하고, 이후 실패가 발생해도 완료된 step은 다시 실행하지 않습니다.

## Step 2: 배치 생성 함수

이벤트를 수신해 도시별로 AI 생성 파이프라인을 병렬 실행합니다.

```ts
// src/infrastructure/inngest/functions/showcase/autoGenerateShowcase.ts
export const autoGenerateShowcase = inngest.createFunction(
  {
    id: "auto-generate-showcase",
    retries: 2,
    triggers: [{ event: "admin/showcase.generate-batch" }],
  },
  async ({ event, step }) => {
    const { cities, startDate, endDate, prompt } = event.data;

    // 도시별 병렬 처리 — 하나 실패해도 나머지는 계속 진행
    const results = await Promise.all(
      cities.map((city) =>
        step.run(`generate-${city}`, async () => {
          try {
            const [title, imageUrl, hotels] = await Promise.all([
              generateTitle(city, prompt),   // Gemini API
              generateImage(city, prompt),   // FLUX + Supabase Storage
              resolveHotelsForCity(city),    // Supabase DB 조회
            ]);

            await createShowcaseContent({
              cityName: city, title, imageUrl, hotels,
              serviceEnabled: true, startDate, endDate,
            });

            return { city, success: true };
          } catch (err) {
            // 도시 하나가 실패해도 error를 throw하지 않고 결과로 반환
            return { city, success: false, error: String(err) };
          }
        }),
      ),
    );

    const succeeded = results.filter((r) => r.success);
    const failed = results.filter((r) => !r.success).map((r) => r.city);

    // 다음 생성 예정일 업데이트
    const nextGenerationDate = await step.run("update-schedule", async () => {
      const config = await getAutoConfig();
      const next = calcNextGenerationDate(config.intervalType, config.intervalValue);
      await updateAutoConfig({ nextGenerationDate: next });
      return next;
    });

    // 완료 이벤트 발송 (다른 함수에서 구독 가능)
    await step.sendEvent("notify-completed", {
      name: "admin/showcase.batch-completed",
      data: { generatedCount: succeeded.length, failedCities: failed, nextGenerationDate },
    });

    return { generatedCount: succeeded.length, failedCities: failed };
  },
);
```

`step.run()`을 도시마다 붙인 덕분에 "교토 생성 성공 → 제주 생성 실패 → 재시도 시 교토는 건너뛰고 제주만 재실행" 이 가능합니다.

## Step 3: AI 생성 서비스

실제 AI 호출 로직입니다. Gemini로 타이틀과 호텔 목록을, FLUX 모델로 이미지를 생성합니다.

```ts
// src/infrastructure/admin/showcaseAiService.ts
import "server-only"; // 클라이언트 번들에 포함되지 않도록

export async function generateTitle(cityName: string, prompt?: string): Promise<string> {
  const model = getGeminiModel(); // gemini-2.5-flash

  const result = await model.generateContent(`
    도시: ${cityName}
    추가 키워드: ${prompt ?? "없음"}

    숙박 앱 메인 쇼케이스 타이틀을 20자 이내, 감성적인 명사형으로 작성하세요.
    타이틀만 출력하세요.
  `);

  return result.response.text().trim().replace(/^["']|["']$/g, "");
}

export async function generateImage(cityName: string, prompt?: string): Promise<string> {
  // FLUX 모델로 이미지 생성 → Supabase Storage 업로드 → URL 반환
  const fluxPrompt = buildFluxPrompt(cityName, undefined, prompt);
  const blob = await generateImageWithFlux(fluxPrompt);

  const path = `showcase/${sanitize(cityName)}/${Date.now()}.jpg`;
  return uploadImage(path, blob);
}
```

`import "server-only"`를 파일 상단에 붙이면 이 모듈이 실수로 클라이언트 번들에 포함될 때 빌드 에러로 잡아줍니다. API 키가 있는 서버 코드는 항상 붙여두는 습관이 좋습니다.

## Step 4: 어드민 수동 실행 API

어드민 UI의 "지금 생성" 버튼이 이 엔드포인트를 호출합니다. Cron과 동일한 이벤트를 발송하기 때문에 실행 결과도 동일합니다.

```ts
// src/app/api/admin/showcase/generate/route.ts
const generateRequestSchema = z.object({
  cities: z.array(z.string().min(1)).min(1),
  startDate: z.string().datetime(),
  endDate: z.string().datetime(),
  prompt: z.string().optional(),
});

export async function POST(request: NextRequest) {
  // Supabase Auth로 로그인 확인
  const { data: { user } } = await supabase.auth.getUser();
  if (!user) return NextResponse.json({ error: "Unauthorized" }, { status: 401 });

  // 어드민 권한 확인
  const access = await getFeatureAccess("showcase");
  if (!access.canWrite) return NextResponse.json({ error: "Forbidden" }, { status: 403 });

  // Zod 유효성 검사
  const parsed = generateRequestSchema.safeParse(await request.json());
  if (!parsed.success) {
    return NextResponse.json({ error: parsed.error.flatten() }, { status: 400 });
  }

  // Inngest 이벤트 발송 — Cron과 동일한 파이프라인 실행
  const { ids } = await inngest.send({
    name: "admin/showcase.generate-batch",
    data: { ...parsed.data, triggeredBy: "manual" },
  });

  return NextResponse.json({ ok: true, eventIds: ids });
}
```

응답으로 받은 `eventIds`를 Inngest 대시보드에서 검색하면 실행 상태, 각 step의 입출력, 소요 시간을 전부 추적할 수 있습니다.

## 로컬 개발 환경

Inngest는 로컬 개발용 CLI를 제공합니다. 터미널 두 개를 띄우면 됩니다.

```bash
# 터미널 1: Next.js 개발 서버
pnpm dev

# 터미널 2: Inngest Dev Server
npx inngest-cli@latest dev -u http://localhost:3000/api/inngest
```

`http://localhost:8288` 에서 GUI 대시보드를 확인할 수 있습니다. 등록된 함수 목록, 이벤트 직접 발송, 실행 이력, step별 상세 로그를 모두 여기서 볼 수 있습니다.

Cron 함수도 로컬에서 수동으로 트리거할 수 있어서, 배포 전에 전체 파이프라인을 테스트하기 좋습니다.

## n8n과 Inngest, 결국 무엇을 선택해야 할까

이 프로젝트에서 n8n → Inngest로 전환하면서 둘의 용도가 명확히 나뉜다는 걸 알게 됐습니다.

| | n8n | Inngest |
|---|---|---|
| 코드 통합 | 어려움 (외부 서버) | 자연스러움 (같은 코드베이스) |
| 타입 안전성 | 없음 | 완전한 TypeScript |
| 인프라 | 별도 서버 필요 | 서버리스 (Vercel 등) |
| 동적 병렬 처리 | 제한적 | `step.run()` 으로 자유롭게 |
| 비개발자 접근성 | 높음 (GUI) | 낮음 (코드) |
| 프로토타이핑 속도 | 빠름 | 상대적으로 느림 |

**Inngest가 적합한 경우:**
- 기존 Next.js 코드베이스와 타입·로직을 공유해야 할 때
- 실패 재시도, step별 체크포인트가 중요한 프로덕션 워크플로우
- 런타임에 결정되는 동적 fan-out 패턴이 필요할 때
- AI API처럼 비용이 드는 외부 호출이 포함된 경우

**n8n이 여전히 나은 경우:**
- 개발자가 아닌 팀원도 워크플로우를 직접 수정해야 할 때
- Slack, Google Sheets, Notion 등 SaaS 연동이 주목적일 때
- 빠르게 아이디어를 검증하는 프로토타입 단계

n8n으로 흐름을 먼저 설계하고, 실제 프로덕션 구현은 Inngest로 옮기는 방식도 나쁘지 않습니다. 이번 작업이 그랬습니다.

---

## 정리

Inngest의 핵심 가치는 **"백그라운드 작업을 일반 TypeScript 코드로 작성하면서, 실패 재시도·체크포인트·대시보드를 공짜로 얻는다"** 는 것입니다.

`step.run()`으로 작업을 나누면 긴 파이프라인이 중간에 실패해도 처음부터 다시 시작하지 않아도 됩니다. AI API처럼 비용이 드는 호출이 포함된 경우에는 특히 중요합니다.

별도 서버 없이 Vercel 위에서 Cron + 이벤트 기반 자동화를 돌리고 싶다면 Inngest는 현재로서 가장 현실적인 선택입니다.
