## 에러 타입이 존재하는 이유

`throw`는 아무 값이나 던질 수 있습니다. 문자열도, 숫자도, 객체도 됩니다. 그런데 `catch (e)`는 하나뿐입니다. 던져진 값이 네트워크 실패인지, 코드 버그인지, 입력 검증 실패인지 구분할 방법이 필요했습니다.

에러 타입은 그 **분기 키**입니다. `instanceof`로 종류를 가르고, 처리할 수 있는 에러만 잡고 나머지는 다시 던지는 구조를 가능하게 합니다.

> 에러 타입은 분류 체계가 아니라 "누가 이 에러를 처리할 책임이 있는가"를 나누는 장치다.

## 내부 동작 방식

### 내장 에러는 엔진이 던진다

| 타입 | 엔진이 던지는 시점 | 성격 |
|------|-------------------|------|
| `TypeError` | `undefined.foo`, 함수가 아닌 값 호출, const 재할당 | 대부분 코드 버그 |
| `ReferenceError` | 선언되지 않은 식별자 접근, TDZ 위반 | 코드 버그 |
| `SyntaxError` | 파싱 실패, `JSON.parse`, `new RegExp` | 외부 입력일 수도 있음 |
| `RangeError` | `new Array(-1)`, 호출 스택 초과, `toFixed(101)` | 값의 범위 문제 |
| `URIError` | `decodeURIComponent('%')` | 잘못된 인코딩 |
| `EvalError` | 현재 엔진은 사실상 던지지 않음 | 역사적 잔재 |
| `AggregateError` | `Promise.any`가 전부 reject될 때 | 여러 에러의 묶음 |

핵심은 `SyntaxError`입니다. 소스 파싱 중에는 컴파일 시점에, `JSON.parse` 같은 런타임 호출에서는 **외부 입력 때문에** 발생합니다. 같은 타입이어도 의미가 다릅니다.

### stack은 "던질 때"가 아니라 "만들 때" 캡처된다

```js
function make() {
  return new Error("boom"); // stack은 여기서 캡처
}

const err = make();
function run() {
  throw err; // 던지는 위치는 stack에 반영되지 않는다
}
```

V8은 `Error` 생성자가 호출되는 순간 호출 스택을 기록합니다. 에러를 미리 만들어 재사용하면 stack이 엉뚱한 곳을 가리킵니다. 또한 stack 수집은 비용이 있어서, 에러를 흐름 제어용으로 대량 생성하면 성능에 영향을 줍니다. (`Error.stackTraceLimit`으로 깊이를 조절할 수 있습니다.)

`stack`은 표준이 아니라 엔진 확장으로 출발한 속성이라 포맷이 엔진마다 다릅니다. 파싱해서 로직에 쓰면 안 되는 이유입니다.

### message와 name은 프로토타입에서 온다

`Error.prototype.name`은 `"Error"`, 각 하위 타입이 자기 `name`을 가집니다. `toString()`은 `name: message`를 조합할 뿐입니다. 즉 `name`을 바꿔도 `instanceof`는 변하지 않습니다. 판별은 프로토타입 체인이 합니다.

## 실제로 언제 쓰는가

### 커스텀 에러로 "처리 책임"을 표현하기

```js
class HttpError extends Error {
  constructor(status, message, options) {
    super(message, options);
    this.name = "HttpError";
    this.status = status;
  }
}

try {
  await fetchReservation(id);
} catch (e) {
  if (e instanceof HttpError && e.status === 404) return null; // 내가 처리
  throw e; // 모르는 에러는 위로
}
```

OTA 예약 조회처럼 "없음(404)은 정상 흐름, 나머지는 장애"인 경우 타입과 필드로 분기하면 catch가 단순해집니다.

### cause로 원인 체인 보존하기

```js
try {
  JSON.parse(raw);
} catch (e) {
  throw new Error("결제 응답 파싱 실패", { cause: e });
}
```

ES2022의 `cause`는 래핑하면서도 원래 에러와 stack을 잃지 않게 합니다. 레이어를 넘길 때 메시지를 문자열로 이어붙이지 말고 `cause`로 연결하세요.

### Promise.any와 AggregateError

여러 결제/검색 공급자 중 하나라도 성공하면 되는 경우 `Promise.any`를 씁니다. 전부 실패하면 `AggregateError`의 `errors` 배열에 개별 실패가 들어옵니다.

## 흔한 오해와 함정

### 1. 문자열을 throw한다

```js
// Before
throw "실패";

// After
throw new Error("실패");
```

문자열에는 stack이 없고, `instanceof` 분기도 불가능합니다. 모니터링 도구도 제대로 수집하지 못합니다.

### 2. catch의 `e`는 항상 Error라고 가정한다

`throw`는 무엇이든 던질 수 있으므로 `e`는 원칙적으로 `unknown`입니다. TypeScript의 `useUnknownInCatchVariables`가 이를 반영합니다.

```ts
catch (e) {
  const err = e instanceof Error ? e : new Error(String(e));
}
```

### 3. instanceof가 실패하는 경우

iframe, 다른 realm, 중복 번들된 패키지에서 온 에러는 **다른 `Error` 생성자**를 가지므로 `instanceof`가 `false`가 됩니다. 라이브러리 경계에서는 `name`이나 `code` 필드 같은 구조적 판별을 함께 두는 편이 안전합니다.

### 4. 비동기 에러는 try/catch 밖으로 샌다

```js
try {
  setTimeout(() => { throw new Error("late"); });
} catch {} // 못 잡는다
```

콜백이 실행될 때는 이미 try 블록의 콜스택이 사라졌습니다. Promise는 `await`나 `.catch`로, 처리되지 않은 reject는 `unhandledrejection`으로 잡아야 합니다.

### 5. 커스텀 에러에서 name을 빼먹는다

`name`을 설정하지 않으면 로그에 전부 `Error`로 찍혀 구분이 안 됩니다. 필요하면 `this.name = new.target.name`으로 자동화할 수 있습니다. 다만 번들러 minify 시 클래스명이 바뀔 수 있어 문자열 상수를 권장합니다.

## 정리

JS 에러 타입의 핵심은 **"catch에서 내가 처리할 에러와 위로 올릴 에러를 구분하는 키"** 입니다.

엔진이 던지는 `TypeError`/`ReferenceError`는 대개 버그이므로 잡아서 삼키지 말고, 도메인 에러만 커스텀 타입으로 만들어 잡으세요. 레이어를 넘길 때는 `cause`로 원인을 이어 붙이는 것을 습관으로 삼는 것을 권합니다.
