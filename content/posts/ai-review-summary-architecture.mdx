## 기능 기획서가 왔을 때

기획서 한 줄이었습니다. "리뷰 AI 요약 기능 추가해주세요."

숙소 상세 페이지에는 많게는 수백 개의 리뷰가 달려 있습니다. 사용자가 예약을 결정하기 위해 그걸 전부 읽지는 않습니다. "이 숙소 조용한가요?", "가족 여행에 적합한가요?" 같은 질문에 빠르게 답을 얻고 싶어 합니다. AI가 리뷰를 요약해서 예약 의사결정을 돕는다는 방향은 명확했습니다.

문제는 구현 방법이었습니다. 브라우저에서 LLM API를 직접 호출하면 되지 않을까, 라고 처음엔 생각했습니다. 그런데 그 생각을 코드로 옮기기 전에 멈췄습니다. AI 기능은 일반 CRUD API와 다른 실패 패턴을 가집니다. 아키텍처를 먼저 설계하지 않으면 나중에 고치는 비용이 기하급수적으로 커집니다.

---

## 코드보다 아키텍처가 먼저인 이유

일반적인 API 호출은 실패해도 패턴이 예측 가능합니다. 네트워크 에러, 4xx, 5xx. 재시도하거나 에러 메시지 띄우면 됩니다.

AI 기능은 다릅니다.

- **응답이 느립니다.** LLM은 짧으면 2초, 길면 10초 이상 걸립니다. UI가 멈춘 것처럼 보입니다.
- **응답 형태가 보장되지 않습니다.** JSON을 달라고 했는데 마크다운으로 감싼 JSON이 오거나, 필드가 빠져 있을 수 있습니다.
- **비용이 발생합니다.** 잘못된 입력으로 LLM을 호출하면 돈이 나갑니다.
- **API key가 있습니다.** 클라이언트에 노출되면 안 됩니다.

이 네 가지를 코드를 짜다가 발견하면 전체를 뒤집어야 합니다. 그래서 설계를 먼저 했습니다.

## 전체 데이터 흐름

```
[사용자]
  |
  | 숙소 선택, 질문 입력 (선택)
  ↓
[ReviewSummaryPanel — 클라이언트 컴포넌트]
  |
  | 리뷰 데이터 선택 (최근 50개, 평점 3점 이상)
  | POST /api/ai/review-summary
  ↓
[Route Handler — 서버]
  |
  | Zod로 요청 검증 (hotelName, reviews, question)
  | 잘못된 입력 → 400 반환
  ↓
[LLM 호출 레이어]
  |
  | 프롬프트 구성 (시스템 + 유저 메시지)
  | OpenAI / Claude API 호출
  | 응답 schema 강제 (structured output)
  ↓
[응답 파싱 & 검증]
  |
  | Zod schema로 응답 형태 검증
  | parse 실패 → fallback 처리
  ↓
[클라이언트로 반환]
  |
  | { summary, pros, cons, recommendedFor,
  |   cautionPoints, evidenceReviewIds }
  ↓
[ReviewSummaryCard — UI 렌더링]
  |
  | 장점 카드, 단점 카드, 추천 대상 태그
  | 근거 리뷰 강조 표시
  ↓
[사용자 — 예약 의사결정]
```

이 흐름에서 중요한 건 각 단계의 **책임 경계**입니다.

---

## 각 레이어의 책임

### 클라이언트 컴포넌트

클라이언트는 두 가지 책임만 가집니다. 어떤 리뷰를 요약할지 선택하는 것, 그리고 결과를 UI로 보여주는 것입니다.

LLM을 어떻게 호출하는지는 모릅니다. API Route가 어떻게 생겼는지도 모릅니다. `/api/ai/review-summary`에 POST 요청을 보내고 응답을 받을 뿐입니다.

### Route Handler

Route Handler는 요청과 LLM 사이의 관문입니다. 요청이 유효한지 검증하고, LLM을 호출하고, 응답을 파싱해서 클라이언트에 반환합니다.

이 레이어가 있기 때문에 나중에 rate limit, logging, caching을 추가할 때 클라이언트 코드는 변경하지 않아도 됩니다.

### LLM 호출 레이어

프롬프트 구성과 실제 API 호출을 담당합니다. 어떤 LLM을 쓰는지 (OpenAI, Claude, Gemini)는 이 레이어만 알고 있습니다. 나중에 LLM provider를 바꿔도 Route Handler와 클라이언트는 영향받지 않습니다.

### 응답 파싱

LLM이 반환한 텍스트를 UI가 쓸 수 있는 구조로 변환합니다. Zod schema로 검증하고, 형태가 맞지 않으면 fallback 처리합니다.

---

## 왜 레이어를 이렇게 나눴나

처음엔 Route Handler 안에 모든 걸 넣으려 했습니다. 요청 검증, LLM 호출, 파싱을 한 파일에. 당장은 간단해 보였지만 문제가 생겼습니다.

테스트를 쓸 수 없었습니다. LLM 호출 코드가 Route Handler와 결합되어 있으면, LLM 로직을 단독으로 테스트하려면 Route Handler를 통째로 목(Mock) 처리해야 합니다.

레이어를 나누면 각 레이어를 독립적으로 테스트할 수 있습니다. LLM 호출 레이어는 프롬프트를 받아 구조화된 응답을 반환하는 함수일 뿐이고, 응답 파싱 레이어는 LLM 출력 문자열을 받아 Zod schema에 맞게 변환하는 함수입니다. 각각 단독으로 테스트가 됩니다.

```
app/
├── api/
│   └── ai/
│       └── review-summary/
│           └── route.ts          # Route Handler: 요청 검증, 조율
├── lib/
│   └── ai/
│       ├── review-summary.ts     # LLM 호출 & 프롬프트 구성
│       ├── schemas.ts            # 요청/응답 Zod schema
│       └── errors.ts             # AI 전용 에러 타입
└── components/
    └── review/
        ├── ReviewSummaryPanel.tsx  # 클라이언트: 호출, 상태 관리
        └── ReviewSummaryCard.tsx   # 클라이언트: 결과 렌더링
```

파일 구조도 레이어를 반영합니다. `api/`는 Route Handler, `lib/ai/`는 LLM 레이어, `components/review/`는 UI입니다.

## 리뷰 데이터 선택 전략

모든 리뷰를 LLM에 넘기면 두 가지 문제가 생깁니다. 토큰 비용이 늘어나고, LLM이 최근 경험이나 극단적인 리뷰에 집중하지 못합니다.

그래서 몇 가지 기준으로 리뷰를 선별했습니다.

```ts
// app/components/review/ReviewSummaryPanel.tsx

function selectReviewsForSummary(reviews: Review[]): Review[] {
  return reviews
    .filter((r) => r.rating >= 3)          // 극단적 부정 제외
    .sort((a, b) => new Date(b.createdAt).getTime() - new Date(a.createdAt).getTime())
    .slice(0, 50);                          // 최근 50개로 제한
}
```

50개 제한은 임의적이지 않습니다. GPT-4o 기준 리뷰 50개가 약 3,000~5,000 토큰입니다. 시스템 프롬프트와 응답 공간을 합쳐도 8k 컨텍스트 내에 들어오는 안전한 수치입니다.

평점 3점 미만 리뷰를 제외한 이유는 요약의 목적 때문입니다. 이 기능은 사용자가 예약을 결정하는 데 도움을 주는 것이지, 악성 리뷰를 분석하는 도구가 아닙니다. 단, pros/cons를 모두 보여줘야 하므로 3점 이상에서도 부정적 내용은 충분히 나옵니다.

## 정리

AI 기능을 붙일 때 "일단 호출하고 나중에 정리하자"는 생각이 가장 비쌉니다. API key 노출, 비용 통제 불가, 테스트 불가능한 코드로 이어집니다.

레이어를 나누는 원칙은 단순합니다. **각 레이어는 하나의 책임만 갖고, 인접한 레이어하고만 대화합니다.** 클라이언트는 Route Handler만 알고, Route Handler는 LLM 레이어만 알고, LLM 레이어는 provider API만 알고 있습니다.

이 구조를 세우고 나면, 이후 포스팅에서 다룰 요청 검증, structured output 설계, 에러 처리, UI 구현 모두 자연스럽게 각자의 자리를 찾게 됩니다.
