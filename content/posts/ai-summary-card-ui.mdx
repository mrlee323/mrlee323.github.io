## 먼저 결론

structured output이 있으면 AI 결과를 "읽는 UI"가 아니라 "스캔하는 UI"로 만들 수 있다. 이게 핵심이다. 나머지 결정은 전부 이 한 줄에서 파생된다.

---

## 컴포넌트를 어떻게 나눌 것인가

처음엔 `ReviewSummaryCard` 하나에 다 때려박았다. 그러다 LLM 스키마를 한 필드만 바꿨을 때 카드 전체가 흔들리는 걸 보고 나눴다.

분해 기준은 단순하다. **무엇이 변하고 무엇이 안 변하는가**.

- 장점/단점의 시각적 표현 방식 → 바뀔 수 있다 (아이콘, 색상, 레이아웃)
- 추천 대상 태그의 렌더링 → 바뀔 수 있다
- 근거 리뷰를 보여줄지 여부 → 제품 판단에 따라 바뀐다
- 상태 관리(loading/error/success) → 변경 이유가 다르다

변경 이유가 다르면 다른 컴포넌트다. SRP를 "단일 책임"이 아니라 "단일 변경 이유"로 읽으면 분해 기준이 명확해진다.

```
ReviewSummaryPanel          ← 상태 관리, LLM 호출
├── ReviewSummaryCard       ← 결과 렌더링 (순수)
│   ├── SummaryText
│   ├── ProsConsList
│   ├── RecommendedForTags
│   ├── CautionPointsList
│   └── EvidenceReviews
└── ReviewSummarySkeleton
```

`ReviewSummaryCard`는 `ReviewSummaryResponse` 타입을 그대로 받는다. LLM이 어떻게 호출됐는지, 에러가 났는지 모른다. 이걸 지키는 게 나중에 테스트를 쉽게 만든다.

---

## structured output이 있을 때 UI 설계가 어떻게 달라지는가

없을 때와 비교하면 차이가 크다.

structured output 없이 LLM 응답이 긴 텍스트 하나라면, UI는 그걸 그대로 보여주는 것밖에 못 한다. 마크다운 파싱 정도가 전부다. 데이터의 구조가 없으니 구조적인 표현도 없다.

structured output이 있으면 응답이 타입이 된다.

```typescript
interface ReviewSummaryResponse {
  summary: string;
  pros: string[];
  cons: string[];
  recommendedFor: string[];
  cautionPoints: string[];
  evidenceReviewIds: string[];
}
```

`pros: string[]`이면 리스트로 렌더링한다. `recommendedFor: string[]`이면 태그로 뿌린다. 배열의 의미가 스키마에 담겨 있으니 UI에서 의미를 해석할 필요가 없다.

설계 순서도 달라진다. 스키마 먼저, UI 나중이다. 스키마가 확정되지 않은 상태에서 UI를 짜면 나중에 다 엎는다.

---

## 상태 관리: boolean 두 개 vs 단일 status

처음에 `isLoading`, `isError` 두 개로 짰다. 코드 리뷰에서 지적받기 전까지 문제를 못 느꼈다.

`isLoading && isError`는 불가능한 조합인데, 타입이 그걸 막아주지 않는다. 런타임에서 어떤 분기가 실행될지 코드를 읽으면서 머릿속으로 계산해야 한다.

```typescript
// Before: 불가능한 조합이 타입상 존재
isLoading: boolean;
isError: boolean;

// After: 가능한 상태만 존재
status: "idle" | "loading" | "success" | "error";
```

단일 `status` 필드로 바꾸면 컴포넌트 분기가 exhaustive해진다. 새 상태가 추가되면 컴파일 타임에 잡힌다.

---

## LLM 응답이 스키마와 맞지 않을 때

structured output을 쓴다고 해서 항상 스키마를 완벽히 따르는 건 아니다. 모델에 따라, 프롬프트에 따라 `pros`가 `null`로 오거나 배열이 아닌 문자열로 올 수 있다.

이걸 UI에서 그냥 렌더링하면 깨진다.

```typescript
// pros가 null이면 .map()에서 터진다
{data.pros.map((item) => <li>{item}</li>)}
```

두 가지 선택지가 있다.

1. API 레이어에서 방어: 응답을 파싱할 때 `zod`로 검증하고, 실패하면 에러 처리
2. 컴포넌트에서 방어: 렌더링 전에 `Array.isArray(data.pros) ? data.pros : []`

나는 API 레이어에서 막는 쪽을 택했다. 컴포넌트에서 스키마 불일치를 흡수하기 시작하면 어디서 무슨 일이 일어나는지 추적이 어려워진다. 파싱 실패는 에러로 올라오게 하고, 컴포넌트는 타입을 믿는다.

---

## 빈 배열 처리 — 레이아웃이 깨지는 지점

`cons`가 빈 배열이면 어떻게 렌더링할 것인가. 아무것도 안 보여주면 2열 그리드에서 `pros` 칸만 남는다.

```tsx
// 이렇게 하면 pros만 전체 너비를 차지하거나,
// 아니면 빈 칸이 생겨서 레이아웃이 어색해진다
{data.cons.length > 0 && <ProsConsList type="cons" items={data.cons} />}
```

LLM이 단점 없는 숙소를 분석했을 때 실제로 이 문제가 생겼다. `cons`가 비어서 `pros`만 렌더링됐고, 2열로 설계된 레이아웃이 1열처럼 보였다.

해결 방향도 두 가지다. 빈 상태를 보여줄 것인가, 레이아웃을 조건부로 바꿀 것인가.

빈 상태를 보여주기로 했다. 단점 없는 숙소라는 정보 자체가 의미 있고, 빈 칸이 있으면 사용자가 "로딩 안 됐나?" 하고 혼동한다.

```tsx
if (items.length === 0) {
  return (
    <div className={`rounded-lg p-4 ${containerClass}`}>
      <p className={`text-sm font-semibold mb-2 ${labelClass}`}>{label}</p>
      <p className="text-sm text-gray-400">
        {type === "cons" ? "특별한 단점이 언급되지 않았습니다." : "장점 정보 없음"}
      </p>
    </div>
  );
}
```

`cons`와 `pros`가 빈 상태일 때 메시지를 다르게 쓴 것도 의도적이다. 단점 없음은 긍정적인 신호이고, 장점 없음은 분석 실패에 가깝다.

## 근거 리뷰 표시 — UX 결정이 아니라 제품 결정

`EvidenceReviews`를 넣을지 말지는 UX 고민이 아니었다. AI가 생성한 결과를 사용자가 신뢰할 것인가의 문제다.

예약 결정은 돈이 오가는 행위다. "AI가 이걸 지어낸 건 아닌가"라는 의심이 생기면 결국 원본 리뷰를 하나하나 읽는다. 그러면 AI 요약의 존재 이유가 없어진다.

근거 리뷰를 붙이면 세 가지가 해결된다.

1. "이 요약이 실제 리뷰에서 나왔다"는 확인
2. 사용자가 더 깊이 보고 싶을 때의 진입점
3. AI 환각이 있으면 근거 리뷰를 보고 사용자가 직접 확인 가능

처음엔 5개를 보여줬는데 3개로 줄였다. 5개부터는 "리뷰 목록이 또 있네"처럼 읽힌다. 근거를 보여주는 게 목적이지, 리뷰 목록을 대체하는 게 아니다.

```tsx
{reviews.slice(0, 3).map((review) => (
  <div key={review.id} className="border-l-2 border-blue-200 pl-3 py-1">
    <p className="line-clamp-2 text-sm text-gray-600">{review.content}</p>
  </div>
))}
```

`line-clamp-2`로 자른 것도 같은 이유다. 전체 리뷰를 여기서 읽게 하는 게 아니라, "근거가 있다"는 신호를 주는 것이다.

## Skeleton: 모양이 결과와 같아야 하는 이유

Skeleton의 레이아웃이 실제 결과 레이아웃과 다르면 로딩 완료 시 레이아웃 시프트가 생긴다. 사용자 입장에선 콘텐츠가 "갑자기 달라지는" 경험이다.

2열 그리드 skeleton이 실제 `ProsConsList`의 2열에 대응하고, 태그 모양 skeleton이 실제 `RecommendedForTags`에 대응한다. 이걸 유지하는 건 디자인 완성도 문제가 아니라 인지 부하 문제다.

Skeleton을 별도 컴포넌트로 분리한 이유도 있다. 처음엔 `ReviewSummaryPanel` 안에 인라인으로 박았는데, 실제 Card 레이아웃이 바뀔 때마다 Skeleton도 수동으로 맞춰야 했다. 분리하면 Card 레이아웃 변경과 Skeleton 변경이 같은 PR에서 묶인다.

## 처음 설계와 달라진 것들

- `ReviewSummaryCard`에 `status` prop을 넘겼다가 삭제했다. Card는 성공 상태의 결과만 알면 된다. 상태 분기는 Panel 몫이다.
- 태그 컴포넌트를 `SummaryText` 안에 넣었다가 꺼냈다. 추천 대상 태그가 요약 텍스트와 다른 이유로 바뀐다는 걸 나중에 깨달았다.
- 에러 컴포넌트를 별도로 만들려다 Panel 인라인으로 뒀다. 에러 UI가 현재 프로젝트에서 재사용되는 경우가 없다. 추상화는 재사용이 확인될 때 한다.
- `evidenceReviewIds`를 Card에서 필터링했다가 Panel로 올렸다. Card가 `allReviews` 배열 전체를 받는 게 부자연스러웠다. Panel이 미리 필터링해서 넘기는 게 더 명확하다.

## 남은 문제

streaming response를 쓰면 structured output을 그대로 쓸 수 없다. 응답이 부분적으로 오는 동안 JSON이 incomplete하기 때문에 파싱이 불가능하다. 이 경우 필드별로 streaming을 제어하거나, 전체 응답을 받은 뒤 파싱하거나, tool call 방식으로 우회해야 한다.

현재는 전체 응답 후 파싱 방식이다. LLM 응답이 5초를 넘으면 streaming을 도입하는 게 낫다고 생각하지만, 아직 그 임계점에 도달하지 않았다.
