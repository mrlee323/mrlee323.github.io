## 가비지 컬렉션이 존재하는 이유

C에서는 `malloc`과 `free`를 개발자가 직접 짝지어야 합니다. 해제를 빼먹으면 누수, 너무 일찍 하면 dangling pointer입니다. 자바스크립트는 이 부담을 엔진에 넘겼습니다. 객체를 만드는 시점은 코드에 보이지만, **언제 더 이상 필요 없는지**는 프로그램 전체 흐름을 알아야 알 수 있기 때문입니다.

문제는 "필요 없음"을 엔진이 정확히 알 수 없다는 점입니다. 그래서 엔진은 근사치를 씁니다.

> "앞으로 이 객체에 접근할 방법이 남아 있는가?"

이 질문의 답이 **도달 가능성(reachability)** 입니다. 쓸지 안 쓸지가 아니라, 쓸 수 있는 경로가 있는지만 봅니다. 이 차이가 메모리 누수를 이해하는 출발점입니다.

## 내부 동작 방식

### 도달 가능성과 Mark-and-Sweep

과거에는 참조 카운팅(참조 수가 0이면 해제)을 썼습니다. 하지만 순환 참조를 처리하지 못합니다.

```js
function leak() {
  const a = {};
  const b = { a };
  a.b = b; // 서로를 참조: 카운트가 0이 되지 않음
}
```

현대 엔진은 모두 **Mark-and-Sweep** 계열입니다.

```
[Roots]  전역 객체, 현재 호출 스택의 지역 변수, 레지스터
   │
   ├─ 1. Mark  : 루트에서 참조를 따라가며 도달 가능한 객체에 표시
   └─ 2. Sweep : 표시되지 않은 객체의 메모리를 회수
```

위 `leak()`의 `a`, `b`는 함수가 끝나면 루트에서 닿지 않으므로 서로 참조하더라도 회수됩니다. 순환 참조는 문제가 아닙니다.

### V8의 세대별 GC

V8은 "대부분의 객체는 금방 죽는다"는 관찰(generational hypothesis)에 맞춰 힙을 나눕니다.

| | Young generation | Old generation |
|---|---|---|
| 대상 | 방금 만든 객체 | 살아남은 객체 |
| 알고리즘 | Scavenger (복사) | Mark-Sweep-Compact |
| 비용 | 작고 빠름 (수 ms 이하) | 큼, 증분/동시 처리 필요 |
| 빈도 | 자주 | 드물게 |

Young 영역은 두 개의 semi-space로 나뉘고, 살아있는 객체만 반대편으로 **복사**합니다. 죽은 객체는 건드리지 않으니 비용이 살아있는 객체 수에 비례합니다. 두 번 살아남으면 Old로 승격됩니다.

Old 영역의 Major GC는 힙 전체를 훑기 때문에 비쌉니다. 그래서 V8은 작업을 잘게 쪼개 실행하고(incremental), 별도 스레드에서 병렬로 처리하며(concurrent/parallel), 메인 스레드를 멈추는 구간(stop-the-world)을 최소화합니다. 그래도 완전히 0은 아닙니다. 할당이 폭주하면 프레임이 끊기는 이유입니다.

한 가지 더, **GC 시점은 개발자가 제어할 수 없습니다.** `null`을 대입해도 즉시 해제되지 않고, 다음 GC 사이클에서 회수 대상이 될 뿐입니다.

## 실제로 언제 신경 쓰는가

대부분의 코드에서는 신경 쓸 필요가 없습니다. 다음 상황에서 의식합니다.

- **오래 떠 있는 페이지**: SPA에서 라우트를 수백 번 오가는 OTA 예약 플로우처럼 새로고침 없이 오래 쓰이는 화면
- **Node.js 서버 프로세스**: 요청마다 조금씩 쌓이는 누수는 몇 시간 뒤 OOM으로 나타남
- **대용량 데이터를 다루는 화면**: 검색 결과 수천 건을 매번 새 배열로 만드는 경우

진단은 Chrome DevTools의 Memory 탭에서 합니다. 동작 전후로 **Heap snapshot**을 찍어 비교하고, 해제되어야 할 객체가 남아 있다면 **Retainers** 경로를 봅니다. 이 객체를 붙잡고 있는 루트까지의 경로가 곧 누수의 원인입니다.

## 흔한 오해와 함정

누수의 정체는 대부분 **"쓰지 않지만 도달은 가능한 객체"** 입니다.

### 1. 해제되지 않는 이벤트 리스너와 타이머

```js
// 수정 전
function mountWidget() {
  const data = loadHugeList();
  window.addEventListener("resize", () => render(data));
  setInterval(() => poll(data), 1000);
}

// 수정 후
function mountWidget() {
  const data = loadHugeList();
  const onResize = () => render(data);
  window.addEventListener("resize", onResize);
  const id = setInterval(() => poll(data), 1000);

  return () => {
    window.removeEventListener("resize", onResize);
    clearInterval(id);
  };
}
```

`window`와 타이머는 루트에 가깝습니다. 거기 등록된 콜백은 클로저로 `data`를 붙잡고 있으므로, 컴포넌트가 사라져도 `data`는 살아 있습니다. React의 `useEffect` cleanup이 필요한 근본 이유입니다.

### 2. 클로저가 필요 이상으로 붙잡는 스코프

같은 스코프를 공유하는 클로저가 하나라도 살아 있으면, V8은 그 스코프에서 **다른 클로저가 쓰는 변수**를 함께 유지할 수 있습니다.

```js
function setup() {
  const big = new Array(1e6).fill("x");
  const small = () => big.length; // big 사용
  return () => small;             // 직접 쓰진 않지만 같은 컨텍스트
}
```

반환된 함수가 `big`을 직접 쓰지 않아도 컨텍스트가 공유되면 `big`이 남을 수 있습니다. 엔진 최적화에 따라 달라지므로 "큰 데이터는 클로저 바깥에서 끊는다"를 원칙으로 삼는 편이 안전합니다.

### 3. 분리된 DOM 노드(Detached DOM)

```js
const cache = new Map();
function onItemClick(el) {
  cache.set(el.id, el); // DOM 노드 자체를 저장
}
// el이 문서에서 제거돼도 cache가 붙잡고 있어 해제되지 않음
```

화면에서 사라진 노드를 JS 변수가 쥐고 있으면 노드와 그 하위 트리 전체가 남습니다. DevTools에서 `Detached` 로 검색하면 찾을 수 있습니다.

### 4. 무한히 커지는 캐시

모듈 스코프의 `Map`이나 객체는 앱이 살아 있는 동안 루트에서 도달됩니다. 키가 객체라면 `WeakMap`, 크기 제한이 필요하면 LRU로 상한을 두어야 합니다.

### 5. "null 대입하면 해제된다"

변수에 `null`을 대입하는 건 참조를 끊는 행위일 뿐입니다. 다른 곳에 참조가 남아 있으면 의미가 없고, 지역 변수는 어차피 스코프가 끝나면 사라집니다. `null` 대입이 의미 있는 경우는 **오래 사는 객체의 필드**를 비울 때입니다.

## 정리

가비지 컬렉션의 핵심은 **"쓰는가"가 아니라 "도달할 수 있는가"** 입니다. 메모리 누수는 GC 버그가 아니라, 내가 의도치 않게 남겨둔 참조 경로입니다.

장시간 실행되는 화면이나 서버에서는 리스너·타이머·캐시·DOM 참조 네 가지를 먼저 의심하세요. 의심이 들면 추측하지 말고 Heap snapshot의 Retainers 경로를 직접 확인하는 것이 가장 빠릅니다.
