## 코드보다 오래 걸리는 일

우리 서비스는 레포가 9개다.

```
서비스 프론트
iOS / AOS
서버 — service / payment / account / push
어드민 프론트 / 어드민 서버
```

기획에서 요구사항 하나가 내려온다. "예약 취소 시 환불 정책을 단계별로 안내해달라."

코드를 짜는 시간은 길지 않다. 오래 걸리는 건 **어디를 고쳐야 하는지 파악하는 시간**이다. 프론트에서 안내 UI를 그린다. 정책 데이터는 service 서버인지 payment 서버인지 확인해야 한다. 앱에도 같은 화면이 있으니 iOS/AOS도 대상이다. 어드민에서 정책을 편집해야 하면 어드민 프론트와 서버도 붙는다.

이걸 파악하려면 각 레포를 열어보고, 담당자에게 묻고, 슬랙 히스토리를 뒤진다. 실제 개발보다 이 단계가 길다. 그리고 이 파악을 잘못하면 배포 직전에 "앱은요?"가 나온다.

이 문제를 개인 역량이 아니라 시스템으로 풀고 싶었다.

---

## 1단계: 레포를 한 자리에 모으고 지도를 그렸다

가장 먼저 한 건 단순하다. 9개 레포를 `dev/` 하위에 전부 클론했다.

```
dev/
├── INDEX.md          ← 이게 핵심
├── service-web/
├── service-ios/
├── service-aos/
├── server-service/
├── server-payment/
├── server-account/
├── server-push/
├── admin-web/
└── admin-server/
```

`INDEX.md`가 핵심이다. 각 프로젝트가 무엇을 담당하고, 어떤 도메인이 어디에 있고, 어떤 프로젝트끼리 엮이는지를 적어뒀다.

```markdown
## server-payment
결제, 환불, 정산. 환불 **정책 데이터**의 소유자.
- 엮임: service-web(환불 안내 UI), admin-server(정책 편집)
- 주의: 환불 금액 계산 로직은 여기에만 존재. 프론트에서 재계산 금지.

## server-account
회원, 인증, 권한. 로그인 토큰 발급.
- 엮임: 전 프로젝트 (인증 헤더)
```

이 파일 하나로 "환불 정책은 payment 서버"라는 판단이 검색 한 번에 끝난다. 사람이 읽어도 유용하고, AI가 읽으면 대상 프로젝트를 스스로 찾는다.

**이 문서를 쓰는 게 가장 어려웠다.** 머릿속에만 있던 프로젝트 간 관계를 글로 옮겨야 했는데, 쓰다 보니 내가 모르는 부분이 드러났다. push 서버가 account 서버의 토큰을 어떻게 쓰는지 정확히 몰랐다. 서버 개발자에게 물어서 채웠다.

시스템을 만드는 과정 자체가 도메인 파악이었다.

---

## 2단계: 요구사항 분해를 프로세스로 고정했다

기획에서 오는 티켓과 개발이 쓰는 티켓은 성격이 다르다. 그래서 분해 규칙을 정했다.

```
[기획] Task 티켓          "환불 정책 단계별 안내"
        ↓ 복제
[개발] Tech 티켓          기술 관점의 요구사항 정리
        ↓ 분해
        ├── service-web    안내 UI + 정책 조회 연동
        ├── server-payment  정책 조회 API 추가
        ├── service-ios     동일 화면 대응
        ├── service-aos     동일 화면 대응
        └── admin-web       정책 편집 화면
```

Task는 "무엇을 원하는가"고, Tech는 "무엇을 만들 것인가"다. 이 둘을 분리하지 않으면 기획 티켓에 기술 논의가 쌓여서 나중에 아무도 못 읽는다.

프로젝트별 하위 티켓에는 두 가지를 반드시 적는다. **요구사항**(기획이 원하는 것)과 **개발사항**(이 프로젝트에서 실제로 할 일). 앱 개발자가 자기 티켓만 봐도 맥락을 알 수 있어야 한다.

이 분해 규칙을 스킬로 만들었다. 티켓 URL을 주면 `INDEX.md`를 참고해 대상 프로젝트를 찾고, Tech 티켓과 하위 티켓을 이 형식으로 생성한다.

---

## 3단계: 내가 판단 못 하는 것은 사람에게 넘긴다

여기가 이 시스템에서 제일 중요한 부분이다.

나는 프론트엔드 개발자다. 서버의 트랜잭션 경계나 앱의 배포 주기를 정확히 판단할 수 없다. 그런데 티켓은 내가 분해한다. 그러면 내가 틀린 채로 티켓이 만들어진다.

그래서 스킬에 규칙을 넣었다. **확신이 없는 영역은 결정하지 말고 해당 담당자에게 확인 요청을 남긴다.**

- 앱 관련 판단 → iOS/AOS 개발자에게 티켓 확인 요청
- 서버 스펙 판단 → 서버 개발자에게 확인 요청
- 확인이 필요한 지점은 티켓 코멘트로 명시

```
@서버개발자 환불 정책 조회 API 관련 확인 부탁드립니다.
- 정책 데이터가 payment 서버 소유가 맞을까요? service 쪽에도 유사 테이블이 보입니다.
- 단계별 정책이면 응답이 배열 형태가 될 텐데, 기존 /refund-policy 를 확장할지 신규 엔드포인트를 낼지 의견 주세요.
```

자동화의 목표는 사람을 빼는 게 아니다. **사람이 판단해야 하는 지점을 정확히 찾아내는 것**이다. 애매한 걸 혼자 결정하고 넘어가면 나중에 더 큰 비용으로 돌아온다.

## 4단계: 워크트리로 병렬 격리

대상 프로젝트가 정해지면 각각 브랜치를 만든다. 브랜치명은 지라 티켓 번호를 쓴다. 티켓과 브랜치가 1:1로 붙으면 나중에 "이 브랜치 뭐였지"가 없다.

병렬로 작업하려면 **워크트리가 필수다.** 같은 레포에서 브랜치를 왔다갔다 하면서 동시 작업은 불가능하다. 워크트리는 브랜치별로 독립된 디렉토리를 만들어준다.

```bash
git worktree add ../service-web-PROJ-1234 -b feature/PROJ-1234
```

프로젝트별로 워크트리를 만들면 각 작업이 독립적으로 돌아간다. 파일 충돌이 구조적으로 불가능해진다. 이게 병렬 실행의 전제 조건이다. 워크트리 없이 서브에이전트를 여러 개 띄우면 같은 파일을 동시에 건드리다가 깨진다.

지금은 [Orca](https://www.onorca.dev/)를 쓴다. 에이전트마다 워크트리를 격리해주는 개발 환경이라 이 부분을 직접 관리하지 않아도 된다. 다만 도구를 쓰기 전에 왜 워크트리여야 하는지는 알고 쓰는 게 낫다. 안 그러면 병렬 실행이 왜 깨지는지 이해 못 한 채로 도구를 의심하게 된다.

실무적으로 걸리는 것도 있다. 워크트리는 `.git`만 공유하고 나머지는 새 디렉토리다. `node_modules`가 없고 `.env.local`이 없다. 워크트리 생성 후 의존성 설치와 환경 파일 복사를 자동화해두지 않으면 매번 손이 간다.

## 예상과 달랐던 것: 병렬이 더 정확했다

병렬로 여러 레포를 동시에 건드리면 더 위험할 거라고 생각했다. 실제로는 반대였다.

**순차로 작업할 때 오히려 스펙이 어긋난다.** 월요일에 프론트에서 API 응답 형태를 가정하고 짠다. 목요일에 서버를 짜면서 그 가정을 잊는다. 필드명이 `refundSteps`인지 `steps`인지 어긋난다. 통합 테스트에서 발견한다.

동시에 작업하면 이게 안 생긴다. 프론트가 기대하는 응답과 서버가 만드는 응답이 같은 맥락 안에 있기 때문이다. 인터페이스 불일치가 발생할 여지 자체가 줄어든다.

이건 AI가 똑똑해서가 아니다. **프로젝트 간 관계가 한 컨텍스트에 들어와 있기 때문**이다. 사람이 여러 레포를 동시에 열어놓고 작업해도 같은 효과가 있다. 다만 사람은 9개 레포를 동시에 머릿속에 올리기 어렵다.

멀티 레포 환경의 진짜 문제는 각 레포의 난이도가 아니라 **레포 사이의 맥락 단절**이었다. 병렬 실행은 속도를 위한 선택이었는데, 결과적으로 정확도를 얻었다.

---

## 5단계: 리뷰 — 승인이 아니라 이해를 위한

작업이 끝나면 브랜치별 변경사항을 검토한다. 레포가 9개인데 IDE를 9개 띄우는 건 현실적이지 않다. 워크트리별 diff를 한 화면에서 보고, 궁금한 라인에 바로 코멘트를 달면 그게 해당 에이전트에게 전달돼서 수정으로 이어진다.

여기서 내 역할이 바뀌었다. 코드를 **작성하는 사람**에서 **검증하는 사람**으로.

검토할 때 보는 기준은 하나다. **내가 이 변경을 설명할 수 있는가.**

- 왜 이 파일을 고쳤는지 설명할 수 있는가
- 왜 이 방식을 택했는지 설명할 수 있는가
- 이 변경이 다른 레포에 어떤 영향을 주는지 아는가

설명이 안 되는 부분은 넘어가지 않는다. 물어보고, 이유를 확인하고, 납득이 안 되면 다시 수정한다. 동작하는 코드와 내가 이해하는 코드는 다르다. 이해 못 한 코드를 머지하면 6개월 뒤 아무도 못 고치는 코드가 된다.

이 단계는 자동화하지 않았다. **자동화하면 안 되는 지점**이라고 생각한다. 실행을 위임하는 것과 판단을 위임하는 것은 다르다.

---

## 6단계: 배포 게이트

검토가 끝나면 커밋하고 `dev`에 머지한다. 배포 후 검증 리스트를 브라우저에서 확인하고, `stage`에서 다시 테스트한다.

상용 배포가 이 시스템에서 가장 보수적인 부분이다.

```
상용 배포 브랜치에 포함될 수 있는 조건
├── dev 머지 완료
├── stage 머지 완료
└── 지라 티켓에 테스트 완료 코멘트 존재
```

세 조건을 다 만족한 브랜치만 상용 배포 브랜치에 머지된다. 배포 티켓을 만들 때 대상 브랜치들을 이 기준으로 검증한다.

배포 프로세스도 스킬로 만들었다.

1. 배포 브랜치 생성
2. 검증 통과한 작업 브랜치들만 머지
3. MR 생성
4. 배포 계획서 작성
5. 슬랙에 배포 내용 공유

배포 계획서와 슬랙 공유를 자동화 범위에 넣은 이유가 있다. 이건 개발이 아니라 **커뮤니케이션**인데, 바쁘면 제일 먼저 생략되는 일이다. 그러다 "이번에 뭐 나갔어요?"가 나온다. 프로세스에 넣으면 빠지지 않는다.

---

## 이 시스템이 못하는 것

**도메인 히스토리를 모른다.** 이 결제 로직이 왜 이렇게 복잡한지, 3년 전 어떤 장애 때문에 이 방어 코드가 들어갔는지는 문서에 없다. 이건 여전히 사람이 알아야 한다.

**조직의 정치적 맥락을 모른다.** 이 API를 바꾸면 어느 팀이 곤란해지는지, 지금 그 팀이 다른 급한 일을 하고 있는지는 판단 대상이 아니다.

**"이걸 지금 해야 하는가"를 못 묻는다.** 요구사항이 오면 어떻게 만들지는 계획하지만, 이 요구사항 자체가 타당한지는 묻지 않는다. 그건 내가 해야 한다.

세 가지 모두 결국 **판단**의 영역이다. 자동화로 실행이 빨라진 만큼, 판단에 쓸 시간이 늘었다. 그게 이 시스템을 만든 실제 이유다.

---

## 정리

이 시스템에서 AI가 한 일은 실행이다. 내가 한 일은 설계다.

- 프로젝트 간 관계를 문서로 만든 것 (`INDEX.md`)
- 요구사항 분해 규칙을 정한 것 (Task/Tech 분리, 프로젝트별 티켓)
- 판단 못 하는 지점을 사람에게 넘기도록 정한 것
- 병렬 실행이 안전하도록 격리한 것 (워크트리)
- 상용 배포 조건을 고정한 것 (dev + stage + 테스트 완료)

도구는 바뀐다. 지금 쓰는 것들이 1년 뒤에도 같을 거라고 생각하지 않는다. 하지만 위 다섯 가지는 도구가 바뀌어도 남는다. 그게 설계와 사용의 차이다.

멀티 레포 환경에서 일하고 있다면, 자동화 도구를 붙이기 전에 `INDEX.md`부터 써보길 권한다. 그거 하나만 해도 절반은 온 거다.
