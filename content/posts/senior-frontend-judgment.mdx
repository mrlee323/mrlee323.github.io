## 코드 리뷰에서 뭘 봐야 하는가

2년차 때 코드 리뷰는 주로 이런 것들이었다.

- `let` 대신 `const` 쓰면 좋겠다
- 변수명이 명확하지 않다
- 이 함수가 너무 길다

틀린 말은 아닌데, 지금 돌아보면 표면만 보고 있었다. 코드가 어떻게 변경되는지, 이 변경이 다른 부분에 어떤 영향을 미치는지를 못 봤다.

지금 리뷰에서 가장 먼저 보는 건 **무엇이 변하고 있는가**다.

---

## 타입 변경은 가장 넓은 파급범위를 갖는다

```typescript
// Before
interface User {
  id: string;
  name: string;
}

// After
interface User {
  id: string;
  name: string;
  role: "admin" | "user"; // 추가
}
```

이런 PR이 오면 물어본다: `role`이 optional인지 required인지, 기존 데이터에는 이 필드가 있는지.

`role`이 required인데 DB에 이 컬럼이 없으면 런타임 에러다. `role`이 없는 기존 응답을 받는 코드가 이미 있다면 타입 에러보다 조용한 버그가 생긴다.

타입 변경 PR에서 항상 확인하는 것들:

1. 이 타입을 쓰는 모든 곳을 변경했는가
2. 기존 데이터(DB, localStorage, API 응답)와 호환되는가
3. optional → required 변경이라면 migration은 어떻게 하는가

## 컴포넌트에 prop이 추가될 때

```tsx
// Before
function PropertyCard({ property }: { property: Property }) {
  return <div>{property.name}</div>;
}

// After
function PropertyCard({
  property,
  variant = "default",
}: {
  property: Property;
  variant?: "default" | "compact";
}) {
  return (
    <div className={variant === "compact" ? "text-sm" : "text-base"}>
      {property.name}
    </div>
  );
}
```

`variant`가 optional이고 기본값이 있으니 기존 사용처는 영향이 없다. 괜찮아 보인다.

근데 실제로 확인하고 싶은 건 다른 것이다. **이 컴포넌트가 몇 군데서 쓰이고 있는가.** 30군데에서 쓰인다면 나중에 `variant="compact"`가 필요해지는 곳이 생기면 30군데에 prop을 추가해야 한다. 이미 복잡한 컴포넌트에 분기가 쌓이는 게 시작되는 지점이다.

지금은 괜찮은데 나중에 문제가 될 설계라면 리뷰에서 그 방향을 언급하는 게 맞다. 지금 당장 바꾸라는 게 아니라 이 방향을 알고 가는 게 낫다는 것.

## useEffect 를 볼 때

```typescript
useEffect(() => {
  fetchUserData(userId);
}, [userId]);
```

이걸 보면 두 가지를 본다.

**첫째, 클린업이 없는가.** `fetchUserData`가 비동기라면 컴포넌트가 언마운트된 후에 응답이 오면 상태 업데이트가 일어난다. React 18 이전이면 메모리 누수 경고가 뜨고, 이후에도 stale 업데이트가 생길 수 있다.

```typescript
useEffect(() => {
  let cancelled = false;

  fetchUserData(userId).then((data) => {
    if (!cancelled) setUser(data);
  });

  return () => { cancelled = true; };
}, [userId]);
```

**둘째, 이게 정말 effect인가.** 서버 컴포넌트나 React Query로 처리할 수 있는 데이터 페칭을 클라이언트 effect로 하고 있다면 더 나은 방법이 있다. 근데 이미 클라이언트 컴포넌트에서 작업 중이고 범위가 크다면 지금 PR에서 바꾸지 않고 TODO로 남기는 게 맞을 때도 있다.

## 리뷰에서 묻는 질문들

좋은 코드 리뷰 코멘트는 "이렇게 바꾸세요"보다 질문인 경우가 많다.

- "이 로직이 동시에 두 번 호출되면 어떻게 되나요?"
- "`null`이 올 수 있는 경우는 없나요?"
- "에러가 났을 때 사용자는 어떤 화면을 보나요?"
- "이 캐시는 언제 무효화되나요?"

질문 형식으로 쓰면 상대방이 방어적으로 반응하지 않는다. 그리고 실제로 내가 놓친 맥락이 있을 수 있다. 질문이 아니라 단언으로 쓰면 내가 틀렸을 때 대화가 불필요하게 어색해진다.

---

## 승인과 머지를 결정하는 기준

모든 코멘트를 다 반영해야 머지하는 건 아니다.

**블로킹 이슈** — 런타임 에러 가능성, 보안 문제, 성능 회귀, 데이터 손실 위험. 이건 반드시 수정하고 넘어간다.

**개선 제안** — 더 나은 방법이 있지만 지금도 동작하는 것들. 별도 이슈나 TODO로 남기고 머지할 수 있다.

**취향 차이** — 변수명, 주석 스타일, 코드 정렬. 팀 컨벤션이 없다면 지적하지 않거나, 있다면 linter에 위임한다. 코드 리뷰는 코드 스타일 논쟁의 장이 아니다.

---

## 내가 주니어 때 받고 싶었던 리뷰

기술적인 지적보다 **이 결정이 왜 문제인지**를 설명해주는 것. "이렇게 하면 안 됩니다" 대신 "이렇게 하면 X 상황에서 Y 문제가 생깁니다."

리뷰어의 목표는 코드를 수정하는 게 아니라 리뷰이가 다음에 비슷한 상황을 스스로 판단할 수 있게 하는 것이다. 설명 없이 수정만 요구하면 같은 실수가 반복된다.

지금 내가 팀에 합류한 프론트엔드 개발자들에게 코드 리뷰를 줄 때 이걸 기준으로 한다. 코드보다 판단력이 전달되는 게 장기적으로 더 가치 있다.
